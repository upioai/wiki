01
What It Is

它把「判断」从文字里摘了出来

大模型给你一串要解析的文字，Jev 直接给你一个已经定好类型的值——求它吐 JSON 的提示、解析、兜底重试这三层省了。

现在的做法让会写作文的去做选择题

你写一段 prompt 求它「只返回 JSON」，它返回一段文字，你再解析、再校验、再兜底重试。模型多数算力花在了组织语言上。

Jev 的做法选项是你先定死的

答案空间由你在请求里给定，模型只在里面挑。官方称结构化输出错误率 0%（by construction）——不是调教出来的，是结构上不可能。

一次调用的形状
一份 state + 一组题 → 一次并行 pass → 类型化答案
01 · State塞状态字符串 / JSON 对象 / 文本数组，三选一
02 · Questions列题目一份 state 上可以挂一串题
03 · One Pass并行答所有题在同一个 pass 里答完
04 · Typed拿到值枚举 / 布尔 / 分数，各带概率
05 · Branch直接分支结果进 if / switch，中间不再有解析层

// 出处：docs.typesafe.ai/api 的请求与响应样例

02
Three Primitives

只有三种题可以问

整个模型的表达力就这三样。问不出来的东西，它就做不了——这既是它的限制，也是它不会跑偏的原因。

NOUL是非题

返回「为真的概率」，0–1 的一个数。没有单独的 confidence 字段，这个概率本身就是。

"noul": 0.95

CHOICE选项题

从你定义的选项里挑一个，单题上限 255 个。回每个选项的概率 + 一个 confidence。

"choice": "billing"

SCORE评分题

按你给的有序档位（2–10 档）打分，回一个连续值 + 每档的概率分布。

"score": 1.05
Request · TypeSafe 直连格式，结构逐字照官方文档，值是示例

⚠️ 我们走的是 OpenRouter，端点不是这个——见 §05「不是改一个 model 字段」。
两边 body 都是 model + state + questions，但字段是否完全一致，我只有二手确认 [待验证]

先动哪一处，怎么验

横轴看调用频次 × 省下的钱，纵轴看改起来有多容易。点的形状标的是拦路的东西，不是颜色。

落点优先级定位
横轴 = 业务价值 · 纵轴 = 工程就绪度 · 2026-09-20

// 4 + 1 + 1 + 1 + 2 = 9，与 §04 清单一一对应
// 形状编码的是拦路的东西，不是分类——灰度打印也读得出

First Move

从 Akke 装修阶段分类 开刀。它现在就是一次调用对一份 state 出一个枚举——温度 0、输出很短、定时任务里逐 job 调用，和 Jev 的 choice 是 1:1 的，形态一点不用动。

Why Not 意向轴

评论意向轴看着更诱人（四个枚举轴、主干、量大），但它是整批评论一次请求。Jev 的一次调用只对一份 state 出一组答案——换过去，一批 N 条评论会裂成 N 次请求。请求数涨几倍、一批评论塞不塞得进 state+题 ≤32K，这两个问题不回答，它就不该打头阵。

Price

不是改一个 model 字段。OpenRouter 上 Jev 走独立的 POST /api/alpha/decisions（注意没有 /v1），把它丢给 chat/completions 会直接被拒：「is a decisions model and cannot be used with the chat/completions endpoint」。改造量是重写调用层与响应解析，请求体从 messages 换成 state + questions。估工时按这个算。

06
Limits & Open Questions

它不写字，也就替不了写字的

这一栏存在的意义是防止它被当成「更便宜的大模型」——它只是把判断那一半拆了出来。

CAN能换的

  • 主产物是枚举 / 布尔 / 分数的一次性判断
  • 同一份 state 上现在被拆成多次问的那些轴
  • 跑在高频循环里：每条消息、每个 job、每个镜头
  • 需要概率而不只是答案的闸门（能设阈值）

CANNOT换不了的

  • 话术起草、开场白、改写
  • 日报、诊断、摘要 Softie 日报
  • 从昵称推称呼这类短文本生成
  • 任何需要看图的判定——官方原文「No image, audio, or video input」
  • 逐字 OCR 抄写

UNKNOWN还没核的

  • 准确率：官方只给速度与价格，没给判断质量对比
  • state + 最长一题 ≤32K 够不够塞我们的会话历史
  • OpenRouter 那条是 alpha 端点，路径与稳定性可能变
  • beta 期的限流与 SLA，以及国内网络可达性
  • Zkki 知识库条目数有没有超过 255 的 choice 上限
  • 数据出境合规：state 里会带客户原话
Shape

它落在我们既有的那条契约上：模型管分类、起草、摘要、抽取；代码管路由、重试、状态码。Jev 想接管的正是中间那条缝——有确定答案集合、但判据是模糊的那一类，过去只能丢给大模型。

一句话总括：Jev 不是更便宜的大模型，是把「选择题」从大模型手里单独拆出来的一层。我们库里有 9 处主产物是枚举 / 布尔 / 分数的调用点：4 处形态上 1:1 可换（全在 Akke，其中 opener 闸不在定时任务主干）、1 处要从批量改成逐条、1 处要先把判断和生成拆开、1 处代码在但没人调、2 处因为要看图吃不下。先拿 装修阶段分类 影子并跑——但得先写完 OpenRouter Decisions API 的适配层，这不是改个 model 字段的活。在一致率、延迟、成本三个数拿到之前，官方那 193.6× 快 / 444.6× 便宜 只是厂商在自家 workflow 上的数。
