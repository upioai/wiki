1. 给处理同事的结论

近三天并非出现了一个孤立 Bug，而是暴露出同一类系统性问题：单台云电脑依靠截图、OCR/VL 和鼠标键盘串行操作企业微信，但任务没有完整的持久化状态、租约、逐项回读和自动恢复机制。

因此，一个假红点、错误裁剪、遗留 STOP 文件、搜不到的退群服务群或失败后被误记为“已处理”的任务，都可能造成：

  • 真实客户消息被已读但未回复；
  • 首触文字或图片漏发，系统却不再重试；
  • 一个坏召回任务长期占住队列，后续客户全部延误；
  • 代码已合并，但无法确认云电脑是否加载、客户是否真实收到；
  • 运营只能靠人工看屏、贴日志、重启来恢复。

当前代码已经修复了多数已知触发条件，但“以后不再出现新 Bug”不能靠继续补词表实现。必须完成第 5 节的状态机、事务 outbox、任务租约、自动部署验收和 UI↔DB 对账。

4. 当前权威运行顺序（处理时不要改回旧架构）

销售号 B 的机器只操作企业微信左侧 “消息”主页面，不得点击“客户咨询”。所有 GUI 动作必须在同一进程串行：

  1. 确认仍在消息主页面；
  2. peek_recall 只看是否存在 pending，不提前 claim；
  3. 扫描真实客户未读，存在则优先回复；
  4. 无可执行客户未读时，立即 claim 并发送一条召回；
  5. 召回成功后保留 120 秒短链路，快速处理下一条；
  6. 没有 pending 时，才扫描新服务群并做首触；
  7. 任何内部会话、系统通知、我方末尾或幽灵红点都不能永久阻断后续任务。

5. 必须完成的根治方案

5.1 P0：持久化事件状态机

不要再把“红点消失”当作处理完成。每条客户消息、首触和召回统一记录：

TEXT
detected → identified → read → planned → sending → visually_verified → confirmed
                                  ↘ failed_retryable
                                  ↘ failed_terminal / dead_letter

要求：

  • 只有 confirmed 才允许去重；
  • OCR/VL 失败、焦点丢失、网络失败不得推进基线；
  • 每一步保存时间、尝试次数、截图/日志证据和失败原因；
  • 状态必须落服务端，不能只放云电脑内存或永久 flag 文件；
  • 相同业务事件使用稳定幂等键，进程重启后可续跑。

5.2 P0：事务型发送 outbox

首触“文字 + 活动图 + 配置图”和召回素材拆成独立 outbox item：

  • 每项分别记录 pending/sent/verified/failed；
  • GUI 视觉回读确认气泡类型、目标群和内容后，才标记该项完成；
  • 全部必需项完成后，才能提交业务任务 completed；
  • 中途宕机从未完成项恢复，不重复已确认项；
  • 素材保存 poster_id + SHA-256 + 尺寸 + 期望气泡类型。

5.3 P0：有租约的任务队列与死信隔离

  • claim 必须带 lease 到期时间和 worker/version；
  • 进程死亡、心跳超时后自动释放；
  • 明确退群、拒绝等业务终态立即停止该客户全部兄弟任务；
  • 搜索失败、VL 不确定、焦点失败归类为可重试技术错误；
  • 超过阈值进入 dead-letter，跳过坏任务继续后续客户，并自动推异常卡；
  • 调度按客户回复 SLA、首触 deadline、召回窗口和等待时长公平排序，禁止单任务无限占队。

5.4 P0：自动部署、验收与回滚

自更新不能只做到“下载新脚本”。完整流程应为：

  1. 拉取带签名/哈希的新版本；
  2. 原子替换脚本；
  3. 受控结束旧 PID 并启动新 PID；
  4. 回报 commit、loop version、MD5、PID、启动时间、心跳；
  5. 自动跑只读冒烟：消息主页、截图边界、焦点门、服务端 ping；
  6. 5 分钟内冒烟或心跳失败，自动回滚上一版本；
  7. Lark 发送部署结果卡，明确“代码合入 / 机器加载 / 客户侧验证”三个层级。

5.5 P1：UI↔DB 自动对账

每天至少一次检查：

  • 客户末尾消息超过 5 分钟仍无 reply event；
  • UI 已发送但 DB 未 confirm；
  • DB 标 completed 但 UI 缺文字或图片；
  • pending/claimed 超出租约；
  • 同一客户重复权威 conversation；
  • 首触三项状态不完整；
  • stopped 客户仍有活跃召回；
  • 云电脑版本落后线上版本；
  • crop 自检异常、VL JSON 失败率、焦点恢复率突增。

发现异常后优先自动修复；不能安全修复的，推送带截图、任务 ID、版本和一键操作入口的异常卡。

5.6 P1：确定性门与 VL 的职责边界

  • 代码能判断的城市、价格、素材路由、任务状态、重复发送、退群终态，不交给 VL；
  • VL 只用于读取原生自绘 GUI，输出必须经过 schema 校验；
  • 裁剪前先自检边缘是否切字、输入框边界是否正确；
  • OCR/VL 不确定时弃权并重试，禁止猜测；
  • 长期评估企业微信官方能力能否覆盖部分入站/出站场景，逐步减少 GUI 依赖。

6. 交给同事的执行顺序

第一阶段：48 小时内，消除全局停摆

  • 为客户回复、首触、召回定义统一事件状态和幂等键；

8. 排障时的证据顺序

  1. 云电脑本地状态文件里的脚本版本，是否等于服务端当前下发的脚本版本；
  2. 当前 PID、启动时间、MD5、最近心跳；
  3. [recall-fast]、peek_recall、claim、sent、末尾方向、焦点恢复日志；
  4. 原始截图和实际送入 VL 的裁剪图是否完整；
  5. 事件状态、outbox、dispatch lease 与 stop reason；
  6. 最后才判断是模型问题。不要看到读屏异常就先换模型或改 prompt。
