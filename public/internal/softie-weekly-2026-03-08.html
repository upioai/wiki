🧭流程上的隐患

① 同一类问题反复修 待加强

键盘和布局相关的问题在 3/5–3/7 修了 5 次以上（输入法、软键盘遮挡、横竖屏、安全区、离线提示）。每次 commit 解决了眼前那个问题，却漏了边界情况，只好下一个 commit 再补。原稿的判断是：AI 辅助修复对单点很精准，但对上下文的覆盖不全。

② 高风险代码直推 main 待加强

3/5 以后的直接 commit 里有 iOS IAP、Google Play Billing、支付 provider fallback、上架合规过滤。这几块涉及钱和合规，都没有经过 review 就进了主干。

③ 同一文件被碎片化 commit 反复叠加 待加强

3/6 的 commit 很多，每个只改一个小点，却一次次落在同一批文件上（聊天页、AndroidManifest、离线提示组件）。测试跟不上时，这样最容易引入回归。

做得好的地方 保持

  • 一周内打通 Android 上架准备和 Android / iOS 两端原生支付，并统一了支付路由（Apple IAP / Google Play Billing / Airwallex）
  • 测试从修复失败用例起步，补到 131 个单元用例和 3 个 E2E，运行时间从 146s 压到 1.1s
  • 集中补了一批安全问题：生产禁止自定义系统提示（防 prompt 注入）、上传接口补管理员鉴权、Sparks 金额校验、服务账号 JSON 加进 .gitignore、media API 补 CSRF、Android 强制 HTTPS
  • 支付事务一致性：webhook 处理和订阅 / Sparks 发放放进同一个事务，不再出现「支付成功但没到账」的中间态

✅建议与遗留技术债

优先级建议
高支付相关代码（IAP / Billing / 收据校验接口）一律走 PR + review，不直接 commit
