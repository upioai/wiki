01

先分清三条跑道

"夜里让 Claude Code 干活"其实是三件不同的事。选错跑道，后面所有工程都白做。

/goal
有人守着的长任务

你在终端里，任务要跑很久，你希望它"没做完别停"。它是会话内的机制：关终端就没了。

适合
下班前挂一个大重构，睡前回来看一眼
不适合
无人值守——没有调度器、没有告警、没有留痕
claude -p + launchd
本机凭据 / 本地仓 → 只能走这条

任务需要本机 Lark CLI 的凭据、需要读本机好几个仓、需要写本地文件时，唯一可行的形态。我们的 23:03 那班就是它。

为什么不用 cron
笔记本睡眠会冻结计时；launchd 的 StartCalendarInterval 唤醒后会补跑
代价
机器得开着；日志要自己收；告警要自己接
GitHub Actions + claude-code-action
默认选它

只要任务的数据能从 API 拿到、产出落在仓里或推到群里，就走这条。有 run 历史、有 Summary、有失败告警、有 timeout-minutes 兜底，全是白送的。

成本闸
--max-turns + timeout-minutes + concurrency
坑
schedule 只认默认分支上的文件，PR 里验不出来
/schedule（云端 Routines）
无状态的轻活

Anthropic 云端跑，不依赖你的机器。但它读不到本机任何东西——只 clone 你选的 GitHub 仓，MCP 只能用 claude.ai connectors。

限制
最小间隔 1 小时（2026-08-11 读官文核过）；绿灯只代表容器没崩，得点进 transcript 看
一句话判据

问："这个任务需不需要读我这台电脑上的东西？"——需要就 launchd，不需要就 GitHub Actions。/goal 不参与这个选择，它解决的是另一个问题。

02

/goal 到底是什么机制

很多人以为它是"任务队列"。不是。它是一个停机条件评估器，理解这点才知道它什么时候有用、什么时候会空转。

/goal <condition> 给当前会话装一个停机条件。之后每一轮结束时， Claude Code 会另起一次独立评估，把整段对话记录喂进去问一句： 

Based on the conversation transcript above, has the following
stopping condition been satisfied? Answer based on transcript
evidence only.

CC 2.1.258 二进制内的原文

没满足，就注入一条 check-in 继续干；满足了，才允许停。要点：

  • 一次只有一个 goal，新的会顶掉旧的；/goal clear 提前结束。
  • 判据是"对话记录里有没有证据"，不是"文件系统里是不是真的做完了"。所以条件必须写成可在 transcript 里落地的事实——"跑通 pnpm test 并把输出贴出来"是好条件，"把代码质量提上去"是坏条件。
  • 它需要受信任的工作区，且当 hooks 被策略禁用时直接拒绝运行。
  • 后台还挂着活的时候，check-in 会变成"去看看它进展如何"，而不是催你重做——但空闲 check-in 有次数上限，撞到就只重新计时不再注入。
我们踩过的那次

有一轮 goal="彻底隔离两个项目"，剩下的步骤是"在第三方后台建一个新 project、生成一把新 API key"—— agent 物理上做不了。停机条件永远不满足，循环空转了 7 次才被人掐掉。

判据：goal 的条件里不能包含任何需要人去点鼠标的步骤。 真遇到了，就把"代劳不了的清单"单独交付出来并主动停，别让循环自己撞墙。

顺带一条同源的：goal 模式下用 brainstorming 类流程，问完核心问题就直接按推荐方案执行。 "提方案 → 等确认"会被停机检查判成"还停在规划阶段"，于是它催你，你又去等确认，循环。

03

一个夜班的六个零件

这是门店工作台仓「值班医生」这一班（2026-08-21 上线，至今 12 天）沉淀下来的骨架。少任何一个，失败形态都是全绿。

零件 1
先查钥匙在不在

第一步不是干活，是检查每一把 secret 非空，缺了硬失败退出，不静默降级。

但要写清楚这一步的边界：它只能查"存在性"，查不了"有效性"。一把过期的 token 和一把好用的 token 长得一模一样。有效性由零件 5 兜。

零件 2
取数（确定性部分）

该用代码算的全部用代码算完，把结果落成一个文件交给 agent，让它只做判断不做取数。取数失败要说"取不到"，不能吞成"没有问题"。

# --fail-with-body：4xx/5xx 非 0 退出【并且】把 body 打出来
# 光 --fail 会把 503 吞成一句 curl 22，查不出是缺哪把钥匙
curl -sS --fail-with-body --max-time 90 \
  -H "Authorization: Bearer ${API_TOKEN}" \
  "${BASE_URL}/api/..." -o report.json
零件 3
agent 那一步

--allowedTools 是干得成活的必要条件，不是安全装饰。删了这一班就变成"绿勾 + 零产出"。

模型档位按任务定，不要照抄别的 workflow。值班班干的是归因——"体检说心跳丢了，去查为什么"——弱模型会停在第一个看起来对的答案上，把症状当根因报出来。一天跑一次的班，档位差价可以忽略。

claude_args: >-
  --model claude-opus-5 --effort xhigh --max-turns 60
  --allowedTools "Read,Grep,Glob,Edit,Write,Bash(git:*),
    Bash(gh pr create:*),Bash(gh pr list:*),Bash(gh pr view:*),
    Bash(gh label:*),Bash(node:*),Bash(pnpm test:*)"
零件 4
产出落成文件

让 agent 把结论写进仓库里的一个文件，而不是只写进 Summary。两个原因：下游步骤要读它；空跑检测要判它。

GHA 给每个 step 各自一份 $GITHUB_STEP_SUMMARY——上一步写进去的东西，下一步根本读不到。

零件 5
空跑检测

整份骨架里最重要的一步。绿勾 + 零产出 = 门禁失效，而这两者在 Actions 页面上长得一模一样。

# 判据必须是 agent 真正落盘的那个文件
if [ ! -s doctor-verdict.md ]; then
  echo "::error::值班 agent 空跑"
  exit 1
fi

零件 1 挡的是"已知原因"（钥匙没配）；这一步挡的是任何原因——token 无效、限流、action pin 被 bump、--allowedTools 被谁删了。

零件 6
双指标 + 心跳

每个夜班必须同时落两个数：① 自身存活（heartbeat 文件 mtime / 每周一强推一张卡）和 ② 业务 delta（本轮处理了几条、改了什么）。

"exit 0" 不等于业务有效。反过来也要小心：产线不健康不该让这个 workflow 红灯——让它天天红，两周后所有人都学会忽略这个红灯。红灯只留给"取不到数"和"agent 空跑"。

②必须落到最细的产出单元。管线吃多个源时，聚合数字健康会完整掩盖其中一个源的死亡。判据："这条班声明要处理 N 个单元，我能不能说出每个单元今天各产出了多少？"答不上来就是没落到位。

本机那条链长什么样

launchd 版本的六个零件，压缩在一个 30 行的启动脚本里（节选）：

#!/bin/bash
set -u
# launchd 的 PATH 极简，node / claude / lark-cli 全要显式写全
export PATH="<claude 所在目录>:<lark-cli 所在目录>:<node 所在目录>:/usr/bin:/bin"
# launchd 不读你的 .zshrc，node 版本管理器那段路径漏了 claude 就起不来

date '+%F %T' > "$DIR/heartbeat"          # ① 存活心跳

OUT="$(claude -p "$(cat "$DIR/PROMPT.md")" \
        --dangerously-skip-permissions 2>>"$LOG")"
RC=$?                                       # ② 退出码
printf '%s\n' "$OUT" >> "$LOG"

# ③ 业务 delta：prompt 里约定它必须吐这一行
RESULT="$(printf '%s\n' "$OUT" | grep -E '^AUDIT_RESULT ' | tail -1)"
if [ $RC -ne 0 ] || [ -z "$RESULT" ]; then
  echo "[$(date '+%F %T')] FAILED rc=$RC" >> "$LOG"
  exit 1
fi

本机夜班的启动脚本（路径已略）· 在跑

写脚本时的三条

① 判成败的命令不许接管道。cmd | tail -5 的退出码是管道最后一条命令的，失败会被伪装成 0。 重定向到文件再读，或用 set -o pipefail。
② --bare 和订阅 token 二选一，别两个一起写。 --bare 跳过 hooks / LSP / plugin sync / auto-memory / keychain 读取 / CLAUDE.md 自动发现， 让每台机器上结果一样（skills 不受影响，仍可用 /skill-name 触发）。 但它的鉴权严格只认 ANTHROPIC_API_KEY 或 apiKeyHelper，OAuth 与 keychain 一概不读。 所以要用订阅额度（CLAUDE_CODE_OAUTH_TOKEN）就不能加 --bare， 加了得到的是 Not logged in——而按案例四的机制，这在 Actions 页面上和空跑长得一模一样。 我们四个仓目前 --bare 用了 0 次，全走订阅 token；要用 --bare 就得改配 API key，那是按量计费。
③ 想拿单次成本就上 --output-format json，返回里带 total_cost_usd（客户端估算，与账单会有出入）。

04

提示词怎么写

夜班的 prompt 和白天的对话不一样：它要在没人纠正的情况下连着跑三十天，所以每一句都要能挡住一种漂移。

一、先写"你不许做什么"，再写"你要做什么"

越界比漏做严重得多。我们值班班的边界段是逐条从事故里长出来的：

  • 绝不写库、绝不改任何任务状态。手工改一次任务表废掉过一条已付费的单。
  • 绝不碰线上 env / secrets / 部署配置。
  • 不重复 CI 已经在做的事。代码回归由 CI 守；夜班该盯的是 CI 看不见的东西——没人改代码的日子，代码不会自己坏，但线上现实会漂。

二、把"读数的口径"写进 prompt，否则它会把数据读反

我们的体检阈值全部按一天校准（失败码 ≥2 报 FAIL）。同一套判据套在 30 天窗口上必然偏红—— 那是量纲错配，不是产线出事。首跑那天 agent 差点让人照着 30 天窗口的红灯去查工厂机日志。 现在 prompt 里明写：判"今天有没有事"只看 24h 那份，长窗口那份只看趋势、不看它的 level。

同理要写清"这条业务线现在处于什么阶段"。调试期的成片堆积是正常产物，不写清楚，agent 每天都会把它报成积压问题。

三、给人看的那份，规矩要比给机器看的更严

推进群的卡片和 Actions 里的完整报告说的事实必须一致，但长度不同。我们在这上面翻过两次车： 第一次 agent 把"结论 / 归因 / 改动 / 待办"四段平铺推过去，用户原话是"太乱了，我看不清重点是什么"； 第二次它深挖之后写了 630 字技术报告，回复是"我没看懂"。

现在群卡片的硬规矩：

  • 第一段永远是"今天要你做的"，哪怕内容是"没有，你不用管"。人的第一诉求是"要不要我动手"，不是"你查到了什么"。
  • 总共不超过 12 行，超了就砍归因细节（那些在 Summary 里）。
  • 不出现代码路径、行号、error_code 原文、函数名。要给证据就给 Actions 链接。
  • 判据：把这段念给一个没看过代码的人听，他能复述出"发生了什么、要不要做什么"——做不到就重写。
  • 再加一段"可以让我做"，给 2–3 句她能直接复制的话，而且必须贴着今天的实际情况。别写你做不到的（"重启工厂机"——你碰不了线上配置），她照着说了却办不成，比不给例子更糟。

四、允许它说"本轮无事"

prompt 里要明写："没学到就明说本轮无新知——那跟本轮无操作一样是合格的结论。不要为了有产出而写。" 不写这句，一个每天都要交作业的 agent 会开始编。

同理，如果让它沉淀经验，要求它写判据不写数字："失败率 38%"三个月后是错的，而"replica- 前缀是两条线共用的、不能当判据"明年仍然成立。

05

事故柜

下面每一条都发生在我们自己的仓里，都能在 origin/main 上查到。它们共同的形态只有一个：全绿。

日报停更 8 天，连红 7 天无人认领

main 上了分支保护之后，日报 workflow 里的 git push origin HEAD:main 一律被拒。 代价不是"少了个 commit"——那一步 exit 1 会中止整个 job，后面"发布到公开站"和"推群摘要"两步一起被 skip。

规矩　一个夜班里，把产出送出去的那一步必须排在所有回写之前，或者干脆不回写本仓。
主仓 · 日报 workflow
监控自己死了 10 天，而它每天照常告警

一次重构把索引文件搬进了新目录，检查脚本的 readFileSync 在模块顶层就 ENOENT，整个采集器当场死掉，4 项比对一项没跑成。 外层 continue-on-error: true 让上层照常绿，告警脚本每天照常追一条"复查仍异常"—— 看起来像"监控还活着、问题还没修"。

规矩　告警还在日更，不代表监控还活着。搬文件/改路径时，回查所有指向它的闸门。
门店工作台仓 · 采集器检查脚本
14 条断言全绿，守的却是错的东西

上面那次事故里，那个文件有 14 条测试断言，一条都没红—— 其中直接守着采集器的那 11 条全是源码文本断言： 守的是"代码里有没有这句话"，守不住"这句话指向的文件还在不在"。

规矩　源码文本断言至少要配一条把那段代码真的执行一遍的测试。同一条教训第 4 次复发时，不要再写第 5 遍文档，改成机器闸。
门店工作台仓 · 同一采集器的测试
上线第一天起 100% 空跑，两天 100+ run 全绿零产出

配进去的 CLAUDE_CODE_OAUTH_TOKEN 值本身无效——非空、能过存在性检查，但 API 侧不认。 每次 init 后约 2 秒即 is_error=true、1 轮、$0、零评论，action 却照报 success。 期间自动合并脚本一直拿这个"绿勾"当"审过"在合 PR。

规矩　这就是零件 5 存在的理由。存在性检查挡不住无效凭据，只有产出断言能。
门店工作台仓 · 审查 workflow 头注
三层叠加，合并能力静默归零

① 汇总函数无条件 return 0，任何拦截都不影响退出码；② 按决定不推群；③ 失败告警的监听名单里没有这个 workflow。 三层叠加 = 那把 PAT 一过期，run 永远 success，只剩日志里一行没人翻的"够格但没 PAT"。

规矩　只把"机制故障"算作失败，"正常拦截"一律不算——实测最近 100 条已合 PR 有 57% 命中高危路径，拿它当失败会让 run 天天红，告警立刻废掉。
主仓 · 自动合并脚本
让 agent 去开一个它开不了的 PR

值班手册写着"改好基线就开一条 PR"，但两个班的 prompt 都在 .github/workflows/ 里， 而 GitHub App 的 token 不允许创建或修改该目录，push 直接被拒。 值班照着做，改好文件、commit、push 才撞上这堵墙，白烧一轮。

规矩　prompt 里要求的每个动作，都要先确认它的 token 真做得到。做不到就改成"把可直接复制的替换行贴进 Summary，标明要人代改"。
门店工作台仓 · 值班手册
10 个 workflow 抢同一个仓

多个夜班在同一时段往同一个发布仓 push，non-fast-forward 直接红。修法是加撞车重试。

规矩　写同一个目标的班，要么错开时间，要么加 concurrency 组，要么加重试。并发不是小概率事件，是必然。

空跑检测自己误报，每天红灯而产线没事

用 sleep 定时，被 Mac 睡眠冻结

为量晚高峰链路劣化写了个采样脚本，用 sleep 到点 + nohup。 笔记本一睡，计时跟着冻结，6 轮一轮没跑——进程还活着、日志有头部，看起来完全正常。 而本机早就有一个 launchd 版的同类采样器，跑了一整晚。

规矩　"等到某个时刻"一律走 launchd（唤醒后补跑），不要用 sleep 循环。动手前先列一遍本机已有的 launchd 任务。

它已经不跑了，长得和天天全绿一模一样

GitHub 会在公开仓里把 60 天无活动的 scheduled workflow 自动停掉，不报错不通知。 我们这几个仓都是私有库，这条机理对它们不成立——但结果一样： §00 那条实测说了，schedule 本来就会整天不跑。 两种情况下你看到的都是同一个画面：最近好像没看到那张卡。

规矩　每周一强推一张心跳卡，不管绿不绿——这是唯一能区分"一切正常"和"它已经不跑了"的信号。配套的：拿"上次运行时间"判活时，宽限必须大于一个完整周期（日频班取 ~1500 分钟），否则光是那 40–70 分钟的漂移就够它每月误报几次。

今晚开第一个班

别一上来就搭会动手的班。第一个班必须是只读的——先证明它每天都真的跑了、真的产出了，再给它写权限。

三个适合起步的班

当日复盘
只读 · GitHub Actions · 20 分钟搭完

拉今天的 commit / 合并的 PR / 关掉的 issue，写一段"今天这个仓发生了什么、有哪三件事明天该接着做"，推到群里。

为什么先做它
产出对错一眼可验，出错代价为零
代码审计
只审不修 · 结论落盘

审计和修复必须分成两个会话。审计会话只交付两样：结论落盘成一份 docs/audit-YYYYMMDD.md，以及一段下一轮可直接粘贴的修复提示词。

为什么
实测多轮多 agent 审计全部停在"汇总"，零修复落地
业务探索
只写 issue，不写代码

给它一个方向（"看看竞品这周发了什么"、"我们的 X 指标为什么在掉"），让它调研完开一条 issue，附证据链接。

硬约束
结论必须带来源链接；说不清来源的一律标"待验证"
别做的三类
红线

无人值守时不要：改数据库或任务状态、动线上 env / secrets / 部署配置、往公网发布任何未经打码的内容。

起步清单

先列一遍本机已有的 launchd 任务和仓里的 .github/workflows/，确认没有人已经在做这件事本机沉淀的同类脚本通常带着历次事故的补丁，扩展它 > 另起炉灶
选跑道：要读本机东西 → launchd；不要 → GitHub Actions
配 CLAUDE_CODE_OAUTH_TOKEN（本机 claude setup-token → gh secret set）用订阅额度，不走 API 按量计费；注意它绑在跑 setup-token 那个人的订阅上。⚠️ 用它就不能加 --bare
拿这把 token 在本机真跑一次 claude -p "回一个 ok"，确认它能鉴权，再往 Secrets 里塞案例四那两天 100+ run 全绿零产出，起因就是漏了这一步：token 非空、存在性检查过得去，API 侧不认
cron 错开整点几分钟，并在注释里写清 UTC ↔ 北京时间的换算
写钥匙存在性检查（缺了硬失败）
写 --allowedTools、--max-turns、timeout-minutes、concurrency
写空跑检测（判 agent 落盘的那个文件，不判 Summary）
接进失败告警名单，并真实发一条验证送达日志里写着 "alert sent rc=1" 不算告警——没人读日志。判据：这条告警最近一次真实送达的 message_id 是什么？
加每周一心跳推送
用 workflow_dispatch 手工跑一次（schedule 只认默认分支，PR 里验不出来）
连着看三天的 run，确认产出内容每天都不一样每天输出一模一样，通常意味着它在复述 prompt 而不是在读数据
一个容易漏的坑

claude-code-action 对每次运行都会检查触发者是不是机器人。 定时触发也算——GitHub 会把它归属到"最后改过这个 cron 的人"。 如果那个人是个 bot 账号，这一班永远起不来，得把它列进 allowed_bots。
