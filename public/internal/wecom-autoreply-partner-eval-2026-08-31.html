01客户加了销售的企业微信，然后就沉在那儿了

THE GAP

投放和短视频把人带到企业微信，接下来全靠销售一个人扛。三个卡点都不是「销售不够努力」能解决的。

LATENCY接不及时

客户问一句「你们整装多少钱一平」，销售可能在量房、在开会、在另一个客户那儿。两小时后再回，人已经问过三家了。

CONSISTENCY话术不齐

同一个问题十个销售十种答法。有人报错价，有人漏掉该问的户型和预算，有人把客户聊死了自己都不知道。

FOLLOW-UP老客户没人跟

聊过一轮没成交的，理论上该在一周后跟一次。实际上没人记得，也没人有那个时间。

我们要解决的

AI 接待做的就是这三件事：第一时间接上话、把该问的信息问全、到了该人接手的节点主动交出去。它不替代销售。它保证销售接手的时候，手里已经有东西——客户是谁、要什么、聊到哪一步了。

02官方接口我们试过，撞在两道硬墙上

WHY THIS PATH

做企业微信自动接待只有两条路。这一页说清楚我们为什么把云电脑代回做成了主力，而不是嘴上说的「对接官方 API」。

对比项方案 A · 企业微信官方接口方案 B · 云电脑代回
备案域名回调域名必须完成 ICP 备案，且备案主体须为贵司营业执照主体不需要
企微后台配置需建自建应用 / 开通客服，改回调与可信域名不需要
能接哪种消息只接客服入口来的（公众号 / 小程序 / 视频号 / 二维码）客户直接加销售的普通单聊
覆盖真实获客场景看获客入口，多数门店走不通绝大多数
额外硬件无一台常开 Windows 环境
平台位置官方开放能力自有账号自有设备，非官方开放范围
我们的交付状态做过技术验证，尚无交付先例现役主力，生产运行中
这一条纯技术手段绕不过去

方案 A 的备案墙我们实测撞过：托管平台（Vercel、Fly 等）的默认域名、裸 IP 一律被判「域名主体校验失败」。不是配置问题，是资质问题——备案主体必须就是那家企业自己。

而官方的微信客服接口，接得住的只有从客服码进来的消息。客户直接加了销售企微号之后的正常单聊，它碰不到——偏偏那才是门店真实的获客形态。

所以方案 B 的存在理由只有一句

它跑在贵司自有的企业微信账号和自有设备上，不涉及任何协议破解或第三方外挂，不需要备案域名，也不用动企微后台一个字。代价是需要一台常开的 Windows 环境，我们提供部署与巡检。

03端上只管收发，判断全部留在服务端

ARCHITECTURE

这是整套系统最要紧的一条分工。端侧换掉不影响话术、知识库和历史数据，改一次话术也不用碰任何一台设备。

  1. 执行端云电脑读屏。

    阿里无影云电脑上跑一个 Python 主循环，截屏识别出「有新消息、是谁发的、说了什么」。读屏用的是视觉大模型，分大活 / 小活 / 兜底三档，任一档不确定就不往下走。

  2. 中转外网中转。

    云电脑连不上业务服务端，中间架一层自有中转做转发。这一跳同时是限流与审计点。

  3. 服务端大脑生成回复。

    拼装这个客户的对话记忆、企业知识库、业务规则与销售人设，交给大模型出一句话。所有判断只发生在这一层。

  4. 护栏发之前先过闸。

    价格是否有依据、要不要转人工、是否会连发多条、身份有没有串——逐条由代码判定，不靠模型自觉。

  5. 执行端模拟点击发出。

    回到云电脑，把这句话打进对话框发出去。确认送达才回写记账，发失败不会被算成一次成功接待。

  6. 人在环人工把关。

    销售每天过一遍对话记录；触发转人工的会话直接静音并告警到本人。链路存活由三路探针每 15 分钟自检一次。

这样拆开换来什么

换端不用重写业务（今天是云电脑，明天换真机或换通道，服务端一行不动）、出问题能逐条回溯（每次生成都留痕）、改话术不用碰设备（话术在服务端配置里，不在脚本里）。

04什么时候该 AI 回，什么时候必须交给人

DECISION PATH

交接口是确定性的代码判据，不是让模型自己判断「这句我该不该回」。判据刻意做得保守：宁可多回一轮，也不能把一个正常咨询的客户永久闭麦。

客户新消息企业微信单聊
↓
服务端大脑生成候选回复记忆 · 知识库 · 规则 · 人设
↓
命中交接判据？由代码判定
否 → 合并成单条发出确认送达才记账
是 → 停回复 · 告警到本人会话置为已交接

交接判据（节选）· 客户投诉 / 连续拒绝 / 临门谈价 / 明确要求找真人 · 判据与冷却期均可按贵司口径调档

为什么这条必须是代码

「这个客户生气了，别再自动回了」——如果交给模型自己判断，它大部分时候对，偶尔一次错，而那一次就是事故。所以这一层做成确定性判据：命中即停，不做概率判断。

反向也一样重要：判据宁松勿紧。把一个正常咨询的客户永久转人工，等于让他在没人看的会话里干等——那比多回一轮糟得多。

05不让它说错话的六件事

GUARDRAILS

每一条都是被真实事故逼出来的，不是设计阶段想出来的。通用大模型最贵的毛病不是答不上来，是一本正经地编。

HANDOFF转人工

确定性判据触发，会话置为已交接并停止自动回复，同时告警到销售本人。带冷却期，误触发能自动复活。

PRICE GUARD价格

输出里一旦出现价格数字，与该品牌登记的价格区间比对。品牌没登记区间却报了价，几乎必然是编的——打标进盯盘。

SINGLE BUBBLE形态

带换行的内容会被企微拆成多条连发，那是最像机器人的瞬间。这条已从「提示词里请求模型注意」升级成代码硬闸：合并成单条才允许发出。

IDENTITY身份

多个销售身份并行运行，各自的人设、语气、可承诺范围分开。身份串了就是当场穿帮，所以这一层不共用。

RED TEAM压测

一组带性格的虚拟客户（爱砍价的、挑刺的、只问不买的）定期与线上话术对打，回归验证护栏是否还在生效。上线前不靠「感觉还行」。

TRACEABILITY回溯

话术、模型、规则、脚本、语料五层各有版本，联合成一个版本号并快照留存。出了问题能定位到那一刻的完整配置，也能整体回滚。

工程侧的兜底

仓内 114 个测试文件、23 条 CI 流水线、14 个定时任务；链路存活由三路探针每 15 分钟自检。还有一道「看闸的闸」——护栏本身失效也会被发现，而不是安静地不再触发。

07顺带一提：AI 说的每句话，都能查到出处

KNOWLEDGE BASE

接待系统背后连着一套企业知识库。它不是接待的前置条件，但决定了 AI 回答产品问题时是「照着资料说」还是「凭常识编」。

层装什么量级
企业文档品牌手册、工艺说明、行业资料，整篇按相关度进上下文近百
金牌话术真实销售对话，按阶段和质量分挑选后作为范例数百
素材条目可检索的资料条目，切分为可引用片段数千（部分启用）
知识积木从资料里抽出的可复用事实块，逐条启用数百
决策规则确定性业务规则，不交给模型自由发挥数十
门店事实本店可做什么、不做什么、服务范围百余
难做的是后半段

向量检索、开源 RAG 框架市面上到处都是，一周能搭一个。它们解决的是「从一堆文档里找到相关句子」，不解决「怎么保证这句话现在还成立」「怎么让模型没法虚构来源」。

所以我们没把资料直接丢给模型自己看着办。资料先被结构化拆解、按业务域归类，机器做预审，但最终由人在工作台上点亮，才允许被 AI 引用。没点亮的资料就在库里灰着，模型看不见。

为什么这件事值钱

编一个你们没有的工艺，编一个你们没报过的价，编一份不存在的检测报告——客户拿着截图上门时，赔的是甲方。这一层就是为了让那种事没有发生的路径。

08四周，以及需要贵司准备的东西

ROLLOUT

这个节奏是按同类交付排的建议值，可以按贵司实际情况调。第三周是最关键的一周——目标不是省人力，是把话术问题暴露完。

WEEK 1
资料与话术

收集企业资料与真实销售对话，做结构化拆解与归类；确定人设、可承诺范围、价格口径与禁区。

WEEK 2
环境与联调

部署云电脑执行端、接通企微账号、跑通端到端。用虚拟客户做首轮压测，把明显不能说的话先关掉。

WEEK 3
灰度

先挂 1–2 个销售号、每条回复人工过目。这一周把话术问题暴露完，比省下多少人力重要得多。

WEEK 4
放量与交接

扩到全部销售号，人工复核从「逐条」降到「抽检」，转人工规则按真实情况调档，交接日常运维方式。

需要贵司提供 · PREREQUISITES

  • 一位企业微信管理员，负责账号与权限
  • 参与试点的销售企微号（建议从 1–2 个起）
  • 一台可以常开的 Windows 设备环境（云电脑或本地机均可，我们负责部署与巡检）
  • 企业资料：手册、报价口径、工艺说明、常见问题
  • 一位能拍板「这句话能不能说」的人——这是最关键的一个角色
  • 灰度期每天愿意花二十分钟看对话记录的人

09我们不承诺的事，先说在前面

BOUNDARIES

  • 不承诺无人值守。2026-08-21 我们把产品里这个模块的名字从「企微自动接待」改成了「微信接待」，主动去掉了「自动」两个字——现阶段每天仍需人工逐条检查，叫「自动接待」属于过承诺。如果有供应商说他们能完全无人值守，请让他把最近一周的真实对话记录调出来给您看。
  • 不承诺成交率提升多少个百分点。转化受产品、价格、区域、投放质量共同影响。我们能承诺的是响应速度、话术一致性和跟进覆盖率——这三项可以量化验收。
  • 不承诺平台规则不变。方案 B 跑在自有账号与自有设备上，不涉及协议破解或第三方外挂，但也不属于企业微信官方开放的能力范围。我们的做法是把接入方式做成可切换的：业务逻辑全在服务端，端侧换掉不影响话术、知识库和历史数据。
