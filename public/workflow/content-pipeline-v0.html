这是内容生产流水线的架构起点：定了状态机、表结构、vendor 适配器框架，跑通了 ffmpeg dryrun 合成。当时默认选可灵做视频、火山豆包做 TTS。后续的模型选型细化见 AI 短剧调研 v2（同样收敛到可灵，但升级到 Kling 3.0 + @Element 原生一致性）。

1目标与边界

为 Akke 自己（及未来客户）的新号自动产出"业主 vs 设计师"AI 真人短剧短视频。端到端到成片落库为止，最后一步不接自动发布——由运营手工上传抖音，避免短期内绑定云手机/第三方上传 API 的风控风险。

选题→脚本→分镜→视频生成→配音→字幕+成片→待发布

不在 v0 范围：抖音矩阵自动发布、评论/私信自动响应、直播/长视频/横屏；聚焦 9:16 竖屏 ≤60 秒。用户已明确选"AI 真人短剧"而非数字人代播。

2架构（复用现有骨架）

基本从零起，但骨架齐全——多租户 RLS / Vercel cron / Fly worker / Langfuse 观测全复用，新增工作量集中在"视频 vendor 适配 + 状态机 + 拼接 pipeline"。

Vercel (Next.js)
  ├─ /api/cron/content-generate-topics  (每日 09:00)
  │    读 brand_profile + knowledge_documents → LLM 生成选题
  ├─ /api/cron/content-advance           (每 15 分钟)
  │    approved topic → 脚本 → 分镜 → enqueue 渲染 → 监控 → 拼接成片
  └─ /api/content/{topics,scripts,posts}/approve  (运营审稿)
        │
        ▼  scrape_jobs(job_type='content_render_*')
Fly worker (FastAPI + Playwright + ffmpeg)
  ├─ /content/storyboard   script 拆分镜（LLM）
  ├─ /content/render-shot  单分镜调 video vendor
  ├─ /content/tts          分镜配音调 TTS vendor
  ├─ /content/compose      ffmpeg 拼接 + 字幕烧录
  └─ services/video_gen/   策略模式适配器（kling / dreamina / runway / dryrun）
        │
        ▼
Supabase: content_topics / content_scripts / content_shots
          / content_assets / content_posts  (+ Storage)

3状态机

content_topics（pending→approved→producing→done）→ content_scripts（drafting→reviewing→approved→done）→ content_shots/content_assets（queued→generating→ready）→ content_posts（drafted→reviewing→approved→ready→scheduled→published）。

3 个人审 gate：Topic + Script + Post 必审；Storyboard / Asset 不审——既不打断创作节奏，又锁住质量。

Workflow 仓（/Users/gloom/Workflow）= 通用媒体生成引擎（n8n + RunPod GPU：FLUX/SDXL 文生图、Wan 图生视频），webhook softie-n8n.fly.dev；Akke 持有业务编排（多租户选题/脚本/审稿/状态机/拼接），不跑 GPU 模型。两者 HTTP 解耦，worker/services/video_gen.py 适配器是接 Workflow webhook 的接缝。
