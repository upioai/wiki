01 / 05 执行方法论 · Speed & Certainty

六个月解决，不要等十年

蒂尔说，能用六个月解决的问题，不要留给十年。西蒙斯说，价格这种事，一定有办法能被建模。两句话指向同一件事：把模糊的问题，变成可以拆解、可以验收、可以交付的东西。

下面三条方法，是把「六个月做完」落到日常协作里的具体做法——不是口号，是流程。

「6 个月能解决的，不要等 10 年。」 —— Peter Thiel
「价格这种东西，一定有办法能建模出来。」 —— Jim Simons
02 / 05 方法一 · Spec Before Code

需求写清楚，验收说明白

Spec 不需要写得复杂，但必须清晰到没有第二种理解方式。

🌫️含糊的需求

反面

「做一个更好的 XX」——好到什么程度、谁说了算，没人说得清。

验收标准留到交付那天才第一次被定义，那时返工代价最高。

🎯清晰的 Spec + 验收

正面

一段话、几行 bullet 都够——但必须回答两件事：做完是什么样、怎么算通过。

验收描述写在动手之前，而不是交付之后才对齐。

常见陷阱：需求写得越长，往往越说明还没想清楚「怎么算通过」——页数不是清晰度的替代品。
03 / 05 方法二 · Repeat The Outcome

不停强调结果，而不是过程设计

过程可以自由发挥，但「要什么结果」必须被反复讲，讲到没人会记错。

🧩过度的过程设计

反面

提前把每一步怎么做都写死，本质是在为不确定的现实预先「锁死」一个方案。

现实一变，整份设计就要重写；没人再回头看「到底要什么结果」。

🔁反复强调结果

正面

把「验收时长什么样」讲一遍、两遍、十遍，讲到执行的人（不管是人还是 agent）想都不用想。

路径留给执行者自己找——过程越自由，越可能找到设计者没想到的更好做法。

纠结过程细节，往往是「怕执行者做错」的心理补偿；重复结果，才是把控制权真正交回给目标本身。

04 / 05 方法三 · Design → Execute → Audit

设计、执行、验收，交给不同 session 接力

1
设计把问题拆成可执行的 Spec 和验收描述——对应方法一。
📐
2
执行按 Spec 动手，过程自由，结果优先——对应方法二。
⚙️
3
审计与验收换一双独立的眼睛复核，不由设计者、执行者自己给自己打分。
🔍

三个阶段可以分给不同 session（甚至不同人）并行或接力完成——设计者不必是执行者，执行者不必是验收者。互相独立，才不会自己骗自己。

这份页面本身 就是一次示范：内容先整理成三条方法（设计）→ 写成页面并发布到 upio.ai/learn（执行）→ 你现在看到的，就是过一遍验收之后的产物。
05 / 05 总结 · 三句话带走

速度，不是抢时间

速度，是把模糊变清晰的次数够多、够快。三条方法各管一段，缺一段都会拖回「十年」的节奏。

①需求 → 验收Spec 不用复杂，但要清晰到没有第二种理解。
②过程 → 结果少纠结怎么做，多重复要什么。
③设计 → 执行 → 验收换一双眼睛，别自己验收自己。
「6 个月能解决的，不要等 10 年；价格这种东西，一定有办法能建模出来。」 —— Peter Thiel / Jim Simons
