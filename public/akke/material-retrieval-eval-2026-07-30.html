素材调用能力评估

R2 里的 58.55 GiB 家底，怎样被企业微信和视频产线更高效、更精准地调用

2026-07-30 实测 + 代码盘点 结论：不需要训练模型
✅
一句话结论

调用能力已经建好约 70%，卡在最后一公里——不需要训练任何模型，也不需要上多模态向量库。最高性价比的动作是一个环境变量：把已经建完、验完、但生产从未启用的 pgvector 检索打开。

0四个发现

Finding 01
台账漂移 4.8 倍

文档记 13130 个文件 / 22.21 G，今日实测 63429 个对象 / 58.55 GiB。没有单一事实源，「我们有什么素材」这个最基本的问题现在答不准。

Finding 02
检索建完了没开

pgvector 检索在真实客户消息上命中率 35%、硬命中 0.60–0.72，但 Vercel 上没设开关，线上一次都没用过。

Finding 03
图片检索别靠向量

效果图 + 知识图集是纯图，无文本可抽。已实测：视觉模型判风格会全塌成「现代简约」。图片必须走结构化元数据过滤。

Finding 04
效果图＝视频产线缺的真图

可灵效果差被归因为「喂的是 AI 假图」。R2 里 11265 张真实效果图，正是那个待跑实验缺的输入。零新增成本。

1家底：实测数字与台账不符

今天用 Cloudflare API 直接查了 akke-kb 桶的用量，和项目文档里记的家底对不上：

维度文档记载（07-18 / 07-26 快照）今日实测（07-30）差异
对象数13,13063,4294.8×
体积22.21 G58.55 GiB2.6×

桶在两周内长了近 5 万个对象。文档里那份「素材家底与调用口径」是 07-26 更新的，四天就失真了——不是谁没维护，而是人工维护的清单必然追不上一个天天在写入的对象存储。

🔴
这不只是数字不准，它有三个真实后果

① 运营答不准客户「你们有什么资料」；② AI 回复可能承诺一份实际不存在的素材（编造的一种）；③ 「R2 里的视频」这件事，用现有台账无法确认——文档明确写着 13130 个文件里只有 1 个 mp4、「不构成视频库」，但那是 07-26 的快照，而桶此后又长了 4.8 倍。视频可能就在新增的那批里。

⚠️
本次未能独立核实的一项

要按类型分解那 63429 个对象需要 R2 的 S3 密钥（R2_ACCESS_KEY_ID / R2_SECRET_ACCESS_KEY），本机 .env.local 里没有，Cloudflare API token 只能拿总量、列不了对象，wrangler 也没有 r2 object list 子命令。所以「视频有多少、在哪个前缀下」这条本报告不下结论。补齐凭据后一条命令即可核实：

aws s3api list-objects-v2 --bucket akke-kb \
  --endpoint-url https://<account-id>.r2.cloudflarestorage.com \
  --query 'Contents[].Key' --output text | tr '\t' '\n' \
  | awk -F. '{print tolower($NF)}' | sort | uniq -c | sort -rn

已知的素材构成（文档 07-26 口径，作为量级参考而非现状）：第三方资料 314 份、效果图 11265 张、知识图集 726 张、原创图文 48 篇、官方海报 11 张。

发现 ②：那套检索不是效果不好，是根本没开

2026-07-20 有人做过一次很扎实的验证，结论值得重复一遍，因为它意味着一笔已经付过的投入正躺着不产出：

  • 拿 20 条真实客户消息本地跑检索 → 命中 7/20 = 35%，且都是硬命中（0.60–0.72）
  • 命中的全是真问题：「我预算就 3 万，110 平全屋柜子能做下来吗」0.666、「两万九只是基础价吧」0.719、「你们是什么牌子的板子」0.602
  • 寒暄类（谢谢 / Hello / 我这边在山东）全部正确未命中——闸门是准的
  • 但 Langfuse 近 24h 的 97 次对话生成里，含知识注入块的是 0 次
🔍
「0 命中」本身不是证据，这个排除做得很对

开着但没命中同样是 0。按 35% 的命中率，97 次里本应约 34 次带注入，实际 0 次 ⇒ 不是没命中，是没开。缺的就是 Vercel 上一个 KB_RETRIEVAL 环境变量。

开之前要知道的两件事：一是知识块会稀释人设语气、输出客服腔（当年就是为此把注入从 3000 字砍到 1500），建议开完当天翻几条真实回复看语气；二是相似度闸 0.6 比 0.5 更稳，会滤掉 0.602 / 0.622 那两条边缘命中。回滚就是删这个 env。

另一个一行代码级的阻塞

🔴
buildKbSection 把 KbHit.file_url 丢掉了

即使检索命中，模型也看不见文件链接，所以它发不出资料。这意味着「问 X 发 X」这个需求在当前代码下不可能实现，跟检索质量无关。修法是仿企微 matchPosters 的套路加一个确定性投递分支——注意 src/lib/llm.ts 属高危路径，必须走 PR。

3图片检索：结构化元数据，不是向量

效果图 11265 张、知识图集 726 张，都是纯图片，没有可切块的文本。这里有一条已经用钱和时间买到的教训，不要重犯：

维度视觉模型打标是否可用实测结果该怎么做
空间
客厅/卧室/厨房…		 可用 qwen2.5-vl 给 7679 张补标成功，成本约 $1。分布：客厅 3522 / 卧室 1290 / 餐厅 798 / 厨房 509 / 卫生间 434 已完成，图集站已按此筛选
风格
现代简约/新中式…		 不可用 判风格全塌成「现代简约」；7 张工业风只对 1 张。缩略图和全分辨率都塌 用源目录标签，别视觉打标
面积 / 户型 未做 — 核心缺口，见下

为什么这条重要：真实的调用场景锚点是「客户报 113 平 → 调 ±15 平的方案图」。这是一个 SQL 范围查询，语义向量帮不上任何忙。同理「只要现代简约的卫生间」是两个标签的交集，不是相似度排序。

💡
所以图片这条路的正确形态

把「风格（源目录）× 空间（已补标）× 面积/户型（待补）」做成结构化列 + 索引，检索是 WHERE 过滤而非向量召回。多模态 embedding 当前不值得上——它解决的是「找一张海边日落空镜」这种开放语义检索，而这里的查询都是可枚举的维度。

⚠️
当时的链路是「AI 生图 → 图生视频」，喂进去的是假图

所以不能就此给引擎定罪。为此立了 M1 图源对照实验（真图 vs AI 图盲评），脚本 ad-studio/tryout/arm_i2v.py 已就绪但一直没跑——因为 jobs.json 里还是占位 URL，缺真实图源。

✅
而 R2 里躺着 11265 张真实效果图

那正是占位 URL 缺的东西。用 xiaoguotu/v2/… 的真图填进 jobs.json，M1 立刻能跑——图已有、脚本已有、零新增采购，就能回答「假图是不是根因」这个决定视频产线走向的问题。考虑到已决定不再为可灵新增花费，先花近乎零的成本把归因搞清楚，明显优于换引擎重试。

换个角度说：效果图不只是「发给客户的素材」，它同时是视频产线的原料。现在这两个系统各自把 R2 当仓库用，但没有共享的素材索引，所以一边缺图、一边有图，互相不知道。

5企微链路的两个硬阻塞

阻塞性质说明能否绕过

顺序建议：备案是行政前置、周期不可控，不要让它挡住其他事。先把不依赖备案的部分（检索开关、file_url、台账、M1 实验）全部推进，备案通了再接回调。

6建议的三层结构（不新增任何供应商）

台账层 · 素材的单一事实源

L1 · 缺失

R2 里每个对象一行：key、类型、尺寸、所属集合、结构化标签（风格 / 空间 / 面积 / 主题）、水印状态、授权状态、对外可用与否。由定时任务对账 R2，而不是人工维护 JSON。这是 Finding 01 那个 4.8 倍漂移的唯一解，也是让两个系统能互相看见素材的前提。

Postgres 表定时对账 R2不存二进制

检索层 · 文本走向量，图片走过滤

L2 · 已建未启用

文本（314 文档 + 图文 + 话术）走已建好的 pgvector；图片走台账层的结构化列做 WHERE 过滤。两条路径并存，不要试图用一种覆盖另一种。

pgvector · bge-small-zh-v1.5结构化过滤MIN_SIM 0.6

投递层 · 确定性优先

L3 · 部分就绪

matchPosters 那套「命中词 → 取 URL → 发图」的确定性套路是对的，扩展它而不是重写。抖音侧只发纯文字（风控红线：私信不发外链、不发我方微信号），文件链接只在企微侧发。

matchPosters 模式deliverMaterial() 待建投递状态机防重发

⚠️
#6 的三个已知坑（别踩第二遍）

① xlrd 未装，而 67 份 xls 恰恰是清单类内容最密集的，不能跳；② 11 份 pdf 是扫描件（pdftotext 无效），且恰是最像干货书的几本，要么 OCR 要么明确挂账，别静默跳过；③ bge-small-zh-v1.5 上限 512 token，单块正文必须卡在 450 字符内，超了静默截断；④ 灌完全文必须重新标定 MIN_SIM——0.5 / 0.6 是拿摘要块标的，全文块相似度分布不同。

8明确不建议做的事

  • ✗
    微调 / 训练任何模型。这里没有一个需求是训练能解决的。资料改一次就要重训，事实准确率还不如直接检索。
  • ✗
    为图片检索上多模态 embedding。查询维度是可枚举的（风格 / 空间 / 面积），结构化过滤更准更便宜。而且风格维度的视觉打标已实测不可用。
  • ✗
    新增向量库供应商。pgvector 在这个量级（482 → 预计 4000–6000 chunk）远未到瓶颈，多一个供应商多一份会静默烧钱的账单。
  • ✗
    为可灵新增花费来「再试试」。先用 R2 真图把归因做掉（动作 #3），再决定要不要花钱。
  • ✗
    在抖音私信发外链或我方微信号。风控红线，现有代码已经守住了，新增投递逻辑不要破坏它。
  • ✗
    把「有什么素材」写死在文档里。这次的 4.8 倍漂移已经证明人工快照必然失真，要么查台账要么别答。

数据来源与核验方式。桶用量（63429 对象 / 58.55 GiB）为 2026-07-30 经 Cloudflare API /r2/buckets/akke-kb/usage 实测；桶清单同日实测。素材构成（314 / 11265 / 726 / 48 / 11）、检索命中率 35%、视觉打标实测结论、产线选型与 M1 实验状态均引自项目 memory 与 docs/specs/，为 07-13 至 07-26 期间的记录。企微 ICP 校验结论为 07-07 实测。
