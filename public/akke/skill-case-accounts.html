案例账号拆解 Skill

给一个抖音、小红书或订阅号的链接，它把这个号的全部作品扫一遍，挑出其中真正的「案例内容」，产出一页可对外的分析，并归入对应行业的样板库。

这一篇讲方法论——规则是怎么被一轮轮人工标注纠正出来的、踩过哪些坑。
只想知道怎么装、怎么用，看 上手指南。

这是什么

给一个抖音、小红书或订阅号的链接，它把这个号的全部作品扫一遍，挑出其中真正的「案例内容」，产出一页可对外的分析，并归入对应行业的样板库。

我们给客户讲「案例内容怎么做获客」时，最有说服力的从来不是我们说，而是同行已经在怎么做。过去要回答这个问题，得人工翻账号、一条条看、凭印象总结，翻一个号要半天，结论还不可复查。

这个 skill 把它变成可复跑、可校准的流程：抓取是自动的，判定靠明文规则，规则由人工标注校准，每条判定都标着得分和理由，可以逐条核对。换个行业、换个账号，重跑一遍就行。

它能做什么

输入可以是账号链接、账号名，甚至只是一张主页截图。抖音、小红书、订阅号文章三个平台都认，作品链接、主页链接、分享短链都行。它会依次做完这些：

  1. 定位账号 —— 从名字或截图找到唯一标识，同名号很多时用抖音号和粉丝数核对
  2. 抓全量作品 —— 滞速滚动加载，实测单个号最多抓过 2819 条
  3. 判定哪些是案例 —— 按全局 + 分行业规则打分，每条给出得分与理由
  4. 下载平台原始封面 —— 不是截图裁切，是平台原图，无 UI 附加物
  5. 入库 —— 你提交的链接直接入库上线，在页面上复核；品类调研捞来的号要先抽 3 条人工标一遍（见下）
  6. 拆前 3 条案例 —— 抖音视频、小红书视频和图文、订阅号文章都能拆；每条一份单条拆解，再出一份综合报告：三条有没有共通之处、能不能用同一个工作流批量做、照着做每集花多少（见下）
  7. 生成分析页 —— 含 4×4 封面海报、案例卡片、判定规则表，每张卡片直链原视频
  8. 归入行业样板库 —— 按品类归档，列表页自动更新并排序

第 5 步为什么不能跳

整夜流水线曾经自动入库过一批号，事后用校准过的规则重算才发现其中好几个根本不该收——用户本人的账号、讲给同行的培训课号、店面摆拍号。那时页面已经对外挂了一段时间。

抽 3 条当场就能拦住它们：这几个号抽到的 3 条全是「不是案例」。我们拿其中一个号的真实标注回放过这道闸，它确实被当场拦下。新采集的号现在一律先进候选池，标完确认才进库：

结论什么时候出现
❌ 不收录抽 3 条全判否——实测最强的否定信号，上一轮有 7 个号如此，重算后命中率全部落在 0–14%；或案例不足 8 条
⏸ 还不能定规则与人工对不上 ≥2 条，说明规则在这一行还没校准，先补规则再回来
✅ 可入库以上都没踩，但还要人过一遍账号级准入那三关

机械判据救不了账号级准入：十弎和杰少都是规则判出了几十条案例、机械判据也会放行的号，拦住它们的只有人看的那一眼。所以工具每次都会把那三关的清单打出来提醒。

顺带一个好处：这一步标出来的结果会落进标注集，入库的同时也在扩充规则的校准数据。无人值守的整夜流水线现在跑到第 4 步为止，候选堆着等人回来标，不再自动入库。

还能成批做：给一个品类（比如「我们在谈一个做茶叶的客户」），它会先检索视频、从内容倒推账号、筛掉不对的账号类型，再逐个跑完上面这些步骤。

检索视频时会跳过数据不好的

目标是「选出真实案例里数据表现好的来分析」，所以检索阶段会按点赞给视频设一道门槛。两个设计细节值得说清楚，都是拿真实数据验出来的：

门槛是相对的，不是绝对的。 各品类的点赞中位数差 4 倍（实测：植发 80、大黄鱼 167、数字游民 217、考公考研 321）。绝对阈值会把低调的品类整片误杀，所以用本品类本轮的中位数，再夹在 50（任何品类低于这个都算没数据）到 1000（避免品类整体很火时挡掉好内容）之间。解析不出点赞的约 15% 按通过处理——不因为解析失败丢内容。

门槛只管「这条视频能不能当样本」，不管「要不要顺着它找这个账号」，也不参与账号排序。 这条验过两次：

验证结果
拿门槛卡账号发现会误杀最好的号——库里命中率最高的之一常州 LX（93%）是被一条 55 赞的视频带出来的，韩朝飞是 20 赞；反过来，数据最好的两条提名视频（23,000 赞和 8,837 赞）带来的账号都落选了
按「数据够的案例数」给账号排序更差——植发品类前五一个库里的号都没挑到，反而挑出「植发失败维权中」这种维权号；大黄鱼把一个已入库的号挤出了前五。改回按案例数排序后好号全回来了

结论很直接：视频点赞预测不了账号质量。 它用来挑样本，不用来挑账号。只靠弱数据视频被发现的号会在报告里标 ⚠，线索保留，抓完再由人判断。

所有对抖音的请求都按慢速节奏走（搜索间隔 25–45 秒、账号间隔 60–180 秒、每几步强制长休息），并全程 checkpoint 落盘，中断可续跑。实测连续跑了一整夜，没有触发风控。

第 5 步：两个入口，入库口径不同

入口要不要先标注上线后
提交一条链接（三个平台都行）不用，直接入库上线列表页卡片标「待复核」，账号页顶部点「通过」或「不收录 + 理由」
品类调研（只在抖音、小红书）必须先抽 3 条人工标，通过才入库正常展示

为什么分开：调研是机器从搜索结果里捞号，混着包装厂、代购、培训课号——第一次整夜自动入库就把用户本人的号和培训课号挂上了线。链接是你看过才提交的，第一道筛选你已经做了，所以复核放到上线之后、在页面上点。

行业不用告诉它：先看账号名（「HJ Decor窗帘软装」就是窗帘），名字看不出再按内容里的行业词数票；拿不准就停下来问你，不会硬猜。抓不全（不足账号声明数的 90%）或案例不足 3 条，链接提交也会被拒——那拦的是数据不全，不是判断问题。

第 6 步：拆前 3 条案例

三个平台都能拆。抖音、小红书按点赞取前 3；订阅号按判定得分取——订阅号单篇阅读数在公开网页上拿不到（只有微信里打开才显示），报告里阅读和评论会如实写「公开页面取不到」。视频和图文是两套报告：图文不拆镜头，拆的是首图、图序、正文节奏和图文怎么穿插；AI 制作流水线也是两张表（视频是剪辑，图文是选图、排版、写稿），成本结构完全不同。

分析页回答「这个号拍了哪些案例」，但商家真正想问的是：最好的那几条为什么好？我能不能照着做？要花多少？所以入库后，按点赞取前 3 条案例，每条拆一遍，再把三条放在一起比。

单条拆解回答一条视频为什么好。每份报告结构固定：基本数据（赞评藏转、互动比、时长、镜头数）、8 个关键帧、逐段时间线（每段标出它在叙事里的作用，比如冷开场、信任、反转、情绪峰值）、爆点归因、热评、商业环节、制作手法，最后是 AI 制作流水线。

爆点归因必须分两栏写：可复制的结构 / 不可复制的运气。混在一起，商家会按爆款的点赞去定预期。比如青森洋子第一条 116.9 万赞，可复制的是第一视角连载、真实服务全流程、顾客换 3D 卡通脸；靠运气的是顾客当场送 LV、顾客本身自带话题。预期要按同账号点赞前 48 条的中位数定（9.2 万），不按 116 万定。

综合报告回答三条能不能用同一个工作流做。方法是把三条的差异逐项列出来，看每一项能不能写成流水线里某一步的参数或开关。青森洋子三条的结论：

问题结论
有没有共通之处有。拍法、从进门到离店的结构、结账话术「价格清不清晰，款式满不满意」三条几乎一字不差；爆点都落在顾客这个人身上，热评和「大家都在搜」几乎不聊美甲本身
差异在哪冷开场（把高潮台词提到第 0 秒）、金句大字幕、主理人出镜片头、剪辑节奏（2 秒到 4.2 秒一个镜头）——全都能写成参数
能不能同一工作流能。写不成参数的只有「遇到好故事」，所以流水线加一步：每位顾客都拍、都转写，由模型打分挑当天最值得剪的一位

AI 制作流水线把商家做一集的过程拆成 14 个环节，每个环节写清楚：候选工具、选了哪个和为什么、怎么调用、机器耗时和人工耗时分开写、单集成本。选工具的原则是能被脚本调用的优先，人只在选题、审故事线、审片、发布四个检查点介入。成本直接写在每一行里，不另算一张账：

做一集（2.5 小时素材，成片约 9 分钟）纯人工剪辑按流水线
人工约 12.5 小时约 1.6 小时
机器（不用人盯）—约 40–50 分钟
算力费（转写、模型调用）—十来块
单集合计（含设备摊销、人工折算）约 650–950 元约 135 元

拆一个账号的开销实测：机器约 50 分钟，人工约 40 分钟（主要是审报告），算力费约 10 元。成本表里的设备价、剪辑外包价、GPU 租价是按行情估的，页面上标了「估」，还没拿到实际报价。

怎么装

两条命令，Claude Code 和 Codex 都生效：

git clone https://github.com/Akke-AI/akke-skills.git
cd akke-skills && ./install.sh

装完重启你的工具。更新就 git pull && ./install.sh。

脚本把真实文件放在跨运行时目录，再从各家自己的目录建符号链接指过去：

~/.agents/skills/analyzing-case-accounts/   真实文件
~/.claude/skills/analyzing-case-accounts    → 链接（Claude Code 读这里）
~/.codex/skills/analyzing-case-accounts     → 链接（装了 Codex 才建）

这样只有一份文件，一次 git pull 所有工具同步生效，不会出现某个工具里的版本落后。没装 Codex 的同事不受影响，脚本会自动跳过。

还需要克隆代码仓库（skill 里的脚本和规则在那边，不重复一份是为了避免两边漂移）：

git clone https://github.com/Akke-AI/akke-official-site.git

本机还需要：Node（npm i playwright-core）、Python 3、ffmpeg、gh CLI。要抓小红书，还得在专用的 Chrome 里扫码登录一次（命令见 scrape/README.md）——不登录只能拿到前 12 条、而且没有笔记 id，脚本会直接报错退出。

怎么用

不用记命令，直接说需求就行。 工具会自己识别并调用，或者你显式写 /analyzing-case-accounts。

三个典型场景，照这么说就行：

场景原话示例
看一个具体账号帮我看看这个号 douyin.com/user/MS4wLj... 的案例内容怎么做的
提交一条链接入库把这条收进参考案例集 xiaohongshu.com/explore/...（抖音、订阅号链接同理）
把账号加进样板库把这个茶叶号加进参考案例集
调研一个新品类我们在谈一个做植发的客户，调研一下这个品类

只有一张主页截图也能开始 —— 把图发给它，它会从截图读出账号名和抖音号，再去定位。

调研新品类时有一件事值得你插手：关键词怎么选。实测茶叶那轮，搜「茶叶 案例」出来的全是讲运营起号的服务商，而搜「茶叶 回头客」「茶叶打包发货」这类交易动作才找到真正的商户。你比它更懂这个行业客户怎么说话，直接把词告诉它。

它怎么判断什么算案例

定义一句话：画面是不是自家做出来的活，而且指向一次真实的交易或交付。不要求点名客户，也不要求写地址。

这句话是被两轮人工标注分别从两个方向纠正出来的，两次都纠正得很彻底：

轮次一跑标注发现问题修法
第一轮 80 条准确率 49%，漏判 39 / 误判 1收得太紧放宽成「自家做出来的活」
第二轮 67 条准确率 58%，误判 28 / 漏判 0放得太松主营内容只当前提，另需案例依据

第二轮那 28 条误判每一条都是同一个原因：「命中本行业主营内容」给的分正好等于收录门槛，于是「提到这一行」自己就算案例——产品介绍、行业知识、促销、进货、店面摆拍全都进来了。

最重要的一条：同一条规则对不同行业是反的

第二轮最有价值的发现不是某个词该不该加，而是「要不要案例依据」取决于这一行的交付物长什么样：

形态行业为什么要额外证据吗
作品展示型门窗 / 窗帘 / 保洁 / 宠物美容 / 美甲 / 婚纱画面里那扇窗、那只狗、那套甲本身就是交付物不要，拍出来即是案例
商品交易型茶叶 / 大黄鱼画面里是商品不是交付物——一罐茶、一条鱼谁都能拍要：发货 / 复购 / 评价 / 订制
服务结果型植发 / 主播招募 / 考公考研不然就是行业知识讲解或培训课程要：具体的人 + 结果

证据是对称的，这才让人放心：对作品展示型也强制要求证据，第一轮准确率从 100% 掉到 39%；不对商品型和服务型要求证据，第二轮 66 条里误判 28 条。两条规则都对，只是各管一类行业。

所以新增一个行业时，先问一句：这一行的画面本身是不是交付物？答案决定它归哪一类。

什么不算案例

精度全靠排除项。前四类是第一轮定下的，后四类是第二轮直接从人工备注里翻译过来的：

不算标注时的原话
转述他人作品「设计师：X」「抄作业」——别人的活不是自家的活
工具产品种草 / 促销卖的不是自家做的活
无关生活 / 情绪 / 解压画面与业务无关
同行向 / 行业吐槽讲给同行听的
行业知识讲解 / 教程「讲知识结构的 只是拿一个患者作为例子」
卖货文案（规格 / 包邮 / 下单）「销售活动」「打折政策」「产品介绍对比评测」
上游进货 / 备货「只是进货的一些场景」——进货是向上游买，不是自家做出来的活
商家自我介绍 / 工厂宣传「典型的产品服务介绍 里面没有提及任何用户属性的地方」

还有一条值得记住的教训：原先的「收录信号」也可能是错的。 大黄鱼的「食用场景 / 做法」本来是加分项，第二轮标注把它判反了（「商家介绍黄鱼的做法技巧」＝不是案例），现在它变成了排除项。改规则时要同时怀疑加分项，不要只往排除项里加东西。

它还会判案例属于哪一类

第二轮新增的维度。四类，其中一类是在标注过程中由业务方现场命名的：

类型判什么第二轮 46 条里
产品服务客户过程案例有客户，且服务动作正在发生22
交付结果案例做完的成品，没有服务动作也没有客户在场10
商家经营日志案例自家在干活，但不指向某一个客户（出海、造船、日复一日配货）6
用户使用案例用户视角的使用与反馈0

「用户使用案例」一条都没有，这本身就是个结论。 全库重算后 990 条案例里只有 1 条属于这一类——21 个样板号里几乎没人在拍用户自己的反馈。要么是做不到，要么是没想到，这正好是可以跟客户聊的切口。

类型倾向也是分行业的：门窗 / 宠物 / 婚纱标出来的 9 条全是「交付结果」（拍成品），美甲 / 保洁的 9 条全是「服务过程」（第一视角拍干活，文案直接写「耗时6小时为一位顾客服务」）。这是内容形态的差别，不是业务的差别，所以每个行业有一个默认类型。

默认类型在页面上会标出来，别当成结论。 全库实测只有 46% 的类型是靠信号判出来的，另外 53% 是落到行业默认值——那是假设。页面上推定的类型用虚线框加「?」区分。下一轮标注该优先抽默认值占比高的号：考公考研两个号的 31 条类型里 0 条来自信号，那一行的分类规则等于还没写。

这一轮重算带来的变化

规则一改，全库必须重算——否则页面上的案例清单和命中率还是旧规则的结果。这次 24 个号里 22 个的命中率变了：

方向账号
几乎没变（作品展示型）婚纱 100%、宠物美容 98%、门窗 89%→89%、美甲 95%→93%
明显下调（商品型 / 服务型）南岐海鲜 99%→6%、日照绿茶 98%→13%、赶海父子 94%→22%、植发三个号 81%/60%/57%→23%/11%/10%
已摘出样板库十弎、左左讲招募、小志考研、阿伟茶业——案例数不足，记录在 data/rejected.json

这个修正和人工标注严丝合缝：第二轮抽到 3 条全判否的 7 个号，重算后命中率全部落在 0–14%。

其中两个号值得单说，它们是同一类问题撞了两次：十弎（植发，378 条作品）和杰少（考研，111 条作品、8 万粉、351 万赞）。两个都是用户/受益人本人第一人称讲自己的经历——十弎在记录自己的植发恢复，杰少在讲自己中专考研上岸。内容真实、数据还很好，判定规则也判它们「是案例」，因为画面确实是真实发生的事。

但它们都缺商业环节：十弎明说「不为任何机构做广告 只说自己植发过程跟感受」，杰少从未提到参加过什么培训班或机构。没有商业方，这就只是一份个人记录，不能作为「商户如何用案例内容获客」的样板。这条已经固化成账号级准入规则：

关检查什么踩过的实例
用户本人的故事，必须有商业环节主角是用户本人时，内容里要能看到商业方——机构、课程、品牌、商家或所购买的服务十弎、杰少
必须是目标商家类型本身是这个品类的商家，不是上下游或旁观者茶叶那轮混进来的包装厂、代购、测评号
内容是自家交付，不是转述他人主体内容是不是在展示自己做的活「这个设计有点贵」

这三条内容规则一条都抓不到——规则判的是「这是不是自家做出来的活」，判不了「这个号是不是我们要的那类商家」。所以它们不是正则，是收号时必须人工过一遍的清单。

顺带解释了为什么全库「用户使用案例」几乎为零：真有这类内容的账号，往往正好卡在「没提商业方」这一条上。

页面上能直接做的事

每张卡片标了案例类型，可以当场重标注

账号页的每条案例都带一个类型标签（推定出来的会标「推定」），右下角有「重标注」。点开是两层选择——先判是不是案例，再选类型，还能写备注。点完直接存到线上，谁都能看到；同一条再标一次以最后一次为准。

重标注不会自动改规则，它改的是检验规则的「考题」。 维护的人用 relabel.py --pull 拉回来并进标注集，成为回归测试集的一部分；规则怎么改，看回归报告里新暴露的漏判与误判。让单条意见直接改规则等于绕过回归，那是把校准机制拆了。

展示只列 ≥50 赞的案例

样板库要给的是「真实案例里数据表现好的」，不是全部案例。加门槛前全库 959 条展示案例里 34% 不到 100 赞、100 条不到 10 赞——页面说它们是值得参考的样板，但这些内容其实没人看。现在展示 959 → 717 条。

够门槛不足 8 条的号，退回展示它最好的 8 条，并在页面上明说「这个号的案例数据普遍偏低」。 保底是必须的：按 50 赞硬卡，有 4 个号会空掉或只剩 1–3 条，其中还包括一个命中率 100% 的号。整号数据都低不等于没有参考价值，但要标出来，不能让弱内容冒充样板。

账号页上能直接看视频拆解

拆过的账号，页面上多两样东西：账号介绍下面是综合报告（默认折叠，点开是三条对照表、共通与不同、能否同一工作流、AI 制作流水线）；前三张案例卡片上多一行「查看拆解报告」，点进去是那一条的完整单条拆解。样板：AOMORI 青森洋子。

维护纪律

规则是数据，不是代码。 全在 case-refs/rules/ 的 JSON 里，改规则不用动 Python。每条规则带 note 说明它为什么存在，接手的人能看懂依据。

改完规则有两件事必做，第二件最容易漏：

cd akke-official-site/case-refs
python3 scrape/regress.py          # 1. 回归：准确率掉了就是改坏了
python3 scrape/recompute.py --dry  # 2. 试算：看全库命中率会怎么变
python3 scrape/recompute.py        #    真算 + 补封面 + 同步文案
python3 scrape/posters.py && python3 scrape/export.py --check   # 整理线上数据 db/ 并校验
git add data rules posters raw db && git commit && git push && python3 scrape/publish.py

第二步不能省。 这一轮改完规则，24 个号里 22 个的命中率变了，最多的从 99% 掉到 0%。只改规则不重算，线上页面展示的还是旧案例清单和旧命中率——页面在撒谎。

重算要同步三处真相：数据文件里的 hit_rate、登记表（data/accounts/<slug>.json）的 note 文案、insights.json 的开头。这次第一遍就栽在这里：数据写成 22%，页面照旧显示 85%，因为页面读的是另一个字段名。

别把准确率当成规则已经可靠。 第一轮改完是 100%，第二轮新标注一来就掉到 58%。当前 128 条：是否判定 98%。真正的检验永远是下一轮新标注。

顺带一个提醒：回归脚本自己也要能跑。 它一度缺了命令行入口，行业映射还硬编码着最早的 8 个号——「改完必跑回归」这条纪律因此有一段时间其实是空的。

规则靠标注校准，不靠拍脑袋。 两种取样模式解决不同问题：

python3 scrape/make-labels.py ambiguous 10   # 新增行业 / 改完规则：查规则对不对
python3 scrape/make-labels.py spread 3       # 入库一批后：查分类维度够不够

生成的是本地 HTML，打开就标，localStorage 自动存，可随时关掉续标，标完导出 JSON。标完存进 labels/，它就成为回归测试集的一部分。

取样时别漏掉 0 分那一档。它不是「确定不是案例」，是「规则什么都没看出来」。第一轮正是靠它发现婚纱摄影 434 条全卡在 0 分，说明是召回有问题而不是阈值有问题 —— 这两种病修法完全不同。

取样先取「赞多的、且模棱两可的」。 优先级 ＝ 模棱两可程度 × log(点赞)。标注成本在人，要把人花在「既拿不准、又真的有人看」的内容上——规则在一条 5 赞的视频上判错影响不了任何人；在一条 10 万赞的视频上判错，整个样板库的口径就歪了。点赞取对数而不是线性，让量级起作用而不是绝对值。

有一个例外必须留着：0 分那一档单独留配额，不能让高赞的「刚够线」挤光。顺带说一个一度没人发现的问题——这个取样模式要找的就是 0–2 分那两档，但它一直从「已判为案例」的数据里取样，而那里面只有 ≥3 分的，≤0 分的实测有 0 条。也就是说这条纪律一度根本执行不了。改从原始全量作品取样后，抽样里 ≤0 分占到 33%。

标注页上的备注框是这套流程里信息密度最高的东西。 第二轮新增的四条排除项全是把备注里的否定理由直接翻译过来的；「其他」里填的名字还可能是一个全新的类型——「商家经营日志案例」就是这么来的。所以宁可少抽几条，也要保证每条都能让人写得下备注。

一个号抽的 3 条全判否，是强信号，别拿「样本太小」放过它。 第二轮有 7 个号出现这种情况，重算后它们的命中率全部落到 0–14%。

两轮标注对同一条视频给出相反结论时，以最新一轮为准——后标的那次见过更多边界情况。回归脚本会把冲突打出来，这次 17 条重叠里冲突 1 条。

为 200–300 个账号做的改造

目标规模是两三百个账号、多人持续增删改。按实测数据推算，有两处会先断，都已经改掉：

原先现在
发布用 GitHub Contents API，一次写一个文件。实测 513 个文件 25 分钟，按 300 个账号推算是 15,600 个文件、13 小时走 git push，往一个稀疏 clone 里写再一次性推。实测 241 个文件 4 秒，快约 170 倍
所有账号挤在一个登记文件里，两个人同时加号就要解冲突一账号一文件，并把手写的（品类、城市、观察文案）和生成的（案例清单）分开放——混在一起每次重算都会把人写的东西卷进 diff

还有两项记在 case-refs/ARCHITECTURE.md 里、约 50 个账号时再做：把图片搬出 git（已定走与站点同源的方案，页面 URL 不变），以及列表页按行业拆页。

skill 本体很短，它不复述代码，只写踩出来的东西 —— 比如抖音抓取的四个坑（普通 HTTP 请求返回全空、Chrome 136+ 禁止对默认 profile 开调试、滚动容器不是 window 导致只能拿到首屏 55 条、话题标签是噪音）。这些不写下来，每个人都要重踩一遍。

有两件事还得人看，别全交给它：

  • 账号类型 —— 规则判内容准，但判不了「这个号是不是我们要的那类商家」。茶叶那轮 286 个候选号里混进了包装厂、代购、测评号，它们发的确实都是「自家做的事」，规则没判错，错在类型。
  • 观察结论 —— 自动入库的页面写的是数据驱动的自动文案，标着「待复核」。像「这个号 16 格封面里大半是同一套模板」这种洞察，目前还得人看出来。
