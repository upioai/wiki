① 第一个产出的案例

云电脑通路的第一条 DM 投递发生在 2026 年 5 月 21 日 14:09，由登录在阿里无影 EDS 云电脑上的抖音 PC 客户端账号「有大有小」发出。接收方是 Akke 同事「夏夏」（抖音号 21878674266），消息内容「测试 - akke poc 5/21」。14 分钟后的 14:13，同一发送账号向另一位同事「饭粒」对应的 Akke messaging account「一筑·全屋定制」（抖音号 54362559027）发出第二条更贴近真实运营的开场白「你好，看到你主页内容很喜欢，请问做装修吗？— akke poc 5/21」。两条均经过接收方手机端 cross-check 确认从主收件箱正常接收，没有被折叠到消息请求。

关键区分　这两条属于 PoC 内部双账号自测——目的是验证「云电脑 + 抖音 PC 客户端 + pywinauto 自动化」这条新通路的基础可行性，而非「对真实潜客发出的第一条生产 DM」。后者要等 Wuying 端的 poller 正式抢到 dispatch_queue 第一条锁之后才算开始。

这次 PoC 通过的意义在于推翻了 5 月 13 日团队基于推断给出的一票否决（推断包括「阿里 IDC IP 登录会触发风控」「Electron 套壳 UIA 拿不到组件」「抖音 PC 没有 DM 功能」等）。实测结果是：新号扫码无验证码、私信按钮可通过 UIA 定位并正常响应点击、DM 功能完整。这次实测唯一确认的死路是 snssdk1128:// deeplink 会被 Windows 弹「打开应用」对话框抢焦点，这决定了后续放弃 deeplink 路径、改走「搜索栏→用户 tab→profile→私信按钮」的导航序列。

核心架构发明：公告板（Rendezvous）模型

云电脑藏在 NAT 和 IP 漂移（每次重启 cloudflared 网址变动）的网络深处，外面找不到。这意味着任何「中央调度器主动连云电脑下发任务」的设计都不可靠。解决方案是把方向反过来——中央放一面公告板（Supabase 的 dispatch_queue 表），云电脑每 60 秒来抢一次锁。外面没有任何节点持有云电脑的直接网络连接。

讲给非技术同事的比喻　把整套系统想成一家「远程代发抖音私信的公司」。公司中央一面墙贴派单，谁先撕谁去做。每间远程办公室里坐着一位小助理（poller）、一双 AI 视力（Vision OCR）、一台开着抖音 PC 的电脑（pywinauto/pyautogui）。整间公司没有任何一根电话线直接打进远程办公室——所有信息都通过墙上的公告板中转。

完整 8 跳链路

① Vercel Cron 闹钟（每 5 分钟响）→ ② /api/cron/cloud-pc-dispatch 派单 API（按 daily_limit + 45-90 min 节奏门挑账号）→ ③ Supabase dispatch_queue 表（公告板，便签贴上去）→ ④ Wuying 端 wuying_poll_agent.py（60 秒 tick，调 claim_dispatch RPC 抢锁）→ ⑤ 本地 cloud_pc_server.py（uvicorn :8765）→ ⑥ 抖音 PC 客户端（pywinauto 找控件 + pyautogui 点击 + pyperclip 中文输入）→ ⑦ 抖音服务器（DM 真投递）→ ⑧ 回写 dispatch_queue.status（sent / failed）。

关键不变量

一台 Wuying = 一个同事 = 一个 messaging account，严格 1:1。AKKE_ACCOUNT_ID 写在 Wuying 本地 .env，bootstrap.bat 自动落盘并在 Windows 启动文件夹建快捷方式，登录 30 秒后自启 agent。同事下班只需 Cmd+Q 关 Mac wuying 客户端，10 分钟后云电脑自动休眠，灵豆停扣。

③ 同样流程批量化运转的问题

「PoC 单台跑通」≠「N 台并发跑稳」。从 1 台 1 人扩展到多台 Wuying × 多同事 × 严格 1:1 绑 messaging account 的过程里，每一层都踩到了真实的摩擦力。下面按问题域分组，每个痛点都附现象 / 根因 / 当前缓解措施——所有条目都基于已发生的实测或 runbook 已覆盖的排错矩阵。

A. 调度公告板侧

死账号锁池
现象　某台 Wuying 被标 channel_pref='cloud_pc' 但实际长期不上线（同事请假忘告知、Wuying 没唤醒），Vercel cron 每 5 分钟仍照常给该账号 claim leads，30 分钟后被 expire-stale-claims 标 expired，下一轮又抢回 active。整池高意向 leads 被这台死账号反复锁住，其他同事的 claim-leads.ts 拿不到。
缓解　请假 ≥ 1 天必须告诉 PM，PM 把 channel_pref 改回 manual，并把现有 active claim 释放（runbook §5 完整 SQL）。
派单重复多发
现象　同一用户的派单可能被 claim_leads_batch 在 4h TTL 过期后重新派单，INSERT dispatch_queue 缺去重守卫。实战案例：「靖哥」comment_id 4a9f7890 在 20 小时内堆积 5 条 pending 行——一旦 poller 启动会向同一个用户连发 5 条 DM，秒触抖音风控。
缓解　INSERT 前加 NOT EXISTS 子句排除已 pending/claimed 的 douyin_user_id；发现堆积立即 UPDATE dispatch_queue SET status='aborted' 留最新一条；强制完成第一次 send 后立即调 mark_lead_contacted 永久去重。

B. Wuying / Windows 操作端

灵豆耗费陷阱
现象　PoC 8 小时实测消耗 95 灵豆 vs 估算 28。根因：wuying Mac 客户端保持运行时云电脑不休眠，按 4 灵豆/小时全速扣。
缓解　下班必须 Cmd+Q 完全关闭 Mac wuying 客户端（不是最小化到 dock），10 分钟后云电脑自动休眠停扣。这是 runbook §2.2 的硬纪律。
Cookie 过期 + 阿里 IDC IP 风控
现象　抖音 Cookie 在云电脑环境下 15-30 天会失效。重新扫码时阿里 IDC IP 出口偶尔触发验证码（概率较低但发生过）。
缓解　定期（每 3 周）在 Wuying 内主动扫码刷新；如遇验证码及时人工处理，不可让登录态失效超 7 天；每台 Wuying 严格 1:1 绑唯一 AKKE_ACCOUNT_ID，PM 一次性下发，agent 不猜默认值。
自启失败 + 双开抢锁竞态
现象　bootstrap.bat 写入 Windows 启动文件夹延迟 30s 自启，偶尔失败 → dispatch_queue 无人消费；如手动跑 agent 同时 cron 也启动了 agent，两个 poller 会抢同一条 dispatch 行出现部分消费。
缓解　唤醒后先确认 agent 是否已起来（看任务管理器有 python.exe、或 dispatch_queue 是否有 claimed_by 非 NULL）；手动启动前先 taskkill /F /IM python.exe 杀残留。
分辨率校准
现象　douyin_dm.py 里 COORDS 字典硬编码了 1456×819 分辨率（Wuying 黄金款经济模式默认值），同事改了 Wuying 显示设置就全失效。
缓解　不要改 Wuying 分辨率；非要改则跑 python calibrate.py 重新采样所有元素坐标，把打印的 COORDS 整段贴回 douyin_dm.py 第 46 行替换。

C. 抖音 PC 操控 + 风控

Electron 多窗口歧义
现象　单进程抖音 PC 派生多个 HWND（主窗口 + widget + renderer），Application.connect(title_re=...) 报 ElementAmbiguousError。
缓解　改用 Desktop.windows(visible_only=True) 遍历，按窗口面积选最大的（= 主窗口）。
点击事件被吞
现象　pywinauto 的 click_input() 在某些 Electron build 下不触发 React onClick，「私信」按钮常被吞。
缓解　取按钮 rect 中心点，改用 pyautogui.doubleClick(x, y)（基于 SendInput 而非合成事件），单击偶尔失效必须双击兜底。
中文输入乱码
现象　pywinauto type_keys() 仅 ASCII，中文输入变 ????。
缓解　所有文本走剪贴板：pyperclip.copy(content) + pyautogui.hotkey('ctrl', 'v')，完美支持中文。
搜索结果精度失控
现象　抖音搜索同名昵称会撞 25+ 个改名号，单因子匹配（仅昵称 or 仅抖音号）容易发错人。
缓解　双因子精度守卫——必须同时匹配抖音号 AND 昵称片段，缺一不放行。
风控验证码突袭
现象　高频或陌生 IP 触发抖音验证码弹窗，焦点被对话框抢走，自动化脚本卡住。
缓解　pyautogui FAILSAFE：检测到验证码 → 鼠标甩到屏幕左上角紧急停 → 任务管理器关 python.exe → 人工处理 → PM 调降 daily_limit；cron 派单间隔 45-90 min jitter 抖散，不轰炸同账号。

D. OCR & 投递验证

主页校验置信度门槛
现象　Haiku Vision OCR 主页校验 conf ≥ 0.95 防止「点错改名同名号」。阈值太严会漏发（false negative），太松会误发（false positive）。
缓解　当前阈值 0.95 是 PoC 实测均衡点；后续需采样 100 条被 Vision 拦掉的截图人工复查比例，再调阈值或 Vision prompt。
DM 真投递验证
现象　HTTP 200 不能作为投递证据（历史上 Web 通道有过 status_code=7911 的 silent drop）。
缓解　云电脑通道的优势在于 UI 自带强 evidence——发送后扫 compose dialog 的 Document text，包含 <content> · 刚刚 文本回显才算成功；这比 HTTP 状态码可靠。

E. 人员与 SOP

多通道并发 race
现象　现有 5 位 ADB+WDA 运营线（饭粒/野荞/夏夏/阳阳/Gus）不切，新增 1-2 位试点云电脑通道。两条链路同时对同一 lead pool 发 claim 时有理论上的争抢风险。
缓解　严格按账号绑定表物理隔离——同一 account 只能绑一条通道；云电脑新账号用独立 account.id，与 ADB pool 完全分开。
掉线监控缺失
现象　Wuying 掉线 / 同事忘开客户端 / 抖音 PC 闪退被登出时，poller 死，但 cron 照常派单 → pending 静坐超 30 分钟无人认领。
缓解　告警阈值：pending ≥ 5 AND oldest claimed_by IS NULL 超 30 分钟 → Lark 推 PM 告警；日常监控实发量 < 10（vs daily_limit=18）→ 查 OCR 失败率 / pool 干涸两个根因。

  • ADB+WDA 既有 5 人线迁云电脑可行性评估　成本（5 台手机 + WDA infra vs 1 台云电脑 + 灵豆）+ 稳定性（uptime vs 掉线率）+ 风控（封号速率）三维对标。

关键决策节点

6/15-6/18 灵豆复盘　例会回顾实际消耗 vs 预期，决定黄金套餐是否维持或升铂金。
P1 完成条件　≥ 1 位新人 onboarding 走通 + dispatch_queue 日均成功率 ≥ 95% + lead 堆积 < 5 条。
「对外真实运营」启动标志　首条来自非 PoC 账号的对外 lead DM 被记录且接收方有回复——这一里程碑达成才算云电脑通道正式上线。
