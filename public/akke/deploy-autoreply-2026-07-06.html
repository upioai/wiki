02自动回复做了什么优化（2 个根因修复，全账号生效）

修复 A · 加微确认被「负面护栏」误挡 PR #773 已合

客户发来微信号、草稿「好的，我们添加您啦，麻烦通过一下~」这类加微确认，被判「负面/投诉」转人工、不自动发——破坏全自动、丢单。

根因：负面护栏词表里有个裸 "烦"，用「包含」匹配，把超高频礼貌词 「麻烦」（麻烦您 / 麻烦通过）全扫成负面。修："烦" → 前缀式负面词 好烦/很烦/太烦/真烦/别烦/厌烦（都不可能是「麻烦X」的子串），从根上消除碰撞；硬负面（投诉/差评/拉黑/别发了…）一个没动。补了回归测试。

修复 B · 多轮对话「无红点漏读」 PR #776 已合

在聊天框已经聊了好几轮，客户接着发消息却没有红点，自动回复漏读不回。

漏读机制（修复前）
自动回一条 → 发送脚本把会话停在打开态
↓
客户在这个「已打开」的 thread 里接着回
↓
抖音判「已读」不标红点 → 只认红点的捕获 漏读
修：发送成功后（气泡已确认发出）自动导航离开会话回抖音首页。客户后续每一条消息都落在「非打开态」会话 → 红点恢复可靠，捕获照抓。不动任何判定逻辑（红点+昵称匹配链完全保留）→ 零「认错人」风险。
生效方式：改的是云电脑脚本 douyin_dm_web_send_dom.py（18327→19310 字节），已同步公共镜像。各机需「更新该脚本 + 重启 agent」才生效（更新命令见 §04）。

03自动回复现在怎么跑（全自动闭环）

不是「读到就无脑回」，是「AI 起草 → 内容闸自动过滤 → 干净的自动发、可能说错的转人工」。这是设计上的安全闸，不是要人逐条点。

客户回复
↓ DOM 捕获（红点，每 15s）
秒级起草：捕获即触发端点生成草稿（~15–40s，原等 5min cron）
↓ 过 autoSend 内容闸
干净 → 自动 approved → agent 立即插队发出 ✅ 全自动
↓
踩雷（谈判 / 报价 / 护栏 / 空或崩 / 疑回声）→ 转人工 needs_human
为什么保留「转人工」这道闸：防 AI 把错价格、进入谈判、说废话直接怼到客户脸上。修复 A 就是把「麻烦」这种本该自动发的误挡拆掉，让全自动更顺，而不是拆掉安全闸本身。

06待优化 · 连发消息「合并成一轮回」

客户常连着发好几条：在吗 → 想问下 → 全屋定制多少钱。希望等他发完、把这几条当一轮回一次，而不是对第一条抢答、或漏掉后面。

现状（已读代码确认）

点现在怎样
会不会回多次不会 ✓ 占位机制（awaiting 的 NOT EXISTS）保证一条会话同时只有一个草稿 → 连发不刷屏
会不会抢答半句会 ✗ 秒级端点「捕获到就起草」，没等静默 → 可能对早的那条（在吗）先起草发出
后面的消息会被忽略 ✗ 第一条起草后会话不再「待回」，第二条（多少钱）不触发重 draft，发出的回复没带上它
同一 15s 窗口内快连发中间几条丢 捕获读的是会话列表预览＝最后一条，窗口内更早的被覆盖、没入库

方案对比

方案做法优劣
A · 定时去抖最后一条客户消息静默 N 秒才起草简单每条回复都晚 N 秒（单条也白等）
B · 新消息作废重 draft
推荐		草稿发出前客户又发新消息 → 作废旧草稿、带上新消息重 draft；发送走自然轮询节奏（本就 ~15s 间隔）+ 短静默确认单条零延迟（照常秒级）；连发自动合并成最新一轮；顺带修好「第二条被忽略」的现有 bug改动稍多（要让新消息能作废未发草稿 + 重开待回）
C · 读 thread 兜底
二期		有活动的会话开一次 thread，读近几条气泡全抓同窗口极快连发也能全抓、最彻底要开会话 + 探气泡方向 DOM，改动最大
推荐 B 为主，C 作二期：B 不牺牲单条速度就把「抢答半句 / 忽略后续」根治，同窗口极快连发（少数）留给 C 兜。静默秒数 / 阈值走 env 可调。
本质权衡：要「合并」就必须「等一下」——分歧只在把等待放哪。A 放在「起草前固定等 N 秒」→ 单条受累；B 放在「发送前的自然轮询间隔 + 新消息作废」→ 单条不受累。所以 B 更优。

方案 B 上线后 · 端到端时效拆解（从客户发完最后一条算起）

步骤花费说明
① 捕获检测（红点，DOM）0–15s（均 ~8s）poll 每 15s 一轮，落在哪一轮看运气
② 写库 record_dm_inbound<1s一次 DB 写
③ [B] 新消息作废 + 静默确认单条 ~0；连发＝等最后一条合并逻辑：起点钉在最后一条，不额外加时间
④ 秒级起草（chatReply LLM）~5–10s捕获即触发端点，不等 5min cron
⑤ autoSend 内容闸<1s确定性判定 → approved
⑥ 发送轮询领取0–15s下一轮 poll 领走 approved 草稿
⑦ DOM 发送 GUI~10sCDP 定位输入框 → 键入 → 发送 → 验气泡
合计（单条）~25–50s，典型 ~35s连发再叠上「客户自己连发那几条的间隔」
时间大头是两处 15s 轮询（①捕获 + ⑥发送领取），占一半以上；LLM 起草和 DOM 发送本身都不慢。方案 B 不拖慢单条——③在单条时 ~0，它只在连发时把「该等的等到位」避免抢答。想更快可把 AKKE_POLL_INTERVAL 从 15s 调小（但增加 CDP/DB 轮询压力，需权衡）。
对照修复前：老的抖音 PC 客户端 VL 版，发送 GUI 段就 ~35s（3–4 次截图 AI），草稿又走 5min cron → 端到端常 6+ 分钟。DOM + 秒级 + B 之后压到 ~35s。
