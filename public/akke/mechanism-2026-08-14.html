00 · 读法

哪些是销售说的，哪些是界面上写着的——两者分开标

这一页的判断分两类，混在一起会出事，所以全程分开标注：【口径】= 销售在会议里说的；【实证】= 截图上直接读到的字。凡是两者冲突或只有口径没有实证的，一律进「待问清单」，不写进结论。

一处方法上的坦白

11 张截图全部是腾讯会议里对方共享屏幕的录屏截图（标题栏「水流AI–子淮正在共享屏幕」），也就是说：看到的是销售自己那台演示机的状态，不是甲方装机后的状态。演示机上同时装着 ToDesk、向日葵远程控制等工具，无法判断这些是产品依赖还是销售自用——已列入待问。

01 · 水流

水流 AI员工系统 —— 本地 Windows 客户端 + 自研微信聚合壳 + 双模 RPA
一句话结论 　置信度 0.80

它是一台「装在你电脑上、以你的身份操作的机器人」，而且有软/硬两种 RPA 模式——硬件模式是不是会接管鼠标键盘，是本次最该问清的一件事

① 用什么设备

电脑为主，手机为辅。【实证】Windows 客户端，窗口标题 AI员工测试，左下角常驻设备标识「子淮PC」。
【口径】大部分事情在电脑端做；小红书自动获客只能手机做，且指定机型摩托罗拉 S50；电脑和手机装同一个水流软件，电脑给手机发指令。

两条能互相印证

【实证】养号任务弹窗里，采集平台「小红书」是灰的，并提示「产品功能迭代升级中，【小红书】相关功能暂时关闭」。
这与「小红书只能手机做」对得上——PC 侧小红书能力关掉了，所以被迫走手机端。锁死摩托罗拉 S50 这一点，最可能的解释是他们只对这一款 ROM / 无障碍服务做了适配（0.55 推断，需确认）。

② 怎么控制 / 运行

环节机制依据

双模 RPARPA 助手面板底部写着「硬件RPA支持：未开启」——说明存在软件 RPA 与硬件 RPA 两套，且演示时硬件模式是关的【实证】截图 4 0.85

这里有一处必须点破的矛盾

本次【口径】是「浏览器打开以后，电脑仍可以做别的事情」。
但 08-06 那次的实证截图上，水流跑起来时屏幕顶端有红字「模拟操作中，请暂停操作键盘鼠标」，浮层里还写着「Ctrl+Alt+Del 解除锁定」。

最可能的解释（0.6，可证伪）：两句话说的不是同一件事——浏览器抓取（独立浏览器窗口跑）不占用人机交互，而硬件 RPA / 微信托管（真接管鼠标键盘）会锁住。「硬件RPA支持：未开启」和「隐藏模式」两个开关正好是这条假设的落点。

零假设：如果这条不成立，那么「模拟操作中请暂停键鼠」应该在任何任务下都会出现，或者根本不该有「硬件RPA」这个词。验证方式（一句话）：「跑微信托管的时候，这台电脑还能同时用来做别的事吗？硬件 RPA 开启后有什么不一样？」

③ 是否依赖电脑 / 插件 / 脚本

  • 依赖客户端：是，必装。
  • 依赖用户写脚本 / 装插件：否，全部材料里未见任何要用户配脚本、装浏览器插件的环节。
  • 依赖电脑常开：是——【口径】「要一直开机」。
  • 手机侧：装同一个水流软件、由电脑下发指令 → 属于「电脑控制手机」，不是手机自跑；连接方式（USB / 局域网 / 远程）本轮未确认，已列入待问。

④ 实际操作流程

从截图能还原出一条完整链路：

  1. 设关键词 → 客户端弹浏览器，在抖音采集评论
  2. 采集数据表：字段为 序号 / 昵称 / 头像 / 发布者昵称 / 评论内容 / 评论时间 / IP地址 / 点赞数 / 操作；可按平台与评论时间区间筛选
  3. 勾选后批量动作：关注 私信 回复 留痕 删除 清空；行级动作：查看主页 视频链接 二维码 删除 拉黑
  4. 公转私链路（一级菜单单列一项）
  5. 微信聚合客户端接管：右侧侧栏四个 tab —— 快捷回复 / RPA助手 / AI销冠 / 客户信息
  6. SOP 跟踪客户：按好友逐条设置 SOP 计划，可看执行记录

02 · 今立

今立智能 超级智剪 —— 纯电脑安装包，靠「官方合作」而不是靠模拟点击
一句话结论 　置信度 0.60

它把风险赌在「我是抖音官方合作商」这一句话上；而私信回复的实现却是一张 Excel 关键词表——技术档次和叙事档次差得很远

① 用什么设备

纯电脑端。【口径】「电脑安装包的形式」；「安装包有更新的话，打开电脑软件后会自动弹出更新提示」。全部材料未出现任何手机侧要求——这与水流（小红书必须用摩托罗拉 S50）形成鲜明对比。

② 怎么控制 / 运行

环节机制依据
客户端Windows 安装包，自带更新检查【口径】
风控路线「抖音官方合作商，和抖音合作，交钱，所以私信不容易被封禁/限流」——如果属实，它走的是官方授权通道，而不是模拟人工点击【口径】0.45 未验证
私信自动回复关键词匹配表：一张 Excel，A 列关键词、B 列回复，工作表页签为「话术流程 / 关键词」。不是语义理解【实证】截图 10 0.9
前后台「电脑自动化操作和使用者使用电脑不冲突」【口径】，无界面证据
响应速度「秒速回复用户」——事件触发式，不排队【口径】

③ 是否依赖电脑 / 插件 / 脚本

  • 依赖客户端：是。
  • 依赖用户写脚本：不写代码，但要人工维护关键词表——这实际上就是「用户提前配置」的另一种形态，而且维护量不小（一个单品类工厂就 43+ 行）。
  • 依赖手机：否。
  • 依赖电脑常开：本轮未确认（已列入待问）。既然是安装包 + 秒回，大概率要常开，但没有证据。

④ 实际操作流程

装包 → 绑定平台账号（08-10 材料里销售强调走「官方二维码授权，不是任何第三方」）→ 维护关键词表 → 私信/评论按关键词触发自动回复 → 内容侧走超级智剪那一整条（脚本 → 素材 → 数字人 → 混剪 → 时间轴工程 → 创意计划 → 多渠道发布）。

⑤ 发送时间机制

这一格基本是空的

目前只有一条【口径】「秒速回复用户」，即事件触发、无延迟。本轮材料里没有看到任何时间窗口、频率控制、节奏模板、冷却时间的配置项——而水流那边这三样都有界面。

这既可能是「没做」，也可能是「没演到」。但对家装场景是个实质问题：秒回陌生私信本身就是平台风控最敏感的特征之一，一个连频控都没有的系统，和它宣称的「官方合作所以不封号」是互相依赖的——如果官方合作那句话是假的，这套就没有第二道防线。

零假设：如果它有频控，销售在被问到封号问题时最自然的回答应该是「我们有频率控制」，而不是「我们和抖音有合作」。可证伪方式：直接问「一个号一天最多发多少条、间隔怎么设」。

① 它把「算力」翻译成了人话

今立自己承认的两个短板（销售口径，直接记下来）

「重复发信息的情况，也存在」「上下文处理不好」。

这两条和「关键词表驱动」是同一件事的两面——关键词匹配天然没有会话状态，所以既会重复触发，也接不住上下文。这是我们在同一场景下可以正面打的点，而且是他们自己说的，不用我们去论证。

03 · 对照

同样是「电脑端」，两家其实是两条完全不同的路
维度水流 AI员工今立 超级智剪我们（参照）
① 设备电脑为主 + 手机（小红书专用，锁摩托罗拉 S50）纯电脑云电脑 + iPhone（WDA）
② 控制方式本地客户端驱动浏览器 + 自研微信聚合壳 + 软/硬双模 RPA本地安装包，声称走抖音官方合作通道云电脑 GUI 串发 + WDA + 抖音 web 接口签名
③ 前台占用抓取时不占；硬件RPA / 微信托管疑似会占（待证）声称不冲突，无证据云电脑独立窗口，不占本机
④ 电脑常开必须（口径明确）未确认云电脑常驻，本机可关
⑤ 回复引擎AI员工（可配上下文轮数 0–50、严苛指数、守则、卡点知识库）+ 流程表节点权重Excel 关键词表（自认重复发送、上下文差）LLM 语义 + 金牌案例训练 + 人审
⑥ 时间机制三层完整：工作时段 + SOP 相对/绝对时刻模板 + 定时执行/闲时计划只有「秒回」，未见频控cron 入队 + 配额 + 串行节奏
⑦ 风险归属自己承认「爬虫 → RPA」是为了降封号风险，但风险仍在甲方账号上把风险押在「官方合作」这一句上人机混合，可降级人工
⑧ 价格带2,980 / 9,980 每年（+300/月设备租赁）13,800 – 290,000 每年—
对我们最有用的一条 　置信度 0.70

「电脑端竞品」这个说法把两种完全不同的风险模型混在了一起，采购时必须拆开问

水流是「用你的身份、在你的机器上、模拟你本人操作」——好处是不需要平台配合，坏处是封号风险 100% 落在甲方账号上，而且要占一台常开的电脑。
今立是「我和平台有约，所以我可以合规地发」——好处是如果为真，风险几乎归零；坏处是这条无法自证，而且一旦不成立，它连频控这道基础防线都没有。

所以对同一句「我们是电脑端」，要问的两个问题完全不同：对水流问「跑的时候电脑还能用吗、硬件RPA 是什么」；对今立问「官方合作是哪一类资质、能不能看合同/后台接口」。
