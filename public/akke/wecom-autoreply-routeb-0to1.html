02 / 0→1 逻辑原理图

一条客户消息，怎么自动变成一条回复

五段流水线，分布在三台主体上。两个地基约束决定了形态：(1) 企微 PC 客户端 UIAutomation 树黑盒 → 只能截屏 OCR；(2) 云电脑（国内）连不上 Vercel，但能连 Fly → 大脑调用走 Fly 中转。

① 截屏 VL 读消息
无影 · 扫未读→点开会话→Qwen VL 读最新客户消息 + 身份（UIA 树黑盒，纯 OCR）；内部群/自己发的/重复 → 跳过
↓ POST generate（带 WECOM_CHAT_SECRET）
② Fly 中转（桥）
akke-worker-prod · 透传到 Vercel（云电脑连不上 vercel.app，Fly Tokyo→Vercel 必通）；不持密钥
↓ 服务端转发
③ chatReply 生成
Vercel · 拉历史 + 小艳人设/知识库/few-shot → nurture 话术；落 messages(role=customer) + 会话；Langfuse/成本注入
↓ 回 reply 文本
④ GUI 发送
无影 · 拟人延迟 5–20s → 点输入框 → ctypes 逐字 Unicode 打字（不粘贴）→ Enter
↓ POST confirm（发成功才回写）
⑤ 回写
Vercel · 落 messages(role=ai) status=sent；显式失败：没真发出就不记，DB 不假阳性
蓝=无影云电脑（中国 IP，唯一能读写企微 GUI） · 绿=Fly worker（中转桥，云电脑↔Vercel） · 紫=Vercel（大脑 chatReply + DB 落库，云电脑连不上）
关键：读靠截屏 VL（企微 UIA 控件树整个黑盒，探针实测只暴露标题栏）；大脑调用靠Fly 中转（绕开 Vercel 大陆不可达，同时绕开卡死 kf 方案A 的 ICP 备案墙——本路是入站请求不调企微 API）。

迁移 workflow 失败（db push 没跑到）supabase/setup-cli 拉 CLI release 撞 GitHub API 限流（transient flake，非 SQL 问题）重跑 workflow（限流窗口过了即过）重跑 success

04 / 下一步待做优化

接下来做什么

下一步优化列表

①
明早灰度真发（在场盯第一批）最该做
主号无隔离，风险最高。改 AKKE_WECOM_DRY_RUN=0 + AKKE_WECOM_HOURS=9-21（收回测试用的 0-24），9 点起开着终端看头几条真实客户的读/回质量，手放在建 wecom_reply_STOP 秒停上。
②
逐字输入 / 发送键 线上复核
自家群已验逐字 Unicode 吃 + Enter 发；真实客户窗口再确认一次（不吃切 AKKE_WECOM_TYPE_MODE=paste；发送键不对切 ctrl+enter）。
③
转人工 / 接管
V1 没做。客户明确要真人时，先 prompt 软处理；后续接最小版「转人工 → AI 停回」（接待人选待定）。
④
多条消息合并读
补「自上次回复以来的多条客户消息」一次性读齐合并成一轮回复，修「只读最新一条」缺口。
⑤
稳定身份防串台
探无障碍树/会话存档能否拿到稳定 external_userid，替「显示名认人」；量大前必做。
⑥
登录态持久化 + 未读扫描鲁棒化
验无影重启后企微登录是否还在（类比抖音 cookie 过期运维）；多个未读会话时的扫描/点击策略（目前点最上一行）。
⑦
灰度提量
该号观察 1–2 周无异常，再把日限从 20 往上调。
⑧
朋友圈点赞（V2，另案）
企微做不到给客户朋友圈点赞（产品边界）；点赞=硬需求时只能走个人微信一体化，封号最高，单独评估。

方案选型回顾（为什么是这条路）

起点是「云电脑 + 低风险」两个互相打架的诉求；逐层裁定后落到方案B + 风险最小化。

最低风险 kf 官方 API（方案A）— 合规零封号，但卡 ICP 备案域名、需客户多点一次链接 → 冻结待命
本报告 企微 PC GUI 自动化（方案B）— 能落地、客户资产可继承；代价=封号风险（主号无隔离，灰度从严补偿）
最高风险 个人微信一体化 — 唯一能做朋友圈点赞，但封号最狠、号失全失不可继承 → 仅 V2 点赞硬需求时评估
读法三选一中：③UIAutomation（黑盒否决）/ ②会话存档（官方稳但 ¥1800/年+客户存档提示）/ ①OCR（用户选定，零额外成本、全在云电脑）。
