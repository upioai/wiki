她回了 2 个字

花爷魫先生用了 3 小时 05 分才回，回的只有#2「你好」2 个字。没有问产品、没有问价格、没有报户型、没有任何 disclosure —— 比草莓圣戴女士主动报「我没有做嵌入 / 放客厅里」温度低了整整一个量级。这是一个勉强睁眼的客户：他确认了「我看到了，我愿意聊」，但没给任何抓手。

⚠ 极弱信号
「你好」+ 3 小时延迟 ≠ 高意向回应。这是抖音 DM 里典型的「礼貌确认」级别 — 客户点了「确认聊天」按钮，知道你不是机器人，但还在评估你值不值得继续花字。对应的正确动作是「再问一个低成本问题让他多说一句」，而不是立刻跨步推微信。本案 ACT 06 走了相反的方向。
ACT 06 · 接住 2026-05-25　21:43 CST · 客户首响后 50 分

跟进话术：跳过产品咨询，直接推微信

跟进 DM（#3）的策略选择是跳过产品咨询、直接转通讯渠道：「加我v：Homedz3791（设计师武海艳）…直接发你方案，抖音图压缩看不清」。承接句「在的呢～餐边酒柜的细节等」很短，没有继续追问户型/预算 —— 整条话术的重心是把对话从 DM 搬去微信，前提是相信「能搬走 = 加微 = 进入私域转化漏斗」比「在 DM 里继续养」更值。

承接 → 锚定专业身份 → 抛微信号 · 三步链
第一段「餐边酒柜的细节等可以加我v」：承接客户来意，但不展开问户型，立刻拐到「加 v」。
第二段「设计师武海艳」：抛真人姓名 + 设计师身份，把营销号包装成「专业服务」，是 Akke 加微话术的标准模板。
第三段「我做过几套浙江同户型，直接发你方案，抖音图压缩看不清」：给加微的具体动机（要发方案 + 抖音图糊）—— 这部分是有效的，符合「不是『留个微信吧』，是『我有东西要发你』」原则。
🔀 系统 draft 与实发话术不一致
DB 里其实有一条 AI 自动生成的标准跟进 draft（status=draft，没用上），策略与 PM 实发完全不同 —— draft 想继续聊产品/锚价/活动，PM 实发跳到加微。两条话术放一起就能看出对客户温度的判断差：
DB draft · 未使用
「你好，花爷魫先生姐，你刷到的酒柜效果图是我们设计的，浙江接过几单类似户型。设计费包含在总价里，全屋按投影面积568元/㎡全国统一价，现在活动期价格还能更优惠些。您家准备先动哪一组柜子？」
PM 实发 · 见 #3
「在的呢～餐边酒柜的细节等可以加我v：Homedz3791（设计师武海艳），我做过几套浙江同户型，直接发你方案，抖音图压缩看不清」
策略对照：DB draft 是「再问一句拿条件」（与 ACT 05 signal 的建议同向）；PM 实发是「跨步推微信」。截至 5-27 20:49 共 47 小时客户未回 —— 当然不能说就是因为换了策略，但「极弱首响 → 急推微信」这条路径在这个案例里没有跑通。
ACT 07 · 现在 stage = ice_break · 加微未通过 · 47h+ 沉默

他没再回

对话停在 ice_break · 客户至今未对加微请求做任何回应（5-27 20:49 截图显示无新消息，距加微 47 小时）。
系统视角里这条会话停在「opener 已发 · 等首响」（DB 里跟进 #3 不存在）；现实视角里它停在「加微未通过 · 客户温度回落」。followup_policy=standard 的下一步会自动起草一条新跟进 —— 但因为客户首响其实已经收到过、只是 DB 没有记录，下一条 followup 如果照 ice_break 模板写，会重复破冰一遍，进一步打扰。本案的正确下一步是先 writeback 修复客户回复 + 跟进 #3 入库，让系统看到真实的对话状态。
复盘 · 这条线索教会我们的

5 个可复用的话术原则

1
「你好」不是回应，是抽样观察。客户首响只有 2 字 + 3 小时延迟时，下一步该做的是「再问一个低成本问题让他多说一句」（如「你家是几室几厅？」），而不是立刻推微信。本案的 DB draft 选择是对的，PM 实发选择是错的 —— 客户至今 47 小时无回应。
2
评论越短，越要先用产品价值钓，而不是直接搬通讯渠道。「设计费这么说私」只有 6 字、零具体信息时，opener 给省级 + 工艺痛点 + 报价（568/平）是对的方向；跟进时如果客户也只回 2 字，说明客户对 opener 信息都还没消化，再加一层私域转化只会让他选择不回应。
3
昵称含「先生」时不要默认加「姐」尾。「花爷魫先生姐」的双性别 token 是 generateColdOpener 的 prompt 缺一条条件分支：昵称含「先生」「哥」「老师」等已隐含性别的尾词时，「姐 / 哥」称呼后缀应该跳过。本案客户没拒收是侥幸，下一条同类 lead 可能直接拉黑。
4
跳出系统手发 = 故意切断审计。PM 用 Claude Code chat 起草 + 手机原生 DM 直发，DB 完全 0 记录 → 系统认为这条会话停在 opener 阶段，followup_policy 会按 ice_break 重复破冰，潜在地打扰客户。要么走 mark-contacted writeback 把手发同步进 DB，要么在 PM 决定接管后暂停 cron 对这条会话的 followup，不要让两条故事线并存。
5
check-replies cron 失效要靠人发现，案例里要诚实写。本案 last_inbound_at = null 但客户明确回了 —— 是 check-replies 在 5-25 20:53 那条 inbox 漏抓导致。PM 从手机 4G 端肉眼发现回复，触发了一连串绕过系统的决策。在「客户回复检测」这条管道修好之前，所有 ice_break 会话都得手机端兜底，案例库里要保留这条记录，提醒下一次 Akke 自动跟进决策不能完全信任 DB 状态。
