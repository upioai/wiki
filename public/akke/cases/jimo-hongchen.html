复盘 · 这条越界 + 重发 bug 教会我们的

5 个可复用的话术 / 系统原则

1
触达决策要锁版本，re-score 不能擦记忆。 既墨红尘 5-24 sweep 时 intent=93 系统主动触达，后被 re-score 改成 0 — 重发 pipeline 看当前 0 分 + 没 conversation 记录 = 把她当未触达 lead 又发一次。修复：dedup 应锚 today-openers.idx + status=sent（历史触达记录），不依赖当前 intent_score 或 conversations 表。analyze cron re-score 应只更新 comments 表，绝不影响触达状态。
2
正确 + 完整 ≠ 像人。 #5 是 270 字结构化方案（数据 + 编号 + 建议），客户两次精准戳穿「像豆包写的」。AI 文案的反检测路径不是更长更全，而是更碎更自然（多发几条短的 vs 一条堆砌长的）。
3
本地切口 > 全国模板。「广西的回南天」（#1）>> 「广西这边南方梅雨季潮气重」（#11）。当 city 为 NULL 时，找省内的具体生活痛点词（回南天/暖气干/挑高大）替代地名，是降级模式的最佳实践 — 应该写进 qwen3 prompt。
4
send-one.py 必须查 ChatRoom UI 而不只是 messages 表。 当 PM 手动消息没经 writeback 时，messages.count() == 0 不等于真没聊过。修复方案：发送前在 ChatRoomActivity dump UI 看 dm-bubble 节点数 — 任意 > 0 就 abort 重发，降级到 writeback 现有消息。
5
case-study skill 不应该自动新建 conversation。 build-case-study.ts 找不到 conversation 时报错就好，不要让 PM 通过 case-study 流程触发一次额外的 DM 发送。这次重发 bug 链路：PM「为既墨做案例页」→ skill 调 build-case-study → 没数据 → PM 让 Claude「手动开 conversation 补发后再写案例」→ Claude 发了 #11。但根因还是 (1) — 即使 case-study 流程关闭，下一次 sweep / batch-send / nurture cron 也会因为 re-score 把她当新 lead。
