销售手机里的历史客户目前没有完整同步到云端，不能直接让云端判断和召回。一期必须先由 APK 扫描手机会话，第一层识别“客户 / 同事 / 无关人员”，非客户直接跳过；第二层只打开客户会话、回读具体聊天并同步云端，再判断是否进入七次召回。不要求销售人工补备注、白名单或标签。七次话题、分阶段间隔、发送前复核、回复后重建和第 7 次后的低频培育继续完整参考企微现行逻辑。

01

从企微现行召回复用什么

本页已对照企微召回代码、生产部署台账和运行复盘。企微不是“到第 7 天发一次”，而是以 fixed_7_v1 七次计划为主，并在每次派单前用 stage_v1 重判停止信号和当前阶段；发送成功后按阶段计算下一次时间。个人微信完整复用这套发送逻辑与节奏，只替换 APK 执行端。

直接复用

候选基础门

  • 先确认对象属于客户；同事、系统号和其他无关人员直接跳过。
  • 最后一条必须是我方消息，客户一回复就自动掉出候选。
  • 存在可核验会话与历史；没有消息、身份不可信或幽灵会话不主动推。
  • 入队前再次读取停止状态，防止生成话术期间客户状态已变化。
直接复用

规则先于 AI

  • 明确拒绝、已成交、已装修完等确定性事实直接停止，AI不能推翻。
  • 客户在等自己的设计师效果图时延后，不给他发我方案或案例图。
  • 只有规则落在模糊的“观望”状态时，才让 AI进一步细分。
直接复用

历史承接与选题

  • 从产品配置、品质保障、服务流程、预算、板材防伪、售后、工厂直供等标准话题里选。
  • 有户型、面积、风格、装修阶段时，优先使用相近案例、效果图、风格建议、施工提醒等画像钩子。
  • 没客户原话、也没有效画像时，禁止假装知道户型和预算。
直接复用

话术安全闸

  • 必须提供新信息，不能只问“考虑得怎么样”。
  • 禁止编造报价、优惠、期限、案例、方案进度和交付承诺。
  • 禁止把客户原话生硬引用出来；禁止重复历史已发正文；最终合并成一个气泡。
口径纠正

“7 次”的含义

一个沉默客户进入一轮最多 7 次的召回计划。每次到期只发一条，之后等待到下一阶段时间；不是要求先沉默 7 天，也不是连续 7 天机械发送。

完整复用

七次计划与回复重建

沿用 fixed_7_v1 的七个话题顺序；每次派单前仍重读最新历史并检查停止信号。客户回复后，旧轮未发任务全部作废，自动接待承接完成后，根据新回复生成新的个性化七次计划。

03

个人微信智能召回完整逻辑

第一级：先识别人，再决定要不要读取聊天

识别结果参考证据系统动作
客户历史里存在装修、户型、柜体、报价、量房、方案、到店等业务对话；或已有可靠客户身份记录。进入第二级，打开会话读取具体历史；身份仍有疑问时标记“待确认”，不发送。
同事企业内部通讯录、已知员工账号、长期内部工作沟通、文件协作或排班通知等确定性证据。直接跳过并记录原因；不得进入历史召回判断。
无关人员系统服务号、群聊、订阅通知、快递外卖、亲友或其他与销售业务无关的会话。直接跳过；不上传无关聊天正文，不生成任务。
无法确认只有昵称、没有足够聊天内容，或分类证据互相冲突。保持未分类并跳过发送；后续有新消息时再增量判断，不让销售补备注。
隐私和成本边界：第一层尽量只使用会话标题、会话类型、末条摘要和本机已有身份线索做粗分；只有判为客户或高概率客户，才打开会话读取更多历史。非客户不上传完整正文。

第二级：只对客户做历史判断和七次召回

① 本地建档APK读取客户会话，将可见历史和证据增量同步云端。
② 硬排除拒绝、成交、装修完成、已删、历史不足、正在人工跟进。
③ 历史判断是否值得再次联系？当前阶段和最自然承接点是什么？
④ 取本次话题按七次计划取当前触次；个性化计划优先；一个气泡。
⑤ APK 复核主动搜人、核标题、核最新消息、核销售是否刚跟进。
⑥ 发送并计数真实气泡出现才记 sent，并推进触次；否则 failed / skipped。
⑦ 等待再评估回复→作废旧轮并重建；未回→到期进入下一次；满7次→低频培育。

单微信窗口的任务优先级与切换

优先级触发场景切换动作
P0 · 客户新消息正在召回的客户突然回复，或其他客户出现新消息。停止领取新的召回任务；把新消息加入待回复队列，按最早未回复优先逐个处理。被召回客户回复时，同时取消该客户旧轮剩余召回任务。
P1 · 回复恢复与人工接管上一条客户回复生成成功但尚未确认发出，或销售正在手动输入/发送。先恢复并确认客户回复；检测到人工操作则让出窗口，相关召回任务重新复核后再执行。
P2 · 历史建档没有待回复消息，但还有未完成的存量客户分类或历史同步。按小批量继续扫描；每打开一个会话后都重新检查是否出现客户新消息。
P3 · 主动召回没有待回复、没有待恢复发送、当前不在人工操作，并且召回任务已经到期。一次只领取一条；搜索、身份核对、最新消息复核全部通过后才发送。
总原则：个人微信只有一个前台窗口，必须保持“客户回复 ＞ 历史建档 ＞ 主动召回”。任何新客户消息都可以阻止下一条召回，但不能粗暴打断一个已经按下发送键的动作，否则会造成“不知道发没发”的重复发送风险。

召回执行到一半时，在哪个点切换

尚未输入

立即暂停召回

仍在搜索、打开会话或读取历史时发现新消息，当前召回任务释放或延后，立即转去处理客户消息。

已经输入，尚未发送

清草稿后切换

先确认输入框内容属于召回草稿并安全清空，再保存任务为待重试。清不干净或无法确认时不切换发送，截图并进入人工核对。

已经点击发送

先确认结果再切换

不允许自动重发。先核对真实气泡并完成 sent / uncertain 回执，再处理新消息；结果不确定时把该召回转人工核对。

回复处理完

重新排队，不接着盲发

重新扫描全部未读；全部清空后，原召回任务必须再次核对客户身份、最后消息、人工跟进和到期时间，仍安全才恢复。

04

召回发送话术逻辑

优先级 1

承接未完成事项

客户问过报价、材质、户型、风格、量尺或工期，但对话停在“还缺一项信息”时，直接补上下一步。不要重新自我介绍，也不要复述整段历史。

优先级 2

提供新的具体价值

给一条与历史有关的预算方法、施工提醒、选材尺子、空间建议或下一步准备事项。重点是“对他有用”，不是“提醒他回来”。

有画像才用

个性化钩子

只有历史里真的出现面积、户型、风格、装修阶段时，才能使用相近案例、效果图、搭配或施工节点。没有依据就不用。

无有效历史

直接不发

企微现行逻辑允许零画像时发统一兜底话术；本方案更保守：领导要求“根据历史判断”，历史不足就无法判断，一期不自动召回。

禁止

通用广告式召回

“最近有活动”“考虑得怎么样”“有时间来店看看”这类没有历史承接的文案，不得因为模型能生成就发送。

禁止

连发与机械追发

同一次只发送一个气泡，未到 next_eligible_at 不得产生下一次。客户回复先走自动接待，旧轮剩余任务全部作废；承接完成后才按最新历史重建下一轮。

示例

历史事实建议发送为什么
客户问过预算，我方问户型尺寸后沉默“您家户型图如果还在手机里，直接发原图就行，不用整理。我先按柜子位置帮您粗算一下，看看预算主要花在哪几块。”承接缺口；降低行动成本；不强推到店。
客户说水电刚结束“水电刚结束的话，柜子附近的插座和扫地机位置可以先留意一下，后面柜体尺寸定了再改会麻烦。您有现场照片的话我可以顺手帮您看一眼。”提供施工节点价值；自然打开下一步。
只有我方发过资料，客户从未说话不发送没有历史依据，任何个性化都是猜。
05

部署架构与必须新增的能力

后端

新增个微七次召回策略

  • 独立策略版本，例如 weixin_recall_7_v1，行为对齐企微七次计划。
  • 复用企微候选门、阶段判断、七话题计划、render、去重与安全闸；最短沉默默认仍为 24 小时，可配置。
  • 每次成功后按当前阶段写入下一次时间；完成第 7 次后进入低频五话题培育，而不是误写成停止。
  • 账号必须按 wx_phone_… 托管人设隔离，不能与企微销售 persona 混池。
接口

给 APK 增加任务协议

  • peek_recall：只问有没有活，不占任务。
  • claim_recall：原子领取一条，带客户名、话术和任务 ID。
  • complete_recall：回传 sent / skipped / failed 与明确原因。
  • 协议可复用企微接口语义，但必须校验这是该手机账号的个人微信任务。
APK

新增可打断的主动任务循环

  • 后台低频轮询，不依赖客户通知，但领取召回前必须先清空待回复消息。
  • 主动打开微信搜索客户，结果唯一才进入；搜索和读历史期间持续监听新消息。
  • 打开后核对标题与最后消息；客户已回、其他客户待回复或销售刚发过就暂停召回。
  • 以“未输入 / 已输入未发送 / 已点击发送”记录执行状态，按安全切换规则恢复。
  • 发送完核对真实气泡并回执；结果不确定时绝不自动重发。
历史前置

新增手机存量会话建档

  • 服务端账本目前不能覆盖销售手机上的历史客户，不能把“云端查不到”当成“没有这个客户”。
  • APK先分页扫描会话并完成客户 / 同事 / 无关人员 / 无法确认四类识别；非客户直接跳过。
  • 只对客户打开会话，读取当前界面可获得的历史，增量上传并保留来源、最早/最新时间和角色方向。
  • 回读不完整时状态必须是“历史不足”，不能误判为可召回，也不能要求销售补备注。
云端

客户历史建档协议

  • upsert_contact_classification：上传分类、置信度与证据，不上传无关人员完整正文。
  • sync_chat_history：按消息指纹增量写入，避免每次重复上传。
  • evaluate_recall：仅接收分类为客户且历史充分的会话，输出可召回 / 不召回 / 历史不足三态。
  • 每次发送前再同步最新可见消息，防止销售已跟进或客户已回复后仍发送旧任务。
总闸

急停要挡住存量任务

只关后端“继续入队”不够，APK仍可能领走已经 pending 的任务。总停必须同时让 claim 拒绝、APK停止主动循环，并把在途任务改成 aborted 或留待人工恢复。

风控

一期限额

1 台手机、1 个号；每天最多 5 条；两条随机间隔 5–15 分钟；9:00–21:00；同一客户同一天最多 1 条；严格服从 next_eligible_at；一次最多 1 条在途。

06

部署顺序

P0 · 先产出正式 0.10.5 基线包

从可追溯的 origin/main@d507ff2 运行正式发版脚本，生成带生产窄密钥的“多人共用已配置”包并追加 RELEASES.jsonl。禁止把 PR #946 的空凭据 .ci 测试包直接发给销售，也禁止按那个错误的 v0.10.1 文件名判断版本。

P1 · 1 台覆盖升级，不开主动召回

先装到 1 台选定手机，安装后读取包内 versionName / versionCode / build_id，并去无障碍设置将服务关掉再打开；完成通知访问、输入法启用、电池与厂商自启动设置。心跳必须出现同一个 0.10.5 build_id，再验证现有自动回复、绿色气泡方向识别和“召回历史验收”只读日志。

P2 · 手机存量会话建档（只读）

在 0.10.5 基线上新增分页扫描：先输出客户 / 同事 / 无关人员 / 无法确认四类结果；非客户不读完整正文。抽样验收分类准确率后，只对客户增量回读并同步历史，全程不生成发送任务。

P3 · 后端空跑判断

实现 weixin_recall_7_v1，只输出候选、触次、阶段、下一次时间、历史证据、跳过原因和本次话术，不写待发送队列。连续空跑 3 天，逐条确认七次节奏、历史证据、停止条件和回复重建均与企微一致。

P4 · APK 主动发送腿（仍 dry-run）

不能直接拿未合并的 PR #943 当生产实现；应基于最新 main 重新实现或重放后经 PR 合入，再接入 peek/claim/complete。注入“召回客户回复”“其他客户来消息”“销售手动接管”三类并发场景，验收任务能在安全点暂停、优先回复、清空未读后重新复核并恢复。

P5 · 1 台真发灰度

首周每天最多 5 条。每条以微信真实气泡为证，数据库 sent 不能单独算成功；每天复盘分类误差、回复、删除、跳过、认人失败和发送失败。

P6 · 扩到第二台

首台连续 7 天无异常、身份零错发、人群分类和历史判断通过验收后，再升级第二台。每台使用独立 wx_phone_… 人设和账号，不复用 xiawei/xiaoxia 的企微身份池。

07

上线验收清单

  • 销售不需要新增备注、标签或白名单。
  • 正式交付包的 build_id 可解析到 main commit，且不带 .ci / .dirty / .unknown。
  • 不以 APK 文件名代替包内 versionName、versionCode 和 BUILD.txt 校验。
  • 试点手机心跳版本与交付包 build_id 一致。
  • 0.10.5 覆盖升级后已重新绑定无障碍，系统截屏探针真实通过。
  • 手机存量会话能稳定分成客户、同事、无关人员和无法确认。
  • 同事、无关人员不会打开深读、不会上传完整正文、不会生成任务。
  • 无法确认的联系人保持跳过，不会被默认当成客户。
  • 历史回读日志能看到 N 条、最早/最新与角色方向。
  • 历史不足的客户不会生成任务。
  • 客户最后一条已回复时不会进入候选。
  • 明确拒绝、成交、装修完成客户不会入队。
  • AI证据能逐条回指历史原文。
  • 召回正文不编造、不引用客户原话、不与旧话重复。
  • APK搜索结果不唯一时必定跳过。
  • 打开错误会话或标题不确定时一个字都不发。
  • 销售刚手动跟进后，陈旧任务会被发送前复核挡住。
  • 任何客户出现新消息时，不再领取新的召回任务。
  • 召回对象回复后，旧轮剩余召回任务立即作废并优先承接回复。
  • 其他客户发消息时，当前未发送的召回能安全暂停，先处理待回复队列。
  • 召回草稿已经输入时，只有确认清空成功才能切换会话。
  • 已经点击发送但结果不确定时不会自动重发。
  • 待回复消息全部处理完后，召回恢复前会重新核对身份、最新消息和到期时间。
  • 同一次触达只发一个气泡；未到下一次时间不产生新任务。
  • 未回复客户按阶段间隔继续，累计最多完成 7 次。
  • 客户回复后旧轮剩余任务全部作废，先进入正常自动接待。
  • 承接客户回复后，能按最新历史重建个性化七次计划。
  • 完成第 7 次后进入企微同款低频五话题培育，不误标为 stopped。
  • 数据库 sent 与微信真实消息气泡一致。
  • 总急停后，新任务和已有 pending 都不能发出。
  • 首周每天不超过 5 条，且全程可追溯。
最终上线定义：不是“代码合并了”，也不是“APK装上了”。必须同时看到：正确 build_id 的手机心跳、dry-run 主动搜人全链路、至少一条真发气泡、完整回执、未到期不提前发下一次、到期能推进触次、客户回复后旧轮作废并正确承接，以及第 7 次后进入低频计划。
