一、开场三件事

01一行命令进项目
02先拉齐 git
03把目标说全
04先要方案，再让他动手
05干完二次确认

01　一行命令进项目

cd ~/Akke && claude --dangerously-skip-permissions

用 Codex 的同学把最后一段换成 codex 即可：cd ~/Akke && codex。

先确认文件夹名字。不同电脑上 Akke 项目的目录名不一定一样（有人叫 Akke，有人叫 Akke_AI）。第一次用先敲 ls ~ 看一眼真实名字，再把命令里的路径改对——路径写错的话，AI 会在一个空目录里开工，看起来一切正常但什么都找不到。
--dangerously-skip-permissions 是什么意思：跳过每一步的授权弹窗。好处是不用一直点“允许”，坏处是 AI 可以不问你就改文件、跑命令。只在自己的项目目录里用，别在家目录或系统目录用；心里没底的活就别带这个参数。

02　先拉齐 git（每次开工第一句话）

帮我同步拉齐 git，看一下团队最新的部署到哪一版了。

为什么要说这句：Akke 是 5 个人同时在改的仓，昨天你离开时的状态，今天早上大概率已经不是最新的了。不拉齐就动手，很容易把别人已经修好的东西再修一遍，或者基于旧代码下错判断。

仓里已经帮你做了一半。Akke 仓装了开会话自动同步的钩子——每次新开会话，它会自动把本地 main 快进到最新的 origin/main，并在开头打一行提示告诉你快进了几个 commit。
但它只动 main，不动你当前那条分支。所以如果你昨天的活还在自己的分支上，还是要让 AI 帮你把分支 rebase 到最新主线。
“仓里有什么”不等于“线上跑的是哪一版”。要确认线上到底部署到哪一版，让 AI 去打线上的探针接口（比如 /api/status）；git log 只说得清仓库里有什么，说不清线上在跑什么，这两者差好几个 commit 是常事。

03　把目标说全，先要方案再动手

需求给得越详细，返工越少。推荐顺序是：我把想法说清楚 → 让他先给方案 → 我看方案、提意见 → 确认后他再动手。不要一上来就说“你看着改”。

我的核心目标是 <一句话说清楚要达成什么>。
请先读相关文件和项目规则，先别改任何东西，告诉我你准备怎么做、会动哪些文件、有什么风险。
我确认方案之后你再开始。

干活过程中也要不停把核心目标重复给他——上下文一长，AI 容易跑偏到某个细节上，忘了你最开始要的是什么。

二、话术模板：想不起来怎么说就抄这里

下面这些都是团队日常在用的原话，直接复制改几个字就能用。

开工 / 派活

同步帮我同步拉齐 git，看一下团队最新的部署到哪一版了。

指定仓库请在 <仓库名> 这个仓里完成 <任务>。
Akke org 有 4 个活跃仓共用同一个数据库，说错仓 = 白做一遍。企业微信的活在 wecom-chat，门店工作台的活在 store-workbench，抓取/私信/图文这些在 Akke。不确定就先问他“这个需求归哪个仓”。

自动开工作区后续任务自动开 worktree，在对应的仓库里执行任务；需要提 PR 的自动提 PR。
worktree 就是给这次任务单独开一份干净的工作副本，几个会话同时干活也不会互相踩。Akke 仓已经配了自动隔离，同一个目录开第二个会话时会自动躲进去。

提效 / 并行

多 agent这个任务如果能拆成互不依赖的几块，请派多个 agent 并行处理，提升效率。

换模型/model　难啃的活换更强的模型，简单重复的活换更快的模型。

挂目标/goal <做什么 + 怎么算完成 + 要贴什么证据>　写法见下面第三节和第六节。

卡住 / 出错时

定位根因这个问题请再仔细帮我评估、定位根因，给我证据，先别急着改代码。
复杂问题最值钱的一句话。AI 的默认冲动是马上改点什么让报错消失，但那往往只是把症状盖住。反复让他定位根因，比让他反复试错快得多。

拉回跑偏先暂停，当前改动超出范围了。回到上一个稳定状态，重新给我一个最小方案。

要证据不要跟我说“应该没问题”。把你实际跑的命令和原始输出贴出来。

生成文档 / 沉淀

出文档帮我生成一个文档，把今天遇到的问题和根本原因进行总结，提交到 upio 的 html 页面。
upio 页面就是你正在看的这种页。它们放在 upioai/wiki 这个仓的 public/akke/ 目录里，推上 main 就自动上线；线上地址不带 .html，是 upio.ai/akke/<名字>。

记习惯把这个习惯记进 CLAUDE.md，计入我的个人记忆；以后保持用中文、跟我说大白话。

不入库这段跟项目无关，不需要计入团队记忆，本次会话无关。
很重要。团队记忆是所有人每次开会话都要读的，塞进无关内容等于让全组每天多付一笔税。

收尾/wrap-up　每轮对话结束跑一次：出交接卡、把这轮该记的写进团队 memory、给下一轮的提示词。

验收 / 二次确认

目标核对任务完成后请二次确认：我的目标达成了吗？部署成功了吗？

分清三态请把结论分成三种：已验证通过 / 验证不通过 / 没验成（说清为什么没验成）。
最怕的不是“不通过”，是把“我没查到”说成“没有这回事”。明确要求他分三态，能挡掉大部分假情报。

遇到要开权限的：比如 OpenRouter 的 key、Fly worker 的 token，这类是找 PM 要、由 PM 统一下发的，别自己去找一个凑合的填上，更不要把 key 贴进对话里或写进仓库。

三、五招提效（附各自的适用边界）

1. 派多个 agent 并行

一句“请派多个 agent 并行处理”就行。

什么时候有用：任务能切成几块互不依赖的活——比如同时在多个目录里找线索、从几个不同角度审查同一份改动、并行核实几件互不相关的事实。

什么时候反而更慢：一步依赖上一步结果的活（改完再测、测完再改）。硬拆开只会多烧钱，而且每个 agent 看不到别人的上下文，最后还得有人来合。

2. 用 Codex 接着 Claude 的会话干

Codex 可以把本机 Claude 的历史对话导进来，接着上一轮继续干，不用重新交代一遍背景。

本机已经在用：Codex 的导入台账里有 181 条 Claude 会话记录，其中 175 条是 Akke 项目的。

另外 Codex 自己也有接力命令：codex resume 接回上一次会话，codex fork 从某次会话分叉出一条新的。

3. 空闲/晚上挂 /goal

给他一个目标，他会一直干到目标达成才停，中途想停下来会被打回去继续。适合“有明确完成态”的活（修到全绿、跑到剩余 0 条）。

周期性巡检（每 20 分钟看一眼 CI）用的是另一个命令 /loop。

两个坑，先看第六节再挂。一是关终端就全停，不能真的过夜；二是它的验收方式跟你想的不一样。

4. computer use：让他自己点屏幕

完全不想自己动手时，可以让 AI 直接操作界面去点。本机 Claude 这边接的是 Chrome 扩展，能开标签页、点页面、填表单、读控制台报错。

实测很慢——每一步都要截图、识别、再点，比直接敲命令慢一大截。当成偶尔用一次的兜底手段，别当主力。

另外别让它去点会弹确认框的按钮（比如“删除”），浏览器弹窗会把自动化整个卡死。

5. /model 换模型

难活换强模型，简单活换快模型。一轮对话里随时能换，不用重开会话。

加分项：让他先读历史再提方案

很多方案其实团队早就评估过、否决过。开口前加一句“先翻一下 docs/claude-memory/ 里有没有相关结论”，能省掉一整轮已经被否决过的讨论。

四、会话管理：别让对话框拖慢你

接回上一次对话

/resume　挑一条之前的会话接着聊，上下文都还在。

对话太长了怎么办

新开一个会话，把旧会话的标题（或结论）发给他让他读上一轮，然后把旧终端关掉。
上下文越长每一轮越慢越贵，及时换新会话省下来的时间很可观。

一个目录只开一个会话

同一个文件夹开两个会话会互相抢工作区、抢分支，改到一半的文件可能被另一个会话提交走。Akke 仓已经自动处理：开第二个会话时会自己躲进独立 worktree。看到它说要开 worktree，让它开就是了。

五、记忆记到哪里：三个抽屉别放混

抽屉放什么怎么跟他说
个人记忆
CLAUDE.md		 你个人的习惯和偏好：说中文、讲大白话、不要一上来就动手。只影响你自己。 把这个习惯记进 CLAUDE.md，计入我的个人记忆。
团队记忆
docs/claude-memory/		 项目上的结论和教训：这个方案为什么被否决、这个坑长什么样、这个字段的口径是什么。跟着代码推给全组共享。 把这条计入团队 memory。
不记 跟项目无关的、只在这一轮有意义的临时信息。 这段跟项目无关，不需要计入团队记忆，本次会话无关。
为什么要分清：团队记忆是全组每次开会话都会读一遍的东西。往里塞无关内容，等于让每个人每天都多读一遍废话。所以宁可多说一句“这条不用记”。

六、四个容易理解错的地方

这一节是专门纠偏的——下面每一条，都是听起来很合理、实际会让你白等一晚上或者白高兴一场的说法。

① /goal 挂着过夜？终端一关就全停了

/goal 和 /loop 都活在当前这个会话里。你合上电脑、关掉终端，它们就一起没了，不是在云端替你跑。

真要过夜跑、或者每天定点自动跑，用 /schedule（云端的定时任务），那个才是关了电脑还在跑的。

第二个坑更隐蔽：/goal 判断“达成没达成”，靠的是另一个模型去读你们的聊天记录——它看不到你的硬盘，也打不开网页。所以：

  • ❌ 写“确认文件已经生成”“页面正常” → 它永远判不了真，你会被无限打回。
  • ✅ 写“跑 <某条命令>，输出里出现 <某个具体结果>；必须把最后一次的原始输出贴出来，不贴不算达成”。

另外条件里别写“准确”“流畅”“尽量多修”这种形容词，评估器判不了，只会来回拉锯。

完整写法（含模板和好坏对照）在仓里：.claude/skills/loop-goal-spec/SKILL.md。挂之前让 AI 先读它。

② “自动提 PR”≠“自动合并”≠“已经上线了”

这是三件事，每一步都可能停住：

  1. 提 PR——现在 main 分支已经直推不进去了（服务端会拒），所有改动一律走 PR，连纯文档也是。
  2. 合并——低风险的 PR 会由仓里的机器人在检查全绿后自动合。但高危路径永远不自动合：改到模型配置、定时任务、数据库迁移、权限、CI 工作流这些，机器人只提醒，得你自己盯着合。
  3. 部署——合进 main 之后才开始部署。“PR 显示已合并”不等于“线上已经是新版本”，还要去打开真实页面或接口确认一次。

所以干完之后那句“我的目标达成了吗？部署成功了吗？”要分开问，并且要他拿出线上的证据，而不是仓库的截图。

③ 多 agent 不是越多越好

每多一个 agent 就多烧一份 token，而且它们互相看不见对方的上下文。任务本身是串行依赖的时候，拆开只会更慢、更贵、结论还对不齐。

判断标准很简单：这几块活能不能同时开工、谁也不等谁？能，就拆；不能，就别拆。

④ --dangerously-skip-permissions 真的会跳过确认

名字里的 dangerously 不是吓唬人的。带上它之后，AI 删文件、改配置、跑脚本都不会再问你。

怎么用才安全：只在 Akke 这类自己的项目目录里用；涉及数据库、生产环境、给客户发消息这类不可逆的动作，即使带了这个参数，也要自己盯着他每一步在干什么，别开着就去干别的。

七、收尾清单

  • 二次确认：我的目标达成了吗？部署成功了吗？——要证据，不要“应该没问题”。
  • 跑 /wrap-up：出交接卡（做了什么 / 效果如何 / 没做什么 / 为什么没做 / 经验教训）。
  • 该沉淀的说清楚记进团队 memory；跟项目无关的明确说一句“不用记”。
  • 有 PR 的话，把 PR 链接、验证结果、没做完的部分写进交接，别让下一个人猜。
  • 今天踩的坑值得留档 → “帮我生成一个文档，把今天遇到的问题和根本原因进行总结，提交到 upio 的 html 页面”。
一句话记忆：开工先拉齐 git，动手前先要方案，卡住了让他定位根因，干完了要他拿证据，结束时把经验留下来。
