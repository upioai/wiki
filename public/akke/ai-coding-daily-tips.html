一、开工三件事

01一行命令进项目
02先把代码拉到最新
03把要什么说清楚
04先要方案，再让他动手
05干完了要他拿证据

01　一行命令进项目

cd ~/Akke && claude --dangerously-skip-permissions

用 Codex 的同学把最后那段换成 codex 就行：cd ~/Akke && codex。

先看清楚自己电脑上那个文件夹叫什么。有人的叫 Akke，有人的叫 Akke_AI。第一次用先敲一下 ls ~（意思是“列出我的主目录里有哪些文件夹”），看准名字再把命令里的路径改对。
路径写错的后果很坑：AI 会在一个空文件夹里开工，看起来一切正常，实际上什么都找不到、什么都改不到。
命令后面那一长串 --dangerously-skip-permissions 是什么意思？
就是“别再一步步问我了”。加上它以后，AI 改文件、跑命令都不会再弹框让你点“同意”。
好处是顺畅，坏处是它可以不打招呼就动东西。所以：只在自己的项目文件夹里加这个，别在整台电脑的主目录用；心里没底的活，就别加。

02　先把代码拉到最新（每天第一句话）

帮我同步拉齐 git，看一下团队最新的部署到哪一版了。
为什么要说这句：Akke 这个项目是 5 个人同时在改的。你昨天下班时看到的样子，今天早上基本已经不是最新的了。不先拉到最新就开工，很容易把别人已经修好的东西再修一遍，或者照着旧版本得出错误结论。
好消息是，电脑已经帮你做了一半。每次新开一个对话窗口，它会自动把你电脑里那份“主线代码”更新到团队最新版，并在开头写一行告诉你更新了几条。
但它只更新主线，不会动你自己那条支线。（“支线”就是你自己单独拉出来改东西的那条线，改坏了也不影响别人。）所以昨天的活还没干完的话，还得让 AI 帮你把自己那条支线也拉到最新。
还有一件事很多人会搞混：“代码库里有什么”不等于“网站上正在跑什么”。
代码已经交上去了，不代表已经更新到线上了——中间还要排队、检查、部署，随时可能卡住。想知道线上到底是哪一版，让 AI 去打开线上那个版本信息的网址（比如 /api/status）看一眼，那个才作数。

03　把要什么说清楚，先要方案再动手

说得越细，返工越少。推荐这个顺序：我把想法讲清楚 → 让他先说怎么做 → 我看一眼、提意见 → 我点头了他再动手。别一上来就说“你看着改吧”。

我的核心目标是 <一句话说清要达成什么>。
请先去看相关的文件和项目规则，先别改任何东西，告诉我你打算怎么做、会动到哪些地方、有什么风险。
我确认之后你再开始。

干活过程中也要不停地把核心目标再说一遍。聊久了 AI 容易钻进某个细节里，忘了你最开始要的是什么。

二、话术模板：想不起来怎么说，就抄这里

下面都是我们平时的原话，复制过去改几个字就能用。

开工 · 派活

拉到最新帮我同步拉齐 git，看一下团队最新的部署到哪一版了。

指定项目请在 <项目名> 这个仓里完成 <任务>。
我们团队有 4 个代码库（可以理解成 4 个不同的项目文件夹），但共用同一个数据库，所以长得很像、很容易搞混。说错地方就是白干一遍。企业微信的活在 wecom-chat，门店工作台的活在 store-workbench，抓评论、发私信、发图文这些在 Akke。不确定就先问他一句“这个需求该在哪个仓做”。

自动开一份干净的后续任务自动开 worktree，在对应的仓库里执行任务；需要提 PR 的自动提 PR。
worktree 说白了就是：给这次任务单独复制一份干净的项目文件夹出来，你开好几个窗口同时干活也不会互相踩到。PR 是把改动交上去、等检查和人看过再合进主线的那道手续。这两个都已经配好了，你照抄这句话就行，不用懂原理。

提效 · 并行

多开几个分身这个任务如果能拆成互不依赖的几块，请派多个 agent 并行处理，提升效率。
agent 可以理解成 AI 的分身，一个分身负责一块活，几块同时干。

换个脑子/model　难啃的活换聪明一点的，简单重复的活换快一点的。

挂个目标/goal <做什么 + 怎么算干完 + 要拿什么证明>　具体写法看第三节和第六节，有两个坑要先知道。

卡住 · 出错时

找真正的原因这个问题请再仔细帮我评估、定位根因，给我证据，先别急着改代码。
这是最值钱的一句话。AI 的本能是赶紧改点什么让报错消失，但那往往只是把问题盖住了，过两天原样复发。反复让他找真正的原因，比让他反复试错快得多。

拉回来先停一下，你现在改的东西超出我要的范围了。回到上一个没问题的状态，重新给我一个最小的方案。

要证据不要跟我说“应该没问题”。把你实际跑的命令和跑出来的原始结果贴出来给我看。

出文档 · 记经验

出文档帮我生成一个文档，把今天遇到的问题和根本原因进行总结，提交到 upio 的 html 页面。
upio 页面就是你现在正在看的这种网页。说这句话，AI 会自己写好网页、传上去、给你一个能直接发给别人的网址。

记我的习惯把这个习惯记进 CLAUDE.md，计入我的个人记忆；以后保持用中文、跟我说大白话。

别乱记这段跟项目无关，不需要计入团队记忆，本次会话无关。
这句很重要。团队记忆是全组每个人每次开工都要读一遍的东西，塞进没用的内容，等于让所有人每天都多读一遍废话。

收工/wrap-up　每轮聊完跑一次：他会自动整理出交接单、把该记的记进团队记忆、再给你下一轮能直接粘贴的开场白。

验收 · 再确认一遍

对一下目标任务完成后请二次确认：我的目标达成了吗？部署成功了吗？

分清三种情况请把结论分成三种说：已经验证通过 / 验证下来是不行的 / 我没验成（说清为什么没验成）。
最怕的不是“不行”，是把“我没查到”说成“没这回事”。提前要求他分成三种说，能挡掉大部分假消息。

遇到要开权限的：比如 OpenRouter 的密钥、Fly worker 的令牌（都是让程序能调用外部服务的通行证），这些是找 PM 统一发的。别自己找一个凑合的填上，更不要把这类密钥贴进聊天框或者写进代码里——贴出来就等于泄露了，只能整个换掉。

三、五招提效（以及各自什么时候不好使）

1. 让他多开几个分身一起干

一句话就行：“这个任务如果能拆开，请派多个 agent 并行处理。”

什么时候管用：活能切成几块、几块之间谁也不等谁。比如同时在好几个地方翻资料、从几个不同角度检查同一份改动、同时核实几件不相干的事。

什么时候反而更慢：一步要等上一步结果的活（改完才能测、测完才能再改）。硬拆开只会多花钱，而且每个分身看不见别的分身在干嘛，最后还得有人来合。

2. 用 Codex 接着 Claude 的对话干

Codex 能把你电脑上 Claude 的历史对话读进来，接着上次的进度继续干，不用再从头讲一遍来龙去脉。

这不是理论，本机已经在用了：Codex 里已经存进来 181 段 Claude 的历史对话，其中 175 段是 Akke 项目的。

Codex 自己也有接着聊的命令：codex resume 接回上一次那段对话，codex fork 从某一段里分出一条新的继续聊。

3. 空闲或晚上，挂个 /goal

给他一个目标，他会一直干到目标达成才停；中途想收工会被判官打回去接着干。适合那种“有明确干完标志”的活（修到全绿、跑到剩 0 条）。

如果只是想每隔一会儿看一眼（比如每 20 分钟看看检查跑完没），用的是另一个命令 /loop。

两个坑，挂之前先看第六节。一是关掉窗口它就停了，没法真的替你过夜；二是它判断“算不算干完”的方式跟你想的不一样。

4. 让他自己去点屏幕

完全不想自己动手的时候，可以让 AI 直接操作界面去点。本机接的是浏览器：它能自己开网页、点按钮、填表单、看页面报错。

实测挺慢的——每点一下都要先截图、认清楚、再点，比直接敲命令慢一大截。当成偶尔用一次的备用招，别当主力。

另外别让它去点那种会弹确认框的按钮（比如“删除”）。浏览器弹出来的框会把它整个卡住，动不了了。

5. /model 换个脑子

难活换聪明的，简单活换快的。聊天中间随时能换，不用重开窗口。

加分项：让他先翻翻以前的结论

很多办法其实团队早就试过、也早就否掉了。开口前加一句“先翻一下 docs/claude-memory/ 里有没有相关的结论”，能省掉一整轮已经被否决过的讨论。

四、对话怎么管，别让它拖慢你

接回上次那段对话

/resume　挑一段之前的对话接着聊，之前说过的他都还记得。

聊太久了怎么办

新开一个窗口，把上一段对话的标题（或者结论）发给他，让他先读一遍上次的进度，然后把旧窗口关掉。
聊得越久，他每次回答前要重读的东西就越多，越慢也越费钱。及时换新窗口，省下来的时间很可观。

一个文件夹只开一个窗口

同一个文件夹开两个窗口，两边会抢着改同一批文件，你改到一半的东西可能被另一边打包提交走。这件事已经自动处理了：开第二个窗口时，它会自己躲到一份单独复制出来的文件夹里去干活。看到它说要这么做，让它做就是了。

五、记忆记到哪：三个抽屉别放混

抽屉放什么怎么跟他说
我自己的
CLAUDE.md		 你个人的习惯和偏好：说中文、讲大白话、别一上来就动手。只影响你自己。 把这个习惯记进 CLAUDE.md，计入我的个人记忆。
全组共用的
docs/claude-memory/		 项目上的结论和教训：这个办法为什么被否掉了、这个坑长什么样、这个数字到底怎么算的。会跟着代码同步给全组。 把这条计入团队 memory。
不用记 跟项目没关系的、只在这一轮有用的临时信息。 这段跟项目无关，不需要计入团队记忆，本次会话无关。
为什么要分清：全组共用的那个抽屉，是每个人每次开工都会读一遍的。往里塞没用的东西，等于让所有人每天都多读一遍废话。所以宁可多说一句“这条不用记”。

六、四个容易想错的地方

这一节专门用来纠偏。下面每一条，都是听着挺有道理、实际会让你白等一晚上或者白高兴一场的说法。

① /goal 挂着过夜？关掉窗口它就停了

/goal 和 /loop 都是活在你当前这个对话窗口里的。你合上电脑、关掉窗口，它们就一起没了——不是在云上替你跑。

真要过夜跑、或者每天定点自动跑，用 /schedule，那个才是关了电脑还在跑的。

第二个坑更隐蔽。/goal 判断“算不算干完”，是靠另一个 AI 当判官，而这个判官只看你们的聊天记录——它看不到你电脑里的文件，也打不开网页。所以：

  • ❌ 写“确认文件已经生成了”“页面能正常打开” → 判官永远看不到，只会一直把他打回去重做，你等一晚上也等不到结束。
  • ✅ 写“跑 <某条命令>，结果里要出现 <某个具体内容>；最后必须把原始结果贴出来，不贴不算完成”。

另外别在目标里写“准确”“流畅”“尽量多修一点”这种词，判官没法判，只会来回拉锯。

完整写法（有模板和正反例子）在项目里：.claude/skills/loop-goal-spec/SKILL.md。挂之前让 AI 先去读一遍。

② “自动交上去”不等于“已经合并”，更不等于“已经上线”

这是三件事，每一步都可能停住：

  1. 交上去——现在主线已经不让直接改了（系统会直接拒），所有改动都得先交上去等审，连纯文档也一样。
  2. 合并——影响小的改动，仓库里有个机器人会在检查全部通过后自动帮你合。但碰到要紧的地方绝不自动合：改到 AI 模型设置、定时任务、数据库结构、权限、自动检查流程这几类，机器人只会提醒你一声，得你自己盯着点合并。
  3. 上线——合进主线之后才开始往线上推。“显示已合并”不等于“线上已经是新版本”，还得去打开真实页面看一眼才算数。

所以干完之后那句“我的目标达成了吗？部署成功了吗？”要分开问，而且要他拿出线上的截图或返回结果，不是代码库的截图。

③ 分身不是开得越多越好

每多开一个分身就多花一份钱，而且它们互相看不见对方在干什么。本来就要一步接一步做的活，硬拆开只会更慢、更贵，几个分身给出的说法还对不上。

判断标准很简单：这几块活能不能同时开工、谁也不用等谁？能，就拆；不能，就别拆。

④ --dangerously-skip-permissions 是真的会跳过确认

这串英文里的 dangerously 就是“危险地”，不是吓唬人的。加上它之后，AI 删文件、改配置、跑脚本都不会再问你一句。

怎么用才安全：只在 Akke 这种自己的项目文件夹里加；碰到数据库、线上环境、给客户发消息这类做了就收不回来的事，哪怕加了这串，也要自己盯着他每一步在干嘛，别开着就去忙别的。

七、收工清单

  • 再确认一遍：我的目标达成了吗？真的上线了吗？——要他拿证据，不接受“应该没问题”。
  • 跑一下 /wrap-up：他会出一张交接单（做了什么 / 效果怎么样 / 什么没做 / 为什么没做 / 学到了什么）。
  • 值得留下来的经验，明确说一句“记进团队 memory”；跟项目无关的，明确说一句“这条不用记”。
  • 如果有改动交上去了，把网址、验证结果、还没干完的部分一起写进交接单，别让下一个人猜。
  • 今天踩的坑值得留个档 → “帮我生成一个文档，把今天遇到的问题和根本原因进行总结，提交到 upio 的 html 页面”。
一句话记住：开工先拉最新，动手前先要方案，卡住了让他找真正的原因，干完了要他拿证据，收工时把经验留下来。
