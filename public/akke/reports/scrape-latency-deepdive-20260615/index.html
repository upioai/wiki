Leg A · 抖音侧上架（~几秒，不可控）

用户点「发送」后，这条评论要先在抖音自己的系统里能被 API 查到。我们管不着，但很快——用最快的端到端样本（1 分钟）倒推，这段只占几秒。

Leg B · 入队等待 ＝「等到有人来抓这条视频」（大头）

"抓这条视频" = worker（干抓取活的程序）去这条视频底下把评论捞一遍。它什么时候被抓到，完全由我们的抓取机制决定 —— 有两条路，下面讲全。

B-3 · 视频快车道机制（快路）

由同事 tuan19960216 在 2026-06-14 11:03 上线（PR #340）。藏在 tier-1 的闹钟里，每 2 分钟独立跑一轮（下文把「闹钟响一次 / 跑一轮」叫「1 个 tick」，现 cron */3 = 每 3 分钟一个 tick）：

  • 按「近 48 小时内、被我们 ≤60 分钟新鲜抓到的评论条数」给视频排序，取 top 100；
  • 每 2 分钟重算一次，名单动态换血——评论不断进出 48 小时窗口，这 100 条一直在变；
  • 命中就单独复扫（pri=1），不分 tier、不受 30 分钟号节流约束；
  • "≤60 分钟"指评论者发出该评论的时刻——即「我们是否在它冒出 1 小时内抓到」。这是上车的门槛。
  • 实测这条歆笛视频只有 18% 的轮次被选中（十次轮到两次），所以哪怕在快车道上，Leg B 也还有几分钟等待。

B-4 · 成因：慢路 97% 是「冷视频鸡生蛋」

先把「冷视频」讲具体（本报告操作口径）：判定法＝一条评论走慢路时，看它所在的那条视频「前 24h 有没有被快车道抓过」——没上过 = 冷视频。通俗说＝这条视频不在「快车道高频复扫名单」里，它底下的新评论只能等「整号轮抓」几十分钟~几小时扫一遍才被发现，永远够不上「评论冒出 ≤60min 内被新鲜抓到」的上车门槛（= 鸡生蛋）。
会冷的视频有三类：① 老视频（发布几天/几周，掉出号主页最近 ≤20 条，整号活也不再抓它）；② 不活跃号底下的视频（号本身轮抓间隔长）；③ tier-0 号的视频（每小时才轮一次、还常被饿死到 ≥7h）。
反面「热视频」＝正在被快车道高频复扫的视频（近 48h 有过「≤60min 新鲜抓到」的评论、在名单上）。

Leg C · 队列排队 ＝ 活派出去后，为什么还要排 4.6 分钟（大头）

就算 Leg B 把活派进了队列，worker 也不是立刻抓。实测中位 276 秒、p99 327 秒。机制如下：

  • worker 领活规则 = 优先级升序 + 同级先到先得。活分快道（pri=1：tier-1 整号 + 视频快车道）和慢道（pri=5：tier-0 整号 + lead 资料）。pri=1 永远插在 pri=5 前面。
  • 视频快车道每 2 分钟灌一大批 pri=1 活，此刻队列里站着上百条 pri=1 积压，你这条新活再急也得排在它们后面。
  • 又慢又重的「整号活」（＝抓一整个号：去主页捞 ≤20 条视频再逐条抓，中位 23 秒、最慢 211 秒）和「单视频快活」（＝只抓一条指定视频底下的评论、增量，约 5 秒）挤在同一条 pri=1 队——前面卡一个慢的，后面快的全等。
  • worker 实测 8 个并发槽、~72 活/分钟、~270 整号活/小时；pri=1 到达速率 ≈ 服务速率 → 始终积压上百条，每条新活平均等 ~4.6 分钟。
✅ 已坐实（2026-06-15 23:00 实查 worker 活体）：不是 slot 闲置。/queue/stats 报 pending=2 是假象（只数最近 1000 条窗口），真实 pending=640（pri1 103 / pri5 537）；8 槽真忙（claim 78/分、running 常态 8 个无僵尸）。Leg C 的真因 = pri=1 队列常年积压 ~100 条，新活按"同级先到先得"排在后面——实测一个 23:06:53 的 tick 灌的批次，全等到 ~23:11:35 才被领走（285 秒）。排不空因为：① 快车道昼夜不停每 2 分钟灌一批（深夜 313s ≈ 午间 276s，无低峰）；② 慢整号活（2+ 分钟）混在同条 pri=1 道占槽；③ 还有 poison 活（一条 38 小时前的 pri1 整号活重试到顶卡死、永远 pending）。

Leg D / E · 抓取 + 写库（秒级）

轮到后，worker 调抖音评论 API：抖音新评论排最前，增量抓只取首页、整页无新即早停，通常 1 个请求 ~5 秒搞定；写库亚秒。所以抓取本身不慢，慢的全在 B、C 两段等待。

  • 快慢分道（Leg C①）= 让快活先走：原来"摘一棵树（5 秒）"和"巡整片园子（几分钟）"排同一个队，前面排个巡园的、后面摘单棵的全干等；现在把巡园慢活降一档，让摘单棵的快活先走。
  • 空跑退避（Leg C②）= 空手就少去：一棵树连去 3 次都空手（没新果），就拉长下次去它的间隔（9→18→30 分钟），省得白跑；它一旦又结新果立刻恢复勤去。
  • 注入去重（已做 ✓ #381，2026-06-17）= 别每一轮都重复派去同一棵：破鸡生蛋原来每个 tick 都把那几棵"刚结过熟果"的树重新塞名单、重新派人——可果早摘光了，同一棵被反复派 80 次全空手。#381 让这些树也走"空手就少去"的退避（去掉原本对注入的豁免），注入次数 80→按需。但随后又发现：那些"空手"里其实有 33% 是假空手（树后面那枝新结的果没绕到就走了 = 早停 bug），真有果、还含 lead——这部分得靠修早停 bug（PR #413）才摘得回，退避只是别白跑。

B · Leg B 破鸡生蛋（#363）：治「冷视频上的高意向评论，第一条几乎必慢」

先回顾：Leg B = 「派活」那段路 —— 评论已经存在了，但系统迟迟没派出一个活去抓它。本段治的就是冷视频上这个"迟迟没人派活"。

【问题】一条视频要先进「快车道」才会被频繁单独复扫；而进快车道的门槛是——它的评论得在 60 分钟内被我们新鲜抓到过一次。可冷视频（老视频 / 不活跃号底下的）只能等慢整号活几十分钟~几小时扫一遍，永远赶不上 60 分钟 → 永远进不了快车道 → 它上面新冒的高意向评论第一条几乎必慢。死循环：要被快抓得先进快车道，要进快车道得先被快抓（「鸡生蛋」）。

↑ 拗口的词跟一下：「快车道」＝每 2~3 分钟挑一批「正在冒新评论的 top 100 视频」单独复扫的机制（详见 B-3）；「60 分钟门槛」＝只有被我们在评论冒出 1 小时内抓到过的视频才算"够格"上这条快车道。

【改动】不再死等门槛。只要一条视频近 6 小时内冒过高/中意向评论，就直接把它塞进快车道、还插在最前面（pri=0）优先抓——「破鸡生蛋」= 直接抱它上车，不等它自己够 60 分钟的格。

这个「6 小时」是怎么定的、要不要改？

6h 的由来：注入要圈"刚冒过高/中意向的视频"，6h 是个"近期"窗口——够宽，半夜冒的意向到白天还能补上。

实测发现它的毛病是"太长"：高意向视频天生是老·常青视频（实查"曾产高意向、还活着"的视频全部 >4 天龄）。一条视频 6h 内只要有过一条高意向评论，就被每个 tick 重选注入一次 → 6h ≈ 120–180 个 tick → 同一条被反复抓 80 次、100% 抓 0 新。

但核心病不在 6h 长短，在"每个 tick 都重注一遍"。缩到 2h 只是按比例砍空跑（治标）；根治靠"注入去重"（同一视频注入过就别每 tick 重派）——这已由 #381 落地（A0 清单里那条）。所以 6h 维持不动。

去重会不会把我们关注的视频也抓慢？不会——退避是"自适应"，不是"抓一次就停"。退避按【每条视频】记账（empty_streak）：连抓 3 次都 0 新才开始拉长间隔（9→18→30 分钟），一冒新评论立刻清零、恢复每 tick 勤抓。所以真在不断冒评论的活跃视频永远不空手、永不退避、频率不降；被降频的只有"冒过一波后安静下来"的（实测那反复 80 次正是这批，100% 空手）——对它们降频一条 lead 不少抓、只省白跑。后续旋钮：可给高意向视频设更短的退避上限（如封顶 10 分钟）。

C · Leg C 快慢分道 + 空跑退避（#363 + #366）：治「活派进队列后排太久 + 反复空扫」

先回顾：Leg C = 「排队执行」那段路 —— 活已经派进队列了，等 worker 领走真正去抓。本段治的就是这个排队：别让慢活堵快活、别反复空扫白占位。

【问题①·排队】活派进队列后 worker 一个个领。原来慢整号活（23~211 秒）和单视频快活（5 秒）挤在同一条号牌道（都 pri=1）——前面卡一个慢整号，后面快活全得干等，实测排队中位 ~4.6 分钟。

【改动① · #363 快慢分道】把慢整号活降一档（pri 1→3），让 5 秒的快活先走、别被慢活堵。实测典型延迟 median −67%（见 D）；但极端尾巴 p99 反被注入洪水拖坏 → 已由 #381「注入去重」补上（见下方改动③）。

【问题②·空扫】很多视频被反复复扫却抓不到新评论（实测近 24h 复扫 88,455 条、77% 抓 0 新），白占 pri=1 的位置、加重排队。

「空扫」到底算 Leg B 还是 Leg C 的问题？—— 两个来源，分开治：
· 来源一（C 自己的）：常规快道把"早冒过评论、现在安静了"的视频反复复扫 → 抓 0 新。这是本段 #366 退避治的。
· 来源二（B 制造的）：破鸡生蛋的注入洪水每 tick 重派同一批视频（见 D + A0 #381）→ 也是空扫，但根在 Leg B。
所以"空扫"是症状、根有两个：C 的常规复扫（#366 治）+ B 的注入重复（#381 治）。

【改动② · #366 空跑退避】一条视频连抓 3 次都 0 条新评论，就把它下次复扫往后推（9→18→30 分钟封顶）；一旦又冒新评论立刻清零、恢复勤抓。

↑ 拗口的词跟一下：「退避」＝越扫越没货就越少去扫它、省得空跑；靠 videos 表新加两列记账：empty_streak=连续抓 0 新几次、next_fast_lane_at=推到几点才允许再进快车道。
9→18→30 这三个数怎么来的？= 指数退避（exponential backoff，标准重试算法）。每多空手一次、间隔翻一倍（9×2ⁿ：9→18→30，第三步本该 36 被 30 封顶）。
· 9 分钟起步：比 3 个 tick（≈9 分）略长——给视频留点时间真冒出新评论再去，不浪费。
· 30 分钟封顶：再久就交给"巡整片园子"的全量轮兜底，快道不必死磕一棵安静的树。
⚠️ 诚实说：指数退避是标准模式，但 9 / 30 这俩具体值是工程"按 tick 节奏 + 全量轮兜底周期"拍的默认值，不是理论推导的最优解（env 可调 FAST_LANE_BACKOFF_BASE_MIN=9 / _CAP_MIN=30，嫌慢调小、嫌费调大）。

这座注入洪水到底是什么（部署后 8.5h 切片实测，06-16 04:00–12:25）

A · 一处硬错：worker 早就不是「一批一起回」了

错的说法：「_run_job 用 asyncio.gather 一次并发抢 3 个活，一批一起返回；只要 3 个执行槽被慢整号活占满，新抢回来的快活就在槽外干等」。
实际代码（worker/services/queue.py）：早已改成 task-per-slot（每槽独立循环）——_poller_loop 起 N 个互不相干的 _slot_worker，每个槽自己跑「抢 1 个 → 干完 → 再抢 1 个」，没有"一批一起回"的栅栏。_run_job 只跑一个活，外面套 asyncio.wait_for(deadline=1500s) 兜死活。gather 只出现在一个整号活内部并发抓它那几条视频时（信号量=2）。

为什么这个订正重要：旧 gather 架构下，"一个慢活拖死整批"是真的（p99 曾到 1253s）——这正是当时改架构的原因。但现在不成立了：一个慢整号活只占它自己那一个槽，兄弟槽照样不停抢快活。真正会堵，只发生在「所有槽同时被慢整号活占满」那一刻，新来的快活才得等空槽。

所以「堵在 Leg C」的真因要精确说：不是"慢活冻结整批"，而是 ① pri=1 快道里常年积压上百条（快车道每 tick 灌一大批，新活按同级先到先得排后面）＋ ② 慢整号活混在同条道里、零星占满槽。#363 的「快慢分道」（tier-1 整号 pri 1→3）就是对②的根治——把慢活降到快活之下，保证只要有槽空出来永远先领快活，把"全槽被慢活占满"的概率压到最低。订正后结论不变（仍该分道），但机制叙事得对，别再说"gather 一批一起冻住"。

E · 「收 cold-intent 口径」深挖：数据 → 人话 → 追问 → 方案（2026-06-22）

承接 ⑩-C/D 那条「cold-intent 99% 空跑、钓点在枯、口径要收」。这一节把它挖到能动手：先用数据证明空跑长什么样，再用钓鱼比方把机制讲透，回答一个关键追问——这么改会不会把高/中意向抓漏 or 抓慢，最后给带护栏的退避方案（已出交接、待开 PR）。
读这章前先立 4 个词（之前没定义、最容易把人绕晕）：
· 钓点 = 一条视频。cold-intent 选谁回扫，只看"这条视频近 14 天还冒过高/中意向评论"——不是号源，也跟 tier0 / tier1 无关（tier 是号源的属性，是另一条轴）。
· 「个」= 视频数，「次」= 扫描动作数。一条视频（1 个）会被反复扫很多次：1070 个钓点一共被甩了 13074 次。下表左右单位不同就是这个意思。
· 退避 ≠ cold-intent。cold-intent 是"低频回扫老视频"这件事本身（早就有）；退避是 2026-06-22 才加在它上面的一层省钱规则——专门拉长"老是空手"的钓点的回扫间隔。所以下文「退避前」= 还没装这层时、所有钓点死活都固定 2h 扫一遍。
· 名字坑：cold-intent 的 cold 指"视频凉了"（老视频、掉出 48h 热窗口），不是"意向凉"——它盯的恰恰是冒过高/中意向的视频。英文名跟它干的事不透明对应，知道这点才不会读反。

② 人话：用「钓鱼」把机制讲透（苏格拉底式自问）

  • cold-intent 在干嘛？ 一个钓鱼人，手上一张老钓点清单（近 14d 冒过"鱼"＝高/中意向评论的视频），挨个去甩一竿（回扫看有没有新评论），每个钓点隔 2 小时再去。它专钓老视频——新热视频快车道管，老视频没人管，全靠他。
  • 为什么 97% 空竿？ 89% 的钓点其实早没鱼了，可他还在那儿一遍遍甩（683 个死钓点每个甩 10+ 竿）。浪费不是平摊的，是死钓点在被反复空甩。
  • 最直接的办法？ 哪个钓点连着几竿没鱼，就少去那儿：第一次空→2h 后再来，又空→4h，再空→8h…越空越懒得去。这就是"退避"。
  • 万一冷落的钓点又来鱼了？ 铁律：只要某竿上了鱼，立刻恢复"勤去"（2h 一次）。退避只惩罚"一直没鱼"的，不耽误"刚冒头"的。
  • 省下的力气去哪？ ① pri=3 道松绑→同道 tier-1 整号排更快（顺带回应内部报告对"整号"的关切）；② 不耗在死钓点→活钓点照看更勤→真有鱼处抓更快。
    （这里的 tier-1 是排队优先级那条轴——cold-intent 跟它共用 pri=3 这条道；别跟"cold-intent 扫谁"搞混，它扫的永远是视频、不挑号源 tier。）

③ 追问：现在的方法，会不会让高/中意向抓不到 or 抓得慢？

抓不到？抓得慢？
现在（退避前）对它管的钓点基本不会——1378 钓点每 2h 该扫一遍 = 需 689 竿/h，产能 900 竿/h，够用、不会被 300 上限漏掉有 ~2h 地板：每钓点 2h 才回去一次，最坏等 ~2h（+ 排队 57min）
真正"抓不到"的另一类一条全新冷视频还没冒过意向、没进 14d 清单 → cold-intent 不认识它，只能等「整号轮抓」扫到。但这是整号的活、非 cold-intent 的锅——它天生是"你先冒过一次鱼、我才把你列进钓点"的事后补扫。
退避后的新风险会让"先死后活"的钓点第一条新鱼更慢：一个退避到"8h 一去"的钓点突然来高意向，最坏等 8h 才被发现——比现在的 2h 还慢；若封顶设 24h 更糟，等于亲手拉长慢尾、跟目标反着来。
所以这一追问直接逼出两道护栏（保高/中意向不被退避误伤）：
· 退避封顶压到 6h（不是 24h）：最坏一个复活钓点等 6h，正好卡慢尾边界、不会比现状更糟。
· 高意向钓点给地板 2h：曾冒过高意向（非仅中意向）的钓点封顶压到 ~2h（≈现状、几乎不受退避影响）；只有"光中意向"的钓点才允许退避到 6h。
净效果：高意向几乎不受影响（地板 2h≈现状），中意向最坏 6h（≤现有慢尾），同时砍掉大头浪费。退避治的是"在死钓点上空耗"，不拿"误了真鱼"去换。
