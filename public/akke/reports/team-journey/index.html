⑥ 零星（夏夏）云电脑上线复盘 · Good / Bad Case 时间线

这一段是人工归档的一次性复盘（不随上面的日期切换刷新），目的是把零星这台云电脑从装好到现在出过的问题、为什么出、怎么解决讲清楚，让不懂技术的人也能看明白，并沉淀「做得好的」和「该优化的」。点标题可折叠。
先用一句话说清这是什么：「云电脑」是一台开在云端、24 小时不关机的 Windows 电脑，上面登录着夏夏的抖音号；我们写了个小程序（下文叫 agent / 派单）让它自动「搜到目标用户 → 打开对方主页 → 发一条私信」，不用人盯着手机一条条发。目标是每天自动发约 30 条私信。下面按时间线，把这台机出过的状况逐个拆开。

  1. 6/15 前后BAD CASE第一次在这台机跑就「整批找错人」
    现象用这台机跑反向评论（楼中回复）时，一整批操作全发给了错的人，被系统拦下没真发出去。
    为什么抖音电脑版的界面按钮位置不是完全跟着屏幕大小等比缩放的；这台机的分辨率不是标准值，而配置里又没有按本机实测的「点哪里」坐标，程序就按默认坐标点 —— 结果点到了空白处，没点中对方头像，自然打开的是错的页面。
    怎么解决在本机跑一个测量小工具（measure_nav.py）实测每个按钮的真实位置，写进配置。教训：坐标和界面截图模板都不能跨机照抄，一台一测。
  2. 6/19GOOD CASE私信（DM）通道当天装好、当天跑通
    现象第二台云电脑装好后，私信自动发的通道当天就跑通，发出去 2 条。
    做得好从装到通当天完成，证明通道本身是好的 —— 后面的低产量是别的具体坑，不是路子不通。
  3. 6/19 晚BAD CASE连续 3 小时一条没发，屏幕「没反应」还不报错
    现象晚上起约 3 小时零产出，别的号都在正常发，就它不发，且没有任何报错，最难查。
    为什么自动发消息的小程序跑在一个手动开的黑窗口里。运维去看「怎么没发」时，鼠标在窗口里点了一下，触发了 Windows 的「快速编辑模式」把程序冻住了。程序一冻，它每隔几十秒向服务器报「我还活着」的心跳就停了；超过 5 分钟系统判它掉线，就不再给它派活，它本该领的新单全被别的号抢走 —— 全程没报错，所以像「没反应」。
    怎么解决关掉窗口的「快速编辑模式」；更稳的是让程序开机自启、在后台跑，没人会去点它。排查口诀：云电脑「没发」先看心跳还跳不跳，别先怀疑别的。
  4. 6/20BAD CASE派了 35 条只发成 4 条（三个坑叠在一起）
    现象这天给它派了 35 单，最后只发成 4 条。
    为什么① 这个抖音号连日高频搜人+发私信，被平台悄悄限流 —— 别的号搜得到的人，它搜不到，搜不到本人就发不出；② 云电脑机房里下载脚本的老网址被掐断，更新脚本失败；③ 发送脚本缺一个依赖文件，整个崩掉（14 条卡在这一步）。
    怎么解决①号冷却降频 / 重新登录刷新；②换一个机房能通的下载方式；③把脚本改成缺依赖也不崩、跳过继续（6/21 已修）。
  5. 6/21GOOD CASE分清「该修的」和「本来就无解的」，不白费力
    现象很多目标用户怎么都发不到本人。
    洞见约 38% 的用户没设抖音号、只有一串纯数字 ID，这种在搜索框根本搜不到本人 —— 这是天花板，不是 bug。
    做得好把「无解的 38%」和「该修的」分开：报达成率时分母只算「能搜到的那 62%」，否则永远像没达标；也避免把时间浪费在「修一个修不好的东西」上。
  6. 6/22GOOD CASE用证据推翻错误判断，少走弯路
    现象曾一度以为又是「屏幕分辨率 / 坐标」问题，准备重测坐标。
    为什么不是把当天每一条拉出来看，发成功和找错人是同一晚、隔几分钟交替出现的。如果真是坐标点歪，会「每一条都同样错」，不可能这条对、那条错 —— 所以坐标是好的，真问题是「逐个用户搜不搜得到本人 + 这个号被限流」。
    做得好靠「交替出现」这个证据及时纠偏，没去重测坐标白忙一场（也顺手发现这台真实分辨率是 2940×1912，之前记录里写的 1920×1080 是错的）。
  7. 6/22 · 现状BAD CASE（仍待解）量上不去 = 在线时间太短 + 号被限流，双重夹击
    现象三天累计只发出约 8 条，目标约 90。
    为什么① agent 断断续续在线（6/22 当天 14:00–19:55 离线 6 小时），系统只在它在线时派单，离线时新鲜单全被常开的号抢走 → 派得少；② 在线时又因号被限流搜不到本人 → 发成率低（约 17%，机房标杆 79%）。
    下一步把 agent 改成后台常驻补上在线时间；号做冷却降频 / 重新登录，不行就轮换备用号。

✓ 做得好 / 值得复用

  • 身份门兜底：搜错人时系统会判「不是本人」自动跳过，3 天 0 条误发骚扰 —— 宁可不发，不发错。
  • 五台机同池对比这个分析手法：同样的单子，别的机 0 找错人、这台大批找错 → 一眼定位「是这台机/这个号的问题，不是单子的问题」。
  • 理性归因：用「成功与失败交替出现」证伪了「坐标论」，避免重测坐标白忙。
  • 把天花板量化（约 62% 可达），报数分母用对，不再「假装没达标」。

⚙ 还要优化 / 减少再犯

  • agent 一律开机自启、后台常驻，别用手动黑窗口跑 —— 根治「点一下就冻」和「离线没人派单」。
  • 新机上线先量分辨率 + 实测坐标 + 采模板，三件套缺一不可，且不准抄旧文档/别的机的值。
  • 发送号定期体检：高频搜人发私信会被限流，发现搜不到人就冷却降频、重登或轮换备用号。
  • 「没发」先看心跳：建立固定排查顺序（心跳 → 登录态 → 才轮到坐标），别一上来乱猜。
  • 路线图：让程序从评论气泡直接点进主页（绕过搜索框），可把那够不着的 38% 也接上。
