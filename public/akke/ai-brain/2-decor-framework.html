装修场景该用哪套框架

上一页（① 框架横评）把 LangGraph / Dify / n8n / CrewAI 横着比了一遍。这一页只拍一块板：全屋定制 / 装修这个具体场景，到底该不该引入新框架？这不是泛泛对比，是把决策落到 Akke 自己的代码栈、真实瓶颈和工程判据上做的一次 build-vs-buy 取舍。

§1 这一页要拍什么板

承接 ① 框架横评，本页落到装修场景做「build vs buy」拍板

① 横评回答的是「市面上哪套框架更强」。但「哪套强」≠「我们要不要用」——把通用横评结论直接套到 Akke，会把一道商业/工程取舍题误当成选型题。这一页只拍一件事：装修场景这条具体流水线，该不该为它引入一套新的编排框架。答案会决定主题4 是「移植已有代码」还是「先学一套新抽象再重搭」。

先 WHETHER，再 HOW。「选哪套框架」是 HOW，得先过「装修场景到底要不要框架」这道 WHETHER 闸。横评（HOW）回答得再漂亮，只要 WHETHER 不成立，整页 HOW 都是空转——本页的全部价值，就是把这道 WHETHER 先拍死，避免团队跳过它直接进选型。

§2 Build vs Buy 决策框架

用两条通用工程判据给场景定坐标：拓扑变更频率 × 分支复杂度

引不引框架，业界有一条可操作的判据：看流程拓扑改多勤、分支爆不爆炸。变更频繁 + 分支爆炸，才值得为「可视化改流程 / 显式状态图」付框架税；否则代码栈更省。把装修场景放进这张 2×2，落点一眼可见。

✓ 复用现有代码栈

  • 抖音侧管线已生产验证，移植即用，零学习成本
  • 确定性逻辑（60+ 硬绑信号 / 价格 clamp / RLS）原样保留
  • 改动走 PR + 单测回归，回滚路径清晰
  • 无新依赖、无框架版本锁、无供应商绑定

✗ 引入新框架

  • 先拆已验证逻辑，再用更粗抽象重接，回归风险高
  • 护城河（信号硬绑 / cost 指纹 / 多租户）塞进通用节点会被磨平
  • 解决不了真瓶颈——框架假设「你已经能发消息了」
  • 业界经验：自建 agent 6–12 月到产、TCO 超估 2–4×；框架迁移同理

§3 装修场景的 workflow 怎么落

不是搭新流程，是把抖音侧 dm-reply 管线 1:1 克隆到微信通路

WBS 主题4 接驳表写得很直白：1:1 克隆抖音侧。抖音侧三件套已在生产跑——dm_reply_drafts 四 RPC 草稿队列（migration 20260618173500）、gate.ts/adjust.ts 护栏闸、chatReply 三阶段机。微信侧要做的是把它们移植成 wechat_reply_drafts，只新增一个 store_invite 到店阶段。整条链是「搬运 + 1 个新节点」，没有一处需要新框架。

§4 不引框架，缺的几环用什么补

框架打包卖的五样能力，Akke 现有栈逐条已有承接

框架不是凭空火的，它打包了一组真实能力：可视化、回放、节点测试、人审、调度。逐条对照——这五环 Akke 已经各有实现，且多数更细。

结论很直白：框架打包卖的五样能力，Akke 已经自有对应实现。引框架是「用更粗的抽象换走更细的已有能力」——不是补短板，是降配。

三条触发线，任一长期成立再把决策拿出来重评——当前全部未触发

阈值定义 — ① 频率：触发线 = 运营/PM 需每周自改拓扑（当前月级、走 PR）；② 复杂度：触发线 = >20 并行阶段 / 动态 DAG（当前 3 阶段线性状态机）；③ 产品化：触发线 = 把「编排能力」当产品交付租户自定义（当前纯内部能力）。三条均 未触发，且都需「长期成立」，偶发一次的复杂需求不算。

复评纪律：别为一个边缘 case 提前背框架迁移债。真要触发的信号是趋势（连续数周改拓扑 / 阶段数持续膨胀 / 商业模式转向对外编排），不是某一次的临时复杂需求。主题2 商户联盟若走到「让商户自定义编排」那步，再回来看第 ③ 条。

§6 决策 + 把精力投哪

拍板：装修场景复用现有代码栈，不引新框架。省下的「选框架」精力，有两个真正卡住的地方在等它。

别在「选框架」上耗精力。把力气直接投到两处：① 主题4 微信通路 PoC——个微 vs 企微，先把「能不能合规地发出去」这道 0 号闸打通（企微方向 src/lib/wecom/ 已起步，接着干）；② 主题3 报价数据源——「降30% + 最低档」算法卡在没有可信的品类×城市×面积均价基准，缺数据不是缺框架。框架是流程稳定后的锦上添花，现在添的不是花，是迁移债。
