类似工作流方案的框架横评

把市面上主流的 agentic-workflow / LLM-app 编排框架（LangGraph、Dify、Coze、n8n）拉到同一张桌上横评，再和 Akke 自研的「采集→打分→起草→护栏→人审→发送」流水线逐维对照——回答一个常被默认跳过的问题：我们到底该不该引入一套现成框架。

结论
Akke 的编排本质已经是一条代码驱动的状态机流水线，五环（状态编排 / grounding 护栏 / 多租户隔离 / 人审闸门 / 反封号节奏）全覆盖且有单测兜底。四套主流框架解决的是「快速搭 demo」，没有一套适配 Akke 的多租户 RLS + 人审闸门 + 反封号 + grounding 硬约束——不引入，继续打磨自研栈。

§1 调研背景与方法

为什么先问「该不该」，再问「怎么搭」

这次调研起因于一个反复出现的失误模式：一提到「上工作流框架」，团队（和 fan-out 出去的 agent）会迅速收敛到「LangGraph 还是 Dify？怎么把节点连起来？」——全员在答 HOW，没人在答 WHETHER。但 Akke 不是从零起步：线上早就跑着一条多阶段的自动化管线，引入框架的真实成本是「把已经在生产、有单测、扛过封号的栈推倒重接」，不是「省下从零搭建的功夫」。

WHETHER 先于 HOW。本报告刻意把「是否引入框架」作为第一性问题，而不是默认引入后再比选型。理由是 Akke 的编排约束（多租户数据隔离、人工审核闸门、反封号节奏、反幻觉 grounding）大多是框架不提供、必须自己写的部分——这些恰恰是 Akke 已经写完的部分。框架能省的是「连线搭 demo」，省不掉硬约束。

调研对象与来源

横评聚焦四套被点名的代表框架，覆盖三种典型范式，并查准每套的：编排范式、代码级单测能力、数据驻留与合规、多租户能力、自托管 vs SaaS、社区规模。关键事实均来自官方文档 / 官方仓库，不臆造版本号或 benchmark：

§4 Akke 现状盘点：已有的编排引擎

不是「要不要建工作流」，而是「已经有一条工作流，要不要换地基」

Akke 线上就跑着一条多阶段、带人审闸门的 agentic workflow。src/lib/dm-reply/run.ts 本身就是一段编排逻辑：找待回对话 → chatReply 生成草稿 → gateDraft 置信度判定 → 通过则 approved、不过则 needs_human 转人工——这就是一条带 human-in-the-loop 的状态机，和 LangGraph 的 interrupt() 模式同构，只是用确定性代码而非框架 DSL 实现。

引证：run.ts 注释明确「护栏命中不再 adjust 自动改写直发，改为转人工——一拍错就丢单」。整条管线由 vercel.json 49 条 cron 触发，dispatch/shared.ts 收敛三通道（DM / RC / 二触）的 claim + backlog + 23505 去重原语。

把这条管线拆成「任何编排方案都必须覆盖的五环」，逐环对照 Akke 的实现——五环全部命中，且大多有单测：

编排五环Akke 现有实现仓库引证
① 状态编排cron 触发 + 代码状态机（pending → approved / needs_human → sent），三派单通道共享原语run.ts dispatch/shared.ts vercel.json
② grounding 护栏60+ 确定性信号后置硬绑（地域 / 价格 / 微信 / 捏造经历）+ tool-call 泄漏清理，反幻觉llm.ts llm/signals.ts · sanitize.ts
③ 多租户隔离Supabase RLS tenant_scope 按 accessible_org_ids() 行级隔离 + 每路由 org 守卫011_multitenancy_rls.sql lib/auth/*
④ 人审闸门gateDraft 置信度门：不过转 needs_human，绝不自动发废话；有 vitest 回归dm-reply/gate.ts gate.test.ts

关键观察。这五环里，第②③④⑤环（grounding / RLS / 人审 / 反封号）没有任何框架开箱提供——它们是 Akke 业务特有的、必须自己写的部分，而 Akke 已经写完并在跑。框架能替换的只有第①环（状态编排骨架），而那恰恰是成本最低、风险最小的一环。

§5 逐框架深读

每套框架的适用场景（✓）vs 为何不适配 Akke（✗）

LangGraph — 范式最契合，但只给骨架 docs.langchain.com langgraph GitHub

把 agent 建模为有向图：节点是函数、边决定流转，typed state 贯穿全图，支持环 / 分支 / 条件。随 v1.0（2025 末发布）成熟，提供 checkpointing + 时间旅行、interrupt() 人审中断、LangGraph Studio 可视化调试器（2026 GA），MIT 许可，30k+ ★，用于 Klarna / Uber / LinkedIn / Replit 生产。

✓ 适用场景

  • 从零搭多 agent、长任务、需要显式状态机控制的项目
  • 代码级可测（纯 Python 节点）、自托管、合规可控
  • interrupt() 人审模式与 Akke gate 同构

✗ 为何不适配 Akke

  • 只给状态机骨架——Akke 缺的是 grounding / RLS / 反封号，全不提供 见图2 矩阵
  • 引入 = 把已在产、有单测的 run.ts / gate.ts 推倒重接，纯增成本
  • 对抖音封号、status_code 验真零适配

Dify — 可视化搭 LLM-app 之王，但画布即不可测 dify GitHub 138k★ dify.ai

开源 LLM 应用平台：无限拖拽画布连节点（模型 / RAG / 条件 / 代码块），自带 RAG 流水线、Agent（Function Calling / ReAct）、模型管理、可观测。自托管社区版含多租户工作区 + RBAC，永久免费，138k+ ★（2026-04）、100 万+ 部署应用。

✓ 适用场景

  • 快速给业务方搭可演示的 RAG / 客服 bot demo
  • 自托管 + 多租户工作区，合规优于纯 SaaS
  • 非工程团队也能连线

✗ 为何不适配 Akke

  • 可视化画布无法做代码级单测——Akke 的 gate.test.ts / llm.test.ts 回归网会丢
  • 工作区多租户 ≠ Postgres 行级 RLS，Akke 数据隔离更细
  • 60+ 确定性后置信号硬绑塞进画布节点反而更脆

Coze（扣子）— 门槛最低，合规一票否决 coze.cn 人人都是产品经理 腾讯新闻

字节跳动旗下 AI Bot / Agent 平台，插件生态 + 工作流引擎 + 长短期记忆全托管，零基础可搭。2025-07 官宣开源，但默认形态是托管 SaaS：数据存于 Coze 云服务器；业内评测明确指出医疗 / 金融等高隐私场景应改用可本地部署的 Dify。

✓ 适用场景

  • 个人 / 轻量团队零代码做 bot，上手最快
  • 背靠字节插件生态，中文场景集成多

✗ 为何不适配 Akke

  • 数据驻留字节云、可控性最差——Akke 多租户客户数据不能托管第三方
  • 把核心获客资产 + 话术 + 客户画像交给字节，竞业风险
  • 无代码可测、无法接 Akke 的 RLS / status_code 验真

n8n — 跨 SaaS 粘合强，agent 推理弱 n8n-io/n8n GitHub

fair-code（Sustainable Use License，禁止转售为托管服务）的自动化引擎，400+ 集成节点，2026 补齐原生 AI（OpenAI / Anthropic / Gemini / DeepSeek 等 12+ 提供商）与 MCP Server / Client 节点。社区版自托管免费、无工作流数量上限。

✓ 适用场景

  • 跨 SaaS / webhook / 数据库的运营粘合自动化
  • 自托管 + fair-code，合规尚可
  • 可作 Akke 外围胶水（如告警分发），非核心编排

✗ 为何不适配 Akke

  • 定位通用自动化，非 LLM 推理 / grounding 引擎
  • 节点工作流难做严肃单测；行级多租户缺失
  • 许可证禁止「转售为托管服务」，多租户 SaaS 形态需法务确认

四套框架引入 Akke 核心编排的净收益普遍为 lo：它们替换的是成本最低的「状态机骨架」一环，却要付出推倒重接、丢失 gate.test.ts / llm.test.ts 回归网、grounding 信号迁移变脆的代价。结论 = 核心编排不引入框架，维持自研栈。唯一有限的例外是 n8n 可作外围运营胶水（告警 / 报表分发），但不进核心链路。

这不是 NIH（非我所创）情绪。判据是结构性的：Akke 的差异化价值（grounding 护栏 + 多租户 RLS + 反封号 + 人审）全在框架盲区，框架只能替换通用骨架。在「自己已写完且有单测」对「推倒重接换更弱的可测性」之间，维持现状是更优解。

§7 何时才需要重新评估

把结论钉在触发条件上，而不是「永远不引入」

「不引入」有有效期。出现以下任一信号，应重开本横评：

触发线含义为何此时框架划算
① 运营自改编排拓扑 ≥ 每周非工程同事频繁要求增删流程节点 / 改分支可视化画布（Dify）让运营自助改图，省工程介入
② 分支爆炸 > 20 条并行状态机分支数超出代码可维护阈值LangGraph 的图可视化 + 时间旅行调试开始回本
③ 编排本身作为产品交付租户把「让客户自定义工作流」当卖点交付需要给租户一个可视化编排器，自研 UI 成本 > 接框架
在此之前。Akke 的编排复杂度仍在「一条主线 + 三派单通道」量级，远未触线。投入应放在 grounding 精度、反封号存活率、时效压缩——而非换地基。
