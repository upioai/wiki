给用户建模：复用现有，别另起炉灶

怎么对单个客户建模——判断他在哪个阶段、记住他说过什么、给他专属物料？关键问题不是"用什么新方案"，而是"Akke 现有栈已经覆盖了多少"。

结论
复用并扩展现有 memory.ts + 阶段机 + conversation_examples 复用。三块能力已两块半落地，缺口是窄的增量，不是空白。地基已浇好且在生产跑，任务4 是加房间不是重打地基。

盘点 Akke 已有的三件套

决策：复用而非另起

三块能力的数据载体都已就位，没有从零搭一套用户模型的理由。

数据载体已就位
conversations.customer_profile JSONB、conversations.stage、conversation_examples——存阶段、存记忆、存示例的三张表都在生产里跑着。
另起炉灶 = 重复劳动
重写一遍还要重做多租户 RLS 隔离——memory.ts 已踩过"null org 不能 fall-through 跨租户读"的坑，新方案要把这个坑再趟一次。
已进主路径，非 demo
阶段机 + 记忆已接进生产 chatReply 主链路，每条回复都在用，不是放在旁边的实验件。
判断：地基（阶段 + 跨会话记忆 + org 隔离）已浇好且经过生产验证。在它之上加增量，比另搭一套"更全的用户模型"成本低一个量级，且不用重蹈隔离覆辙。

缺口清单（增量补，不推倒）

承认缺口，但每个缺口都是窄增量，挂在现有地基的下游，不需要推倒重来。

  1. 优先级低 记忆浅合并、无字段级溯源——memory.ts 注释自陈"which key came from which conv 需 schema change"。要等到必须解释"这条物料为什么推给他"时再补 provenance，现在不补。
  2. 这是正确取舍 记忆只存结构化 customer_profile、不回放历史原文——刻意防 token 爆炸 + 串味。别为"更全记忆"去回放原文，那是退步不是进步。
  3. 真缺口 专属物料库（主题5）——这是真正的空白，但应建成阶段机下游，用已有 stage + customer_profile 当检索键，不另造一套用户模型。
  4. 可下沉 阶段流转目前靠 LLM 分类、无确定性转移规则——有确定性信号（已留微信 → decision、已邀约到店 → store_invite）的部分下沉到代码，省 token 更稳。

一句话收口

收口：用户建模的地基（阶段 + 跨会话记忆 + org 隔离）已浇好且在生产跑；任务4 是在地基上加房间（专属物料匹配 + 阶段确定性流转），不是重新打地基。
