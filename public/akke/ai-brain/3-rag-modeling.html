RAG 向量库给行业建模？先验证再决定

要不要上 pgvector / RAG，把「装修行业节奏 + 常见问题」做成知识库喂给 LLM？这是个典型的 HOW，但先得回答 WHETHER：RAG 到底能覆盖几成真实问题。

结论
现阶段不上 先验证。全屋定制约 80% 是订单特定问题（答案在 ERP 里），RAG 的天花板 ≈ 20%；先做一个半天能跑完的验证实验，用数字拍板，别先上工程。

先踩刹车：这是 HOW，但 WHETHER 还没回答

WHETHER 先行 —— RAG 优化的是「通用问题答得准不准」：把行业知识切块、做向量检索、按相关性挑最相关的几条喂模型。但 Akke 真实对话里 80% 的问题压根不是通用问题——「我家这单进度到哪了」「尾款还差多少」「上次定的款式能改吗」，这些答案不在任何知识库，在客户那张订单里。给一道根本不存在于知识库的题写更好的答案，是在优化错的东西。所以先验 WHETHER（RAG 能覆盖几成真实问题）再谈 HOW（pgvector 怎么接），顺序反了就会白烧两周工程。

为什么现阶段不上：三条硬事实

① pgvector 从未启用
两张知识表的 vector(1536) 列建表起就注释着，旁边写着「取消注释即可启用 RAG」。全仓唯一启用的 extension 是 pg_net，没有 vector。schema 早把路铺好，两年没人去取消注释 —— 说明瓶颈从来不在 schema，而在「值不值得」。

② 现有知识「rarely referenced」
代码注释自陈：V1 知识库在 ice_break / nurture 回复里「rarely referenced」。2026-04-26 团队还反向砍小注入量——每类 1-2 条 →1 条、字符 3000 →1500，因为知识块一大就稀释 persona、输出客服腔。方向是在减少知识注入，不是缺检索质量。同段注释把「Real RAG」明确列进 YAGNI。

③ 内容稀薄 + 问题订单特定
知识库内容极少（量级：十几条文档 + 十几条对话范例），全量塞进 1500 字都装得下——RAG「按相关性裁剪」的价值 ≈ 0，没有海量内容需要检索。而真实高频问题（进度 / 尾款 / 款式改动）答案在 ERP / 订单系统，不在知识库。综合算下来 RAG 能覆盖的真实问题顶天 ≈ 20%。
knowledge_documents / conversation_examples

该做的不是上 pgvector，是先做最小验证实验

不要凭直觉拍「20%」，用一个半天能跑完的实验把这个数测出来，再决定。

最小验证实验 · 1 人 1 天
  1. 抽 1 个真实 org，拉它近 1 个月的聊天记录（conversations + messages 按 org_id 过滤）。
  2. 人工逐条给客户提的问题打标，二选一：通用 FAQ（行业节奏 / 常见问题，RAG 答得了）vs 订单特定（只有 ERP / 客户那张单子里有）。
  3. 算「通用 FAQ」占比，对照阈值拍板。
判定阈值：通用占比 ≥ 40% 才值得上 RAG。
低于 40%（预期结果）→ RAG 天花板极低，把这两周工程预算改投 copilot 草拟 + 人审——复用现有 confidence_score + pending_approval 审批闸门，投入产出比远高于检索增强。

这一天换来的是「用真实数据拍板」而不是「先建 pgvector 索引、接 embedding pipeline、再发现没题可答」——比直接上 RAG 省两周。

若验证过关（HOW，一句带过）

万一打标结果通用占比真 ≥ 40%：接 RAG 的工程成本极低——CREATE EXTENSION vector + 取消 008_knowledge_base.sql:27,55 那两行 vector(1536) 注释，无需改 schema，路早就铺好了。但那是 IF 之后的事，先把 IF 测出来。
