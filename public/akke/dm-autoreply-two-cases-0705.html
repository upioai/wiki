02根因 · 分通道

通道根因本质
浏览器端sec_uid 已唯一锁人，面板门却再用 VL 读昵称二次校验，遇花体/emoji/长名误读 → 假阴性拒发多余的假阳性拦截（主页门早已信任 sec_uid，面板门没跟上→不一致）
PC 端find_row_rect 精确等值匹配 + 不滚动；无 sec_uid，identity 只能靠读昵称定位机制脆 + 无唯一锁人手段的天花板
两通道共用失败即永久死锁：dm_reply_drafts 双层（唯一索引 + awaiting RPC NOT EXISTS）都以 status<>'discarded' 判占位，而失败写死 failed放大器：单次发送失败=该客户永久沉默，把偶发变成两天全灭
浏览器端(零星)rejected×4 集中一个号：真限频(7911) 还是 _check_rejected 误报待查疑账号被私信风控（待 P2 调查，不是这轮能定）
浏览器端(郭钰)wrong_user：sec_uid 直达偶发没落成个人主页 → 主页门 ocr_verify 拒发页面加载/导航抖动的瞬时故障（同号也有成功）→ #763 有界重试正好覆盖
两通道(饭粒「1」)卡 sending>15min：发送后 worker 未回调 complete_dm_reply → 挂 sending，sweeper 转人工脏 inbound（「1」当昵称）+ 回调缺失；#763 不覆盖此路径（它没走 failed），需单独治脏 inbound + 回调可靠性

🌐 浏览器端 剩余卡点

  • #764 需云电脑同步激活：镜像已更新，跑着的旧脚本还会 wrong_chat，直到 cloudpc-dom-dm-restart 拉新+重启。
  • rejected（零星）未解：sec_uid 帮不上，是真送达失败/限频。需拉 worker sent_log/Langfuse 区分账号问题 vs 误报（P2）。
  • 发送慢：process_web 用 VL/像素定位，3–4 次 VL 调用 → GUI ~40s（见 §05）。

🖥️ PC 端 剩余卡点

  • 无 sec_uid 天花板：identity 最终仍落在「读昵称」，花体名永远有残余误差，无法像浏览器端那样根治。
  • find_row_rect 加固未做（P1-b）：滚顶+core-char 模糊+点开验身份，尚未动手。
  • 误配风险：有大有小（web-only）被跑成 PC 模式产生了 no_row，需锁死 AKKE_DM_SCRIPT 含 web。
存量 failed 未解锁：有界重试只对新失败生效。两天里已 failed 的存量（零星 rejected×3 + 「爱笑的人」wrong_chat）不会自愈；Yang/雷声已手动 discard，其余需跑一次性解锁脚本。

05怎么优化到「15 秒级」端到端

现状实测端到端 ≈ 6.5 分钟，其中 C 发送段占 88%（均 340s）。要压到 15 秒级，得同时攻三块延迟——而不是只调一处：

先看 C 发送段为什么慢：自动回复不在私信框就地回，每条走 sec_uid 重开会话

机制：网页版私信箱是全局会话列表，就地回复要先在列表里认出目标会话——认错就把话发给上一个人。所以自动回复每条都从 sec_uid 地址栏直达对方主页 → 点「私信」开一个干净会话 → 身份门校验 → 键入发送（process_web）。用「导航到唯一主页」换「绝不发错人」，代价是每条多背 1 次整页重载 + 3~4 次 Qwen VL 调用。（DOM 版 send_dom 也走 sec_uid 开会话，区别只在它用 CDP/DOM 定位、零 VL——所以快，见下。）

sec_uid 路径 · 单条最快耗时拆解（GUI 段，固定 sleep 来自 douyin_dm_web_grounded.py）

步动作机制最快耗时
①地址栏直达主页 goto_profileCtrl+L→清空→SendInput 键入 URL→Enter→等整页重载~6.1s（固定 0.8+0.2+0.2+0.4 + 等待 4.5）
②主页身份门 ocr_verify1 次 Qwen VL 读主页、确认落到对的人~5–7s（1 VL）
③关注 + 点赞最新作品best-effort；无坐标/无作品即跳跳过=0s；真点赞+回主页+重导航 +15~20s
④点「私信」开面板 open_dm_panel1 VL 定位灰「私信」按钮 + 点击 + 等 3.5s~8–10s（1 VL + 3.5s）
⑤面板身份门 verify_chat_panel1 VL 读面板顶部对话对象是不是目标~5–7s（1 VL）
⑥输入框键入 + 点发送↑点输入框(1.0)+SendInput 中文键入+点发送(1.5)~4s
⑦送达核对 _check_rejected+_verify_bubbleVL 读拒收提示 + 气泡确认含本文案~5–7s（1 VL）
最快合计 ≈ 35 秒（③关注点赞跳过、每步一次过、零重试）。典型 ≈ 40–60s：命中作品要点赞并重导航（+goto_profile 4.0s）／面板首验假阴性 +2.5s 复核／OCR 判非主页要重导航（wait 逐次 +2.0s）。这 35s 只是 GUI 段——端到端还要叠上下面三块延迟（捕获轮询 15s + 草稿生成 ~48s + 180s 调度节流），才凑成 6.5 分钟。
对照 · 同样走 sec_uid，但换 DOM：douyin_dm_web_send_dom.py 连隐形 Edge :9222，用 CDP DOM 直接定位输入框（[data-e2e="msg-input"]），零 VL、零像素定位→ 同一条 sec_uid 开会话+键入+发送压到 ~10s。身份靠 DOM 读元素、不靠 VL 读花体名，顺带根治 wrong_chat。把 35s 砍到 10s 的杠杆是「VL→DOM」，不是「换掉 sec_uid」（sec_uid 是身份保险，两条路都留）。
延迟段现状15s 级手段目标
① 捕获轮询poll agent 15s 一轮（已优化）保持；或事件驱动~15s
② 草稿生成(A)~48s（webhook 未配 → */5 cron 兜底节流）配 webhook：客户回复即触发 chatReply，不等 cron~5–8s(LLM)
③ 调度到发送(C-排队)send 与 capture 同子进程，被 AKKE_DM_AUTOREPLY_INTERVAL(默认180s) 节流拆独立 send 支线挂主循环短轮询 / 草稿 ready 即发~5s
④ GUI 发出~30–40s（见下方分通道）见下方分通道浏览器 ~10s

🌐 浏览器端 → 15s 可达

关键杠杆：发送从 VL 换成 DOM。自动回复现走 process_web（像素/VL，3–4 次 VL ≈ 40s）；而 douyin_dm_web_send_dom.py 是 Playwright/CDP DOM 定位（连 Edge 9222，确定性、零 VL）。捕获侧早已是 DOM（web_capture_dom）——把发送也统一到 DOM：

  • GUI：40s（4 VL）→ ~10s（DOM 直接定位输入框+发送）
  • 身份：DOM 读 sec_uid/元素，不靠 VL 读花体名 → 顺带根治 wrong_chat

叠加 ②③ 事件驱动：草稿即时 + 独立 send 支线 + DOM ~10s ≈ 15s 端到端可达。

🖥️ PC 端 → 十几秒，稳 15s 较难

PC 客户端没有 CDP/DOM，只有 UIA + 像素，天花板比浏览器高。能做的：

  • 就地回复改「未读红点 + 新回复冒泡到顶」确定性定位（去掉按昵称 VL locate + 滚屏空跑）→ GUI 40s → 十几秒（memory「C 方案」）
  • identity 仍靠读昵称，无 sec_uid → 花体名残余误差在
战略建议：凡能登网页版的号，一律切浏览器端（DOM + sec_uid 双收益，直达 15s）；只有网页版登录被封、被迫留 PC 的号才吃 UIA「红点冒泡」加固，接受十几秒。
