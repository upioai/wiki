一句话总结：销售传一张聊天截图上来，剩下的基本不用人管。系统自动认字、自动蒸馏出「产品信息」和「金牌话术」两类料，大部分由 AI 判官直接落库、下次生成话术就吃得到，不用发版也不用等定时。只有涉钱 / 前后矛盾 / 疑似把客户和销售标反的那一小撮才留给运营人工把关——质量闸守着，没过关的内容碰不到线上话术。

01

两条口进来：① 人工整理成结构化文件；② 销售自助上传截图，系统用视觉模型（qwen2.5-vl）自动 OCR 识别文字。

04

话术是怎么"拼"出来的：案例注入到哪、Langfuse 管什么

料备好了，一次生成到底把哪些东西拼进了那条 prompt？企微 / 抖音是不是自动注入案例、Langfuse 到底管什么、调用路径长什么样、prompt 由哪几层叠成——四个问题一节答完。

① 生成话术时，案例是自动注入的 —— 是

企微好友代回
身份壳用中性"销售"、用"您" · 走 /api/wecom/chat/reply
抖音私信 / 评论
身份壳"小艳"、用"你" · 走 generateOpener / dm-auto-reply
两条通道共用同一个 chatReply 函数
每次生成话术都会自动把三层表拉出来，挑最相关的 3 条示例 + 4 条决策原则 拼进去。运营发话术时不用手动挂案例，灌一次库两条通道都生效。

② Langfuse 的真实角色 —— 不是它在"调用案例"

这里要纠正一个常见误解：案例的检索、排序、拼装全在代码里做（读数据库表）。Langfuse 只干两件事，都不碰案例数据。

✗ 它不做

不负责检索案例、不负责编排调用。你在 Langfuse 里看到的模板，只有一个"放示例的空位"，空位里填什么，是代码从数据库算好塞进去的。

✓ 它只做

模板托管：存话术模板的骨架，PM 能在后台改、30 秒生效。事后观测：记录这次喂了哪几条案例、花了多少钱。Langfuse 挂了也不影响话术生成（有兜底）。

③ 那真正的调用路径长什么样（全在代码里）

代码 chatReply() → getClient() OpenAI 兼容客户端 → OpenRouter chat completions API → 出话术
Langfuse 只旁挂两件：① getPrompt 出模板骨架 ② observeLLM 收 trace / 成本

拼 prompt、挑案例、算相关度、发请求——全在代码里完成；Langfuse 不碰案例数据、不发请求、挂了也不影响出话术。

④ 话术 prompt 由这几层拼成（叠进一个 system prompt）

1人设 PERSONA小艳 / 身份 · 口吻底子
2语气 STYLE用「你 / 您」· 长度 · 一次一问
3客户记忆 MEMORYcustomer_profile 跨会话
4称呼 + 客户画像这通对话已知的
5品牌档案brand_profile 品牌 / 卖点
6产品知识 knowledge_documents案例来的
7决策原则 decision_rules案例来的
8few-shot 示例 conversation_examples案例来的
9Langfuse 模板骨架4 步结构 + 规则 + 自检 + {{examples}} 占位

案例在哪一块？案例不是单独一层——蒸馏后分散注入到第 6、7、8 这三层：产品事实 → 知识、招式 → 决策原则、金牌问答 → few-shot 示例。所以「喂案例」能影响话术，靠的就是这三层里的案例料；其余几层是人设 / 语气 / 记忆 / 品牌骨架，跟具体案例无关。

05

对话背后的逻辑：客户发来一句话，系统怎么决定回什么

前面讲的是"料怎么备好、怎么拼进 prompt"。这一段讲运行时——一条真实的客户消息进来，到发出一句回复之间，系统一步步在做哪些判断。一句话贯穿始终：凡是代码能确定性判定的，绝不交给 AI 自觉；AI 只负责把话说得像人，"该不该回、能不能发"都有确定性闸门兜着。

cron /api/cron/dm-auto-reply → processAwaitingRow run.ts → 前置确定性闸 → chatReply 生成 llm.ts → gateDraft 置信度门 gate.ts → dm_reply_drafts.status

整条流水线的骨架。定时轮询 /api/cron/dm-auto-reply 每次捞一批"待回对话"（RPC dm_conversations_awaiting_reply），逐条喂进 processAwaitingRow 跑完下面这几步——每步对应的代码锚点都标在括号里。

先认个底：每通对话都有「阶段」

系统给每通对话记一个阶段，决定这一轮用什么口吻、走哪套规则。

ice_break 破冰 · 首次开场 → nurture 培育 · 多轮接话 → decision 临门 · 谈价 / 逼单

两条硬规矩：① 回复客户时永远走 nurture（哪怕阶段还卡在 ice_break 也纠正过来）——否则会拿"开场白模式"去接客户的话，把开场白当回复重发一遍（真踩过的坑）；② decision 谈判阶段默认转人工（怕一句话拍错就丢单），只有纯价格问答放行自动发。代码：stageForReplyDraft() 把 ice_break / 空阶段一律纠正成 nurture（generate.ts）；gateDraft 里 stage === "decision" 且非价格 → 转人工。

第一步：还没惊动 AI，先过一排「确定性前置闸」

很多场景根本不用麻烦 AI——代码一眼能判、直接确定性处置，又快又不会说错。这排闸决定这条消息要不要回、用什么方式回。

拦 客户发的是 [图片] / [视频] / [语音]

系统读不到里面的内容（只有个占位符），不硬着头皮瞎回，直接转人工——上手机 / 云电脑看了再回。isMediaPlaceholder() → 落 needs_human

↓

拦 这条"回复"其实不是客户说的

可能是我方自己发的气泡被抓回来了（回声循环），或是视频文案 / 界面文字被误当成客户消息。语义门认出来 → 不回，避免自己跟自己聊。回声比对 looksLikeOwnBubble() · 语义门 ensureInboundVerdict()

↓

确定性接 客户把微信号发过来了

不靠 AI 自觉说客套话——写死一句"添加您啦"确定性回过去（还会提醒去微信服务号点通过），把人稳稳接到微信侧。识别 customerGaveContact() → 固定模板 buildWechatReceivedText()

↓

确定性接 加微已完成，客户还在抖音说话

纯确认（"好的""嗯嗯"）→ 静默不回（阵地已转微信）；有实质新问题 → 走受限的"收尾 + 引导去微信"回复，不再没完没了地培育。wechatExchangeCompleted() + isShortAck()；实质消息走 generateExchangedClosingReply()

为什么先堆这么多确定性闸这些都是高频又容易翻车的场景。判断题（是不是图片、是不是回声、客户给没给号）交给代码，"一眼假"的错误就永远不会发出去；AI 只在"真得开口好好聊"时才上场。

第二步：真要"开口聊"，才生成——而且分场景走不同逻辑

到这一步才调 AI（chatReply），把上一节那 9 层料拼成 prompt 生成回复。关键是不同类型的客户，对话逻辑不一样。最典型、也最容易翻车的一类：

活案例 · 索取型客户（来要清单 / 手册 / 资料 / 案例 / 888）

这类人全程走「资料交付四步」，而且全程禁反问

① 证明有货（拿客户给的信息 + 两个具体的坑）→ ② 完整版还在我手上（整份是带图的表格，只先给一小块）→ ③ 说清为什么必须加微信（抖音发不了文件、发图会压糊，是平台限制不是借口）→ ④ 收尾是加 v 的引子，绝不甩一个问题回去。

为什么死磕"禁反问"：这类客户被回一句反问（"给个 v 我发你，你家几室几厅？"）最容易流失——他要的是"现在就给"，你回他一个问题 = 又给他派了个活，他就走了。越聊越容易掉，所以要给个加 v 的引子、赶紧把人接到微信。

技术上怎么落：源评论命中 isDataRequestComment() → 生成时 buildMaterialDeliveryHint()（material-delivery.ts）把这四步骨架 + 客户已知信息 + 该空间"具体的坑"拼进 prompt，并整条会话都带着（他后面报户型也一样禁反问）。柜体面积这类数字由代码 extractHomeFacts() 算好塞进去，不让 LLM 现编；"反问"由确定性正则 hasQuestionHook() 判，不靠 AI 自觉。

第三步：AI 写完不直接发，两层确定性闸门先把关

AI 会犯的错就那么几种固定形状，代码逐条兜——能修的当场修好再发（不静默丢单），修不动的才转人工。

哪一层闸拦什么怎么处置
生成层自查 + 重生成 生成崩（空 / 乱码 / 错语言）、索取型里冒出反问、超长、自曝私人生活（"我自己家装的时候…"） 修好再发 先重生成至多 3 次；仍不行就确定性修——砍掉反问句、压回长度、删掉穿帮句，不转人工、不丢单
generate.ts · 判 looksBroken/hasQuestionHook/hasSelfHomeStory/MAX_LEN → 修 repairMaterialDraft/condenseToLimit/dropSelfHomeStory
送出前置信度门 gateDraft 疑似回声循环、长度异常、索取型仍带反问、命中负面 / 投诉、decision 谈判阶段、闭口客套句号话（"有啥不懂随时问"把热客户晾凉） 转人工 任一命中 = 不自动发，落库等人接手
gate.ts · gateDraft() 返回 {autoSend, reason}，false → status=needs_human

过闸

自动发

  • 草稿标 dm_reply_drafts.status=approved，无影 / 云电脑 claim 后就地发出
  • 价格 2026-07-10 起全放开：价格讨论、AI 报的具体数字都直接发，不再卡等审批

这一节的骨架就一句话确定性的判断（是不是图片、是不是回声、有没有反问、超没超长、是不是谈判阶段）全归代码，AI 只管把话说得自然。所以"AI 会不会说错话"这个担心，大半被前后这几排确定性闸挡在了发送之前。

06

想改话术，该动哪一块？

「改话术」不是一件事，是四件事——落在不同地方、生效速度完全不同。先想清楚你要改的是哪一类，再去动对应的那块，别一上来就找代码。
