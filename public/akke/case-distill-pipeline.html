04

话术是怎么"拼"出来的：案例注入到哪、Langfuse 管什么

料备好了，一次生成到底把哪些东西拼进了那条 prompt？企微 / 抖音是不是自动注入案例、Langfuse 到底管什么、调用路径长什么样、prompt 由哪几层叠成、"最相关"那几条又是怎么挑出来的——五个问题一节答完。

① 生成话术时，案例是自动注入的 —— 是

企微好友代回
身份壳用中性"销售"、用"您" · 走 /api/wecom/chat/reply
抖音私信 / 评论
身份壳"小艳"、用"你" · 走 generateOpener / dm-auto-reply
两条通道共用同一个 chatReply 函数
每次生成话术都会自动把三层表拉出来，挑最相关的 3 条示例 + 4 条决策原则 拼进去。运营发话术时不用手动挂案例，灌一次库两条通道都生效。

② Langfuse 的真实角色 —— 不是它在"调用案例"

这里要纠正一个常见误解：案例的检索、排序、拼装全在代码里做（读数据库表）。Langfuse 只干两件事，都不碰案例数据。

✗ 它不做

不负责检索案例、不负责编排调用。你在 Langfuse 里看到的模板，只有一个"放示例的空位"，空位里填什么，是代码从数据库算好塞进去的。

✓ 它只做

模板托管：存话术模板的骨架，PM 能在后台改、30 秒生效。事后观测：记录这次喂了哪几条案例、花了多少钱。Langfuse 挂了也不影响话术生成（有兜底）。

③ 那真正的调用路径长什么样（全在代码里）

代码 chatReply() → getClient() OpenAI 兼容客户端 → OpenRouter chat completions API → 出话术
Langfuse 只旁挂两件：① getPrompt 出模板骨架 ② observeLLM 收 trace / 成本

拼 prompt、挑案例、算相关度、发请求——全在代码里完成；Langfuse 不碰案例数据、不发请求、挂了也不影响出话术。

④ 话术 prompt 由这几层拼成（叠进一个 system prompt）

1人设 PERSONA小艳 / 身份 · 口吻底子
2语气 STYLE用「你 / 您」· 长度 · 一次一问
3客户记忆 MEMORYcustomer_profile 跨会话 + 滚动摘要 context_summary（撑长对话不失忆，详见第 06 节）
4称呼 + 客户画像这通对话已知的
5品牌档案brand_profile 品牌 / 卖点
6产品知识 knowledge_documents案例来的
7决策原则 decision_rules案例来的
8few-shot 示例 conversation_examples案例来的
9Langfuse 模板骨架结构骨架（破冰 4 步 / 后续三步决策，详见第 05 节）+ 规则 + 自检 + {{examples}} 占位

案例在哪一块？案例不是单独一层——蒸馏后分散注入到第 6、7、8 这三层：产品事实 → 知识、招式 → 决策原则、金牌问答 → few-shot 示例。所以「喂案例」能影响话术，靠的就是这三层里的案例料；其余几层是人设 / 语气 / 记忆 / 品牌骨架，跟具体案例无关。

⑤ "最相关" 那几条是怎么挑出来的？两条通道，两套算法

上面说"挑最相关的 3 条示例 + 4 条规则"——这个"相关"怎么算，抖音和企微走的不是一套。贵的算法用在更值钱、量更小的通道上。

抖音 DM

bigram · 关键词式

  • 比客户这句和候选的字面重合度，本地算、不调外部模型
  • 快 + 免费：抖音是海量漏斗，每天成千上万条自动跑，每条都去算向量，延迟和账单都扛不住
  • 代价：换了说法的同义抓不太住（"用什么板" vs "板材啥牌子" 字面对不上）——但抖音多是短培育、靠骨架模板顶着，够用
企微 / 微信代回

语义向量 · bge-m3

  • 把客户这句和候选都转成"意思向量"，按意思接近度排（relevanceByEmbedding）
  • 抓得住换说法的同义："多少钱"≈"报价"≈"一平多少"
  • 企微是暖客/成交通道，量小、单条价值高、产品细节问答多，值得多花这点算力换更准的召回
  • 取不到 / 超时（8s）→ 自动退回 bigram，绝不因此卡住回复

向量现在"现算不落库"企微的向量是每次回复临时算、只存内存（冷启动就重算），没写进数据库——knowledge_documents 里的 pgvector 列至今还注释着。当前候选就 ~200 条（示例 128 + 规则 29 + 知识 43，单 org），现算够快够用，不落库不影响准确性（存不存库，匹配的还是同一串向量）。真正该落库的时机是示例库堆大之后（单 org 过 300–500 条）：那时每次现算上千条会变慢、易撞 8 秒超时、悄悄退回 bigram，才需要启用 pgvector 把向量落库 + 取 top-K 预筛。结论：现在不急，长大了再上（注：届时向量列维度要按 bge-m3 写 vector(1024)，不是注释里那个老的 1536）。

05

对话背后的逻辑：客户发来一句话，系统怎么决定回什么

前面讲的是"料怎么备好、怎么拼进 prompt"。这一段讲运行时——一条真实的客户消息进来，到发出一句回复之间，系统一步步在做哪些判断。一句话贯穿始终：凡是代码能确定性判定的，绝不交给 AI 自觉；AI 只负责把话说得像人，"该不该回、能不能发"都有确定性闸门兜着。想直接看代码锚点（入口 / 函数 / 文件 / 表）的，跳到第 07 节「技术逻辑 · 代码地图」。

先认个底：每通对话都有「阶段」

系统给每通对话记一个阶段，决定这一轮用什么口吻、走哪套规则。

ice_break 破冰 · 首次开场 → nurture 培育 · 多轮接话 → decision 临门 · 谈价 / 逼单

两条硬规矩：① 回复客户时永远走 nurture（哪怕阶段还卡在 ice_break 也纠正过来）——否则会拿"开场白模式"去接客户的话，把开场白当回复重发一遍（真踩过的坑）；② decision 谈判阶段默认转人工（怕一句话拍错就丢单），只有纯价格问答放行自动发。

第一步：还没惊动 AI，先过一排「确定性前置闸」

很多场景根本不用麻烦 AI——代码一眼能判、直接确定性处置，又快又不会说错。这排闸决定这条消息要不要回、用什么方式回。

拦 客户发的是 [图片] / [视频] / [语音]

系统读不到里面的内容（只有个占位符），不硬着头皮瞎回，直接转人工——上手机 / 云电脑看了再回。

↓

拦 这条"回复"其实不是客户说的

可能是我方自己发的气泡被抓回来了（回声循环），或是视频文案 / 界面文字被误当成客户消息。语义门认出来 → 不回，避免自己跟自己聊。

↓

确定性接 客户把微信号发过来了

不靠 AI 自觉说客套话——写死一句"添加您啦"确定性回过去（还会提醒去微信服务号点通过），把人稳稳接到微信侧。

↓

确定性接 加微已完成，客户还在抖音说话

纯确认（"好的""嗯嗯"）→ 静默不回（阵地已转微信）；有实质新问题 → 走受限的"收尾 + 引导去微信"回复，不再没完没了地培育。

为什么先堆这么多确定性闸这些都是高频又容易翻车的场景。判断题（是不是图片、是不是回声、客户给没给号）交给代码，"一眼假"的错误就永远不会发出去；AI 只在"真得开口好好聊"时才上场。

第二步：真要"开口聊"，AI 也照一套「骨架」来说

到这一步才调 AI（chatReply），把上一节那 9 层料拼成 prompt。但 AI 不是自由发挥——后续对话有一套明确的骨架框着它，比破冰那一句还厚，叠了四层（就是第 9 层"模板骨架"的真身，线上 dm.nurture.system）。

骨架① · 三步决策 —— 每轮开口第一件事，客户没归对档后面全走偏

1判意愿档先给客户归档：L0 抵触 · L1 试水 · L2 配合 · L3 求加
2按档选推进档A 给干货 · B 问 1 个细节 · C 钩子 + 要号 · D 直接给号
3先正面答原议题"问 A 答 B" 是信任流失第一杀手，必须先答再推进

还叠着的三层骨架

骨架层管什么线上真身举例
骨架②节奏 一回合只发一条、日常 ≤50 字 / 值得展开的节点 ≤80 字、禁换行禁分条、他多短你回多短 "真人金牌销售实测平均 38 字一个回合"
骨架③场景速查 十几条"读到 X 信号 → 走 Y 话术"，有的直接写死成成品句 问板材："板材分三档：颗粒板最实惠 ENF 环保 / 多层板防潮好贵一截 / 实木最环保再加钱。你最在意哪个？"
骨架④输出前自检 发之前逐条过 0–7 条，任一不过就删了重写 有没有反问、超没超 80 字、有没有乱甩我方号、有没有编"我自己家装的时候…"

上面这套是通用骨架，每条后续回复都走。碰到特定类型的客户，还会在它之上再盖一层更硬的分场景骨架，直接改写通用骨架的动作——最典型、也最容易翻车的一支：

分场景骨架（凌驾通用骨架）· 索取型客户（来要清单 / 手册 / 资料 / 案例 / 888）

这类人全程走「资料交付四步」，而且全程禁反问——把骨架③里所有"反问一句"的动作全作废

① 证明有货（拿客户给的信息 + 两个具体的坑）→ ② 完整版还在我手上（整份是带图的表格，只先给一小块）→ ③ 说清为什么必须加微信（抖音发不了文件、发图会压糊，是平台限制不是借口）→ ④ 收尾是加 v 的引子，绝不甩一个问题回去。

为什么死磕"禁反问"：这类客户被回一句反问（"给个 v 我发你，你家几室几厅？"）最容易流失——他要的是"现在就给"，你回他一个问题 = 又给他派了个活，他就走了。越聊越容易掉，所以要给个加 v 的引子、赶紧把人接到微信。

第三步：AI 写完不直接发，两层确定性闸门先把关

AI 会犯的错就那么几种固定形状，代码逐条兜——能修的当场修好再发（不静默丢单），修不动的才转人工。

哪一层闸拦什么怎么处置
生成层自查 + 重生成 生成崩（空 / 乱码 / 错语言）、索取型里冒出反问、超长、自曝私人生活（"我自己家装的时候…"） 修好再发 先重生成至多 3 次；仍不行就确定性修——砍掉反问句、压回长度、删掉穿帮句，不转人工、不丢单
送出前置信度门 gateDraft 疑似回声循环、长度异常、索取型仍带反问、命中负面 / 投诉、decision 谈判阶段、闭口客套句号话（"有啥不懂随时问"把热客户晾凉） 转人工 任一命中 = 不自动发，落库等人接手

最后：两个出口

过闸

自动发

  • 草稿标 approved，无影 / 云电脑 claim 后就地发出
  • 价格 2026-07-10 起全放开：价格讨论、AI 报的具体数字都直接发，不再卡等审批
没过

转人工（needs_human）

  • 躺库里、不推通知，绝不自动发一句可能翻车的话
  • 滞留哨兵 needs-human-watch 在 30 分钟 / 4 小时 / 24 小时 推 Lark 卡催人接

这一节的骨架就一句话确定性的判断（是不是图片、是不是回声、有没有反问、超没超长、是不是谈判阶段）全归代码，AI 只管把话说得自然。所以"AI 会不会说错话"这个担心，大半被前后这几排确定性闸挡在了发送之前。

06

最近一周补上的三块（2026-07-20 ~ 22）

上面 01–05 讲的是「案例怎么变话术、一条消息怎么决定回什么文字」。这一周又给运行时补了三块能力，分别补强了三个环节：会发图了（不只发文字）、记得住了（长对话不失忆）、能数了（把「约到店」变成看得见的指标）。三块都刻意走确定性、不额外烧 LLM，跟前面几节一个脾气。

① 图片素材：除了发文字，现在还会「发图」

以前 AI 只能打字。现在一条回复可以随文本一并甩几张图——效果图、户型布局图、配置清单长图、装修资料、官方海报。发不发、发哪张，全是代码确定性判的，不交给 AI 自觉（怕它乱发，被客户一眼看成群发素材反而更伤）。

能发的六类图 —— 各有各的来源和触发

图片本身不进数据库，托管在 R2 图床（22G 家底）；只有官方海报单独存一张表。发过的图会在会话里记个 [图片:xx] 标记，防同一张反复发。

类别是什么存哪什么时候发
效果图风格案例 11253 张实拍案例图，按「风格 × 空间」交叉（现代简约 × 卫生间…） R2 xiaoguotu/v2 客户提风格/空间、或泛泛要图；同分类里随机抽，避免每人收到同一批

怎么挑那一张：LLM 先出文字，发图是文字之后按优先级「一轮只发一类」地兜——五类图互斥，避免又刷屏又拖慢云电脑剪贴板：

客户发来图 → 只可能发布局图 否则→ 硬装类 → 发对应资料长图 → pickAsset 布局图 / 清单图 → matchZhishi 知识图集 → 兜底 galleryReplyFor 效果图

官方海报是另一条独立线（matchPosters 触发词命中即挂），跟上面五选一互不干扰。这些判定全是关键词/正则字典，没有一步问 AI——所以「该不该发图」这件事稳定可复现，不会今天发明天不发。

户型图识别 · floorplan-vision（唯一用到视觉模型的地方）

客户把自家户型图拍给你 → VL 读出「几室几厅」→ 选对应的标准布局示意图

这是发图链路里唯一调 AI（视觉模型）的一步：读户型图上有几个卧室、几个客厅。读准了就发那套户型对应的现成布局图。它不自己画图、也绝不猜承重墙——读不准（置信度不够）就老实说不知道、或退回按画像选，宁可不发也不瞎给（同全篇「一眼假的错误不发出去」的脾气）。

企微方案 B（能发图）
服务端把图的 URL 一起回给云电脑 → 云电脑下载 → 剪贴板 → Ctrl+V 内联发出，图和文字一起到。
抖音私信（发不了图）
平台限制：抖音发不了文件、发图会压糊。所以抖音这条不发图，只备料，等客户转到企微、被认领后再由企微侧发。

还差最后一口气：云电脑「取图」没接上客户发来的图，云电脑目前只读到一个 [图片] 占位符、拿不到图的原始像素。所以：户型图识别那条（B1）还在等取图才能真正验证；已知小坑——客户连发两张图，第二张会被悄悄丢掉。这块补上，发图闭环才算真跑通。

② 记忆工具：撑住长对话不失忆

夏夏反馈「聊到二三十轮，AI 把客户前面说的城市、面积、预算全忘了」。这块就是治长对话失忆的，落到 prompt 拼装的第 3 层「客户记忆」。

病根

为什么会「忘」

  • 历史一超 16 条只留最近 10 条，旧轮里客户说的城市/面积/预算全被截掉
  • 提取旧信息的正则只扫我方消息——客户自己说的信息压根没在扫
  • 写画像靠模型自愿调工具，59 条会话只写进 4 条
✓ 修法（自建，不上 mem0）

两条腿：抽画像 + 滚动摘要

  • 确定性抽画像：extractProfileFacts 用便宜的分析模型硬抽 7 个字段（城市/面积/预算/房型…），纯附和的话跳过省钱
  • 滚动摘要：context_summary 按「水位」增量把老对话压成一段摘要，直读 DB、不受 40 条窗口限，乐观锁防重复记
  • 回复后 after() 异步落库，不占云电脑等待时延；全程 fail-safe

诚实的注脚：能力造好了，还没派上用场50 轮记忆和「决策期」这两套至今0 次真实触发——因为实测 46 条真客户会话里，33 条客户开口不到 2 句就没下文，最长的真人对话也才 11 个来回。瓶颈不在「记不住」，在「聊不下去」。所以下一步不是继续堆能力，是拿真实案例去实测——没跑过的东西没法优化。

③ 到店引导：把「约到店」变成能数的指标

企微通道的业务目标本来就是「把客户引导到店」，可之前全仓没有任何一处度量它——日报报的是加了几个好友，跟「约成了几个到店」一点关系没有。结果所有话术改动在业务层不可证伪：只能看回归闸绿不绿，看不到到底约成没。这块补齐了从「催」到「数」的闭环。

催 决策期每条顺一个到店钩子（hookMode=always）

但把「用哪套话术」和「DB 记什么阶段」拆开了：话术按最近 4 条客户消息重算，客户一句「我再看看」的信号过去了就降温回培育期口吻；而 DB 里的阶段只进不退当漏斗指标用。防的是「随口说句我再看看 → 从此每条都被推到店」的催单机器人。

↓

数 约成判据 detectStoreVisitCommit（确定性，判据收紧）

必须有确定时间锚点（明天/周六/28号/下午三点）或明确应约（「好，那我过去」）才算约成；「哪天过去方便」这种反问不算——那还没约成。记进 conversations.store_visit_committed_at（只写第一次）+ 推绿卡告警。宁可少记：错记一个，到店转化率这个指标从第一天起就不可信。

↓每天 21:00 汇总

✅ 每天推「五档漏斗」到 Lark（/api/cron/wecom-funnel-digest）

每档都带「占上一档的比例」，一眼看出哪一级在漏。

新建会话 → ① 客户开过口 → ② 聊起来了 ≥3 句 → ③ 聊得深 ≥6 句 / 到过决策期 → ⑤ 约成到店

量出来才知道漏在哪漏斗把前段也量出来后，最大的漏点一目了然：不在「记不住」，在最前面——加上了好友但客户根本不开口 / 聊不过 3 句。所以「继续优化记忆/决策期话术」的边际收益其实在掉，真正该攻的是首触承接。日报还会自动挑出「客户说了话我方没回」的会话——那多半是云电脑没在跑，比改话术更该先查。

07

技术逻辑 · 运行时引擎的代码地图

第 05 节的每一步，落到代码上是哪个入口、哪个函数、哪个文件、通向哪个出口——开发照这张表顺藤摸瓜就行。贯穿全表一条设计原则：判断题归代码，AI 只管把话说得像人（是不是图片、是不是回声、有没有反问、超没超长，全是确定性判定，不靠模型自觉）。

cron /api/cron/dm-auto-reply → processAwaitingRow → 前置确定性闸 → chatReply 生成 → gateDraft 置信度门 → dm_reply_drafts.status

一条客户消息，走完这 11 步

顺序即执行顺序：前 6 步是"还没惊动 AI 的确定性前置分流"，第 7-8 步才生成，第 9-10 步是生成后的两层闸门，第 11 步落库分流。

08

想改话术，该动哪一块？

「改话术」不是一件事，是四件事——落在不同地方、生效速度完全不同。先想清楚你要改的是哪一类，再去动对应的那块，别一上来就找代码。

你想改的是对应上面第几层去哪儿改怎么生效
话术的步骤和规则
怎么开场、分几步走、该问什么、不该问什么、结尾自检		 第 9 层模板骨架 Langfuse 后台改模板：抖音 dm.ice_break.system / dm.nurture.system / dm.decision.system；企微 wecom.opener.rules / wecom.nurture.rules / wecom.decision.rules 最快 后台点保存，约 30 秒生效，不用发版。PM 自己能改
让 AI 学新东西
新产品、新报价、新的应对招式、新的金牌问答		 第 6/7/8 层案例来的三层 灌库：传案例 → 自动蒸馏 → 审核通过落 knowledge_documents / conversation_examples；跨案例的 decision_rules 跑蒸馏脚本 灌完即生效 下次生成话术自动读，不用发版。想让风格明显变化，蒸 decision_rules 最有效
品牌信息
品牌名、主营、价格区间、卖点、要不要透出微信号		 第 5 层品牌档案 后台人工填 brand_profile（不从案例自动抽） 改完即生效 整段注入，不用发版
人设和语气
叫什么名、什么身份、用「你」还是「您」、一句多长、一次只问一个		 第 1/2 层人设 · 语气 要改代码：src/lib/llm.ts 里的 PERSONA / SALES_PERSONAS（人设）、STYLE / WECOM_STYLE（语气硬底线） 最慢 属高危路径，必须走 PR + CI + 部署，不能直推 main
硬拦截护栏
「绝不能说这句」「不许编年限」「价格对不上就拦」——不靠 AI 自觉，代码强制		 不在这 9 层后置硬绑 要改代码：src/lib/llm/signals.ts（关键词硬绑）、sanitize.ts（清理）、price-guard.ts（价格） 最慢 同样走 PR + 部署；有单测，改完 pnpm test

一句话记住能不改代码就别改代码——「AI 说得不对」十有八九是案例喂得不够（灌库解决）或模板规则没写清（Langfuse 后台解决），这两条当天就能改完看效果。只有人设、语气底线、硬拦截这三类才必须动代码，那就得走 PR + 部署，快不了。
