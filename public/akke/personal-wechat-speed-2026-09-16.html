03 / Windows 电脑端Top 3 优化点：回复速度已经够快，能不能持续大范围跑

先看体验结论：客户消息进入当前微信对话框后，系统直接在这个对话框内完成读取、生成、认人、输入和发送，日常沟通已经达到“即时回复”的可用水平。

再看铺开结论：这套流程具备复制到多台 Windows 设备和多个销售人设的基础，Top 3 改动也都属于通用链路优化。当前能确认的是“速度已经够用、流程可以铺开”；长期大范围稳定性仍要靠每台设备的发送成功率、慢尾和错发记录持续监控，不能只用最快的一条案例作结论。

最大的三个优化点

TOP 1 · 无效会话

非客户行缓存与跳过

命中一次省 5–25 秒仅在跳过一条非客户会话时生效，不是每条回复都省

服务号、群聊、黑名单等已核实的非客户行记录画面特征；下一轮特征不变就直接跳过，只有红点、头像或内容变化才重新确认。

证据：v1.9.13 现场修复，服务号过滤不再消耗回复预算、缓存命中不再调用视觉模型；每命中一次，避开一次约 5–25 秒的无效打开与读屏。

TOP 2 · 发送确认

发送后改成本地像素取证

省一次 2–10 秒模型往返改动当时记录的收益口径

以前点击发送后，还要再调用一次视觉模型判断“是否真的发出”；现在直接比较输入框清空、消息区出现新气泡等本机画面变化。

证据：改动说明记的收益是“省一次 2~10 秒的大模型往返”。曾出现过的“18.5 秒 → 1.8 秒”是两个不同案例的分段相减，中间混着网络与卡顿，不作为本项收益。

TOP 3 · 认人方式

认人改小模型 + 只读标题条

省一次 2–10 秒模型往返与上一项同批改动，各省一次

发送前确认对象时不再读大块聊天画面，只读窗口顶部的客户名称，并改用更小的视觉模型；看不清仍然停止发送，防错发的闸没有放松。

证据：该环节实机分段样本约 1.7–3.7 秒；改动说明记的收益同样是“省一次 2~10 秒的大模型往返”。

Top 3 合计作用
三项是同一件事的三种形态：把本来要问一次大模型的判断，改成本机就能定，或者干脆不做——跳过已核实的无效会话、发送后自己看画面、认人只读标题条。按改动当时的口径，后两项各省一次 2–10 秒的模型往返，第一项每命中一次省 5–25 秒。端到端总账是旧完整案例 51.3 秒 → 最新三条中位数 18.7 秒；生成回复本身仍是 13.6–16.3 秒，是现在最大的剩余耗时。

对话框内的即时回复流程

01 / 发现检测到当前客户未读
02 / 打开进入这位客户的微信对话框
03 / 读取只读聊天区和连续气泡
04 / 生成服务端一次生成回复
05 / 发送在同一对话框内认人、输入、发送并本地确认

最终口径：当前速度已经足够支撑日常自动回复，18–20 秒左右可以让客户感知为“很快就回了”。大范围持续运行的基础流程已经具备；后续要盯的是生成阶段慢尾、不同设备的成功率和异常停发，确保扩到更多设备后仍保持同样体验。
