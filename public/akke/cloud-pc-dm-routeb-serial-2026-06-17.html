0 · 一句话架构

route-B（实时潜在触达）= 事件驱动：盯住「本号已关注、DM 过 ≥1 天没回的高/中意向 lead」，谁发了一条 ≤20min 的新视频，就到他视频下做三连：点赞 + 评论1（无影本地 qwen3 看视频现场生成）+ 评论2（逐字搬当初发他的 DM 原文）。
它不主动挨个发，只在对方发 ≤20min 新视频那一刻顺势触达——这是和「批量二触（已停用）」的本质区别。

2 · DM × route-B 串行共存逻辑（窗口锁）

问题：一台无影只有一个抖音前台窗口。DM（wuying_poll_agent → douyin_dm_grounded）和 route-B（_realtime_touch_consume → douyin_comment_grounded）是两个独立进程，都用全局的 SetForegroundWindow/SendInput 驱动这个窗口，并发会互抢焦点、混键入（发出串字）。原来只能「二选一」人肉避免。
方案 = 抢占式分时（非真并行），一把共享文件锁 + DM 占用标记：
.douyin-win.lock ← 谁操作窗口前抢、完事释放（互斥） .douyin-dm-want ← DM 一个发送批期间置上（route-B 据此让位） DM 端：with dm_batch(): # 置 .dm-want = "我在忙" for 每条: with window_turn('dm'): 发私信 # 贪婪抢 = 优先 route-B 端：for 每个三连: with window_turn('rb'): 发三连 ↑ 抢锁前先等 .dm-want 清除 = DM 在等就让位
  • DM 优先：DM 一有单就贪婪抢锁，route-B 不开新三连；
  • route-B 条目级让位：route-B 每发完一个三连释放锁，下一个三连前若 DM 在忙就等；
  • DM 最坏等 ~2.4min：若 DM 热单到达时 route-B 正在三连中途（三连不可打断、否则发串字），DM 等这一个三连发完即上；
  • DM 空窗（无单）：route-B 自由跑、填空窗；
  • AKKE_WINDOW_LOCK=1 才生效，只小文开，同事机器无 flag = 全 no-op、行为零变化；崩溃残留按 mtime>5min 抢占兜底。
时效口径（今天定死）：DM ≤10min（fresh_window_minutes=10，派单层选 lead）· route-B ≤20min（--max-age-min 20，不动）。锁不改「选哪些 lead」，只影响个别发送动作晚 ≤2.4min。

5 · 下一步待做优化列表

  1. 实战观察共存：DM ∥ route-B 挂几天，看真实撞车率 / DM 实际等待分布（验证 ≤2.4min 假设）。
  2. PR 归档：窗口锁模块 + DM 执行器改动（env-gated 只小文生效）走 PR；评论执行器仓库版（28384）与部署版（fanny 28984）漂移，PR 里一并对齐或单列说明。
  3. 洗池（bad case #6）：special-follow 生成加昵称/内容噪音过滤，剔商家号（防水/床垫/烤串/食品/旅游/宠物），提升真 lead 占比。
  4. 评论2 公开版话术（bad case #7）：去价格/微信红线词，做一套「公开评论安全版」comment2；脏的退化为只发 like+评论1。
  5. 切端点模式（bad case #9）：consume 加 --api-base + .env 给 PT_ENDPOINT_SECRET/AKKE_ACCOUNT_ID（注意 consume 不 load_dotenv，须进程 env），换来发前 claim 去重防狂发 + 自动 e2e 回写。
  6. 评论2 焦点抢占（bad case #3）：无人值守期约定别动无影 GUI；或加发送前前台二次确认。
  7. route-B 开机自启（bad case #10）：锁已保护，可把 _start-realtime-touch.bat 快捷方式丢 shell:startup，两条共存自启。
  8. 回写流程：本地表模式触达后，定期把 comment_log 拷回 mac 跑 mark-second-touch.ts --from-comment-log 写回 second_touch_state（节奏阶梯：每人每天≤1、累计 7 次出库）。
  9. （可选）DM 等待优化：当前 ≤2.4min 是单窗口物理下限，无法再压（三连不可中途打断）。如需 DM 绝对零等待，只能回到二选一。
