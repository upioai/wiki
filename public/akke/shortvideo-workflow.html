统一分怎么算（版本 u1.2）

排序不是按播放量，也不是按评论量——热闹 ≠ 有意向。四项归一加权：

维度权重含义
求资料条数 req0.35评论区有多少人在明着要资料/报价
求资料比例 ratio0.25要资料的人占抓到评论的比例（样本 ≥20 条才算）
中高意向数 intent0.20模型判定的真实购买意向条数
24h 增长 growth0.20近 24 小时评论增长速度

源码：src/lib/material-digest/unified-score.ts。改权重必须同时 bump UNIFIED_SCORE_VERSION，否则历史数据对不上账。

今天实测 · 2026-08-24 直接打 feed 拿到 4 条统一榜条目（unifiedItems），最新一天是 08-24，可回翻 08-23 / 08-22。 这条命令不需要任何密钥，本机就能跑，是判断「上游有没有断」最快的一招：

  -H "X-Store-Code: demo-2026" -H "User-Agent: akke-workbench/1.0" | head -c 400
这里踩过的坑 页面顺序曾经和飞书卡对不上。新口径（统一分）挑人、旧口径（意向加权）排序， 结果第 2 名在统一分里排第 8。教训写死在代码注释里：这个接口只读台账、一个数都不许现算—— 现算必然和已经推出去的卡片打架，而运营分不清是「口径变了」还是「系统坏了」。

第 04 屏这一下是要花钱的

登记出镜人时录的那段语音，会去做音色克隆：fal-ai/minimax/voice-clone，$1.50 / 次，按次计费。

参考音频必须 ≥10 秒，短了必定失败。克隆出来的 voice_id 存在 sw_persons，之后每条片子的配音都用它，不许在代码里写死。

第 06 屏是同步等的，十几秒

拆解走 analyzeVideoStructure()，模型是便宜的分析档 deepseek/deepseek-v4-flash。

失败会把 structure_status 落成 failed 并给一句人话，可以重跑；不排队、不异步——店长就站在屏前等结果。

「已交付」只有人能点

产线自己没有判交付的权限，最多把单子推到 review。这是刻意的：机器判自己做得好，等于没人审。

代价是——现在最大的钱漏就在这一步（见下面「钱」那节）。

发布为什么不是「点一下就发」

系统按流量算出 20:30 这种时间，人可能 23:00 才来点确认。做成即点即发，等于挑时间那件事白算。

所以是：draft（系统备好）→ 人点批准 → queued → 到点由云电脑发。

谁在跑：三层调度

① 提单 store-workbench

n8n 定时器 */30 0-6 * * * 调 POST /api/runner/auto-submit（钥匙 X-Producer-Key）。

一天目标 DAILY_TARGET = 3 条，硬帽是它的 2 倍（允许每条各换一次源片）。半小时重复调是幂等的：按当天已自动提的条数算名额，按 source_url 查全部历史去重。

② 唤醒工厂机 n8n

autoscaler 每 2 分钟查一次 /api/runner/jobs?claimable=1，有活就调 Fly Machines API 把 akke-video-worker 里 stopped 的机器 start 起来。

机器停着不是故障。它是 scale-to-zero 的，队列空时就该停机——监控刻意不判它的死活。

③ 干活 runner/daemon.py

拿号牌认领一条单，每 60 秒报一次心跳；看门狗 5 分钟没收到就判死（留了 5 倍余量，抖动不误伤）。

一条单最多自动重排 MAX_AUTO_ATTEMPTS = 2 次。每店同时在跑默认 2 条（VIDEO_MAX_PARALLEL_JOBS，硬上限 8）。

两条产线，一个开关 PRODUCER_ENGINE

express = 快车道，六步纯确定性，全程只调一次模型；orchestrator = 老复刻线，14 节点；session = 最老的大会话，逃生用。

代码默认是 orchestrator；2026-08-15 起线上按 fly secrets set PRODUCER_ENGINE=express 切到了快车道。此刻线上到底是哪条，我没验——要确认跑 fly secrets list -a akke-video-worker。

快车道 express/v1：六步

为什么会有它：老线在 2026-08-12～14 三天里连续 10 单全灭、成片 0 条。死因不是某个 bug，是结构性的——语义闸门一票否决、而且闸拦在付过钱之后。

付费窗口：为什么钱要绕一趟 n8n

所有花钱的调用（配音、口型、生图、图生视频）都不直接打 fal，而是提交给 n8n 的付费窗口，由它调 fal 并把账记回 Store（reserve_fal / complete_fal）。

  • 一次调用 = 一个 operation_id，由输入内容推导（sha256(binding)[:12]），不能按重试次数编号：换输入不换 id → 冲突；换 id 不换输入 → 重复付费。
  • 所以口型用的暂存签名 URL 必须落盘复用（TTL 6 小时）——重签一条新 URL 就是一个新操作 = 再付一次钱。
  • 付费窗口的重试比出稿慢一个数量级（60s / 180s / 300s）：连接断了不等于对面停了，n8n 那次执行还在轮询 fal，5 秒后重试等于造出第二次并发执行。

瓶颈不在产线，在审片。

$0 有三种含义，别看错
usd=null + warnings 非空真的缺价格表 → 去 usage_meter.py 补单价
usd=null + warnings 空压根没查过表 → 产线那侧的 bug
usd=0 且有 token 数不该出现 → 有人拿 0 冒充「没花钱」，最该查的一种
没有 warnings 这一列做对照，前两种在账面上长得一模一样。

06出问题了：先看哪四个地方

顺序别乱。从上往下，越靠前越便宜。

① 看板本身

wb → 视频生成：每条单卡在哪个状态、失败的写着人话原因。90% 的问题在这一步就能定位到「第几站」。

② 产线体检接口

/api/runner/pipeline-health，8 项判据，每一条对应一次真实事故。窗口最大 720 小时。

③ 每天 08:00 的自动体检

GitHub Actions pipeline-health.yml → 异常推 Lark 项目组群；全绿静默，但周一不管绿不绿都推一张（否则「定时器自己停了」和「一切正常」长得一样）。

④ 逐单日志

video_jobs.log：每一步的耗时、花了多少、闸门判了什么。上面三步定位不了才来这一步。

症状 → 去哪查 → 谁改

你看到的现象大概率在第几站怎么查改在哪
选题列表是空的 / 还是昨天的 站 1–3（上游） 直接 curl 那条 feed（见 ① 节，不用钥匙）；有数据就是工作台侧的事，没数据就是 Akke 昨晚没跑出来 Akke cron
页面看到 15 条，机器只提了 3 条 站 4 看名额（一天 3 条）和去重（同 source_url 全历史只做一次） auto-submit
今天一条都没自动提 站 4 体检 daily_submit。常见真因：僵尸单占满了并行额度（产线死了但状态还挂 running） 看门狗
单子一直 queued，没人领 站 5 工厂机没起来：看 n8n autoscaler 有没有跑、Fly 机器是不是 stopped n8n
running 很久，最后 heartbeat_lost 站 6 逐单日志看死在哪一步。注意：心跳只证明进程活着，不等于它在干活 runner
一批单子全失败 站 6 多半是同一个 bug。近例：写稿撞 HTTP 429 一秒判死、零重试，占一周失败的 71%，全卡在同一批自动提单 runner
主播说的和画面对不上 站 6 · plan 三条各自独立的真因：检索证据太薄（命中一个词就过闸）／语义列没进检索／字幕对错了正文 express/broll
片子后半黑屏但有人声 站 6 · assemble 容器时长 ≠ 视频轨时长。自检要同时查时长和帧数，只查时长看不出丢帧 express/io
成片音画差半秒 站 6 · assemble 逐格 round() 会攒误差，要按累计位置取整再相减；用 -frames:v 不用 -t express/steps
出了片但大脑费是 0 记账 看 llm_usage.warnings 是空还是有话（见「钱」那节的三态表） usage_meter
成片堆着没人审 站 7 体检 review_backlog。这是目前最大的钱漏，不是技术故障 人
页面上按钮点了没反应 任意 多半是状态值域漂了：DB 的 CHECK 约束和代码里的值域必须逐字一致，不一致时数据库静默拒写 video_jobs.sql
批准发布了但抖音上没有 站 8 发布是国内那台云电脑上的常驻程序拉走的（Fly 东京的 IP 被抖音挡着，发不出去）。先确认那台机器在线 publish 队列 + 云电脑
三条别忘的判断纪律 ① 取证失败 ≠ 事情为假。curl 超时、401、jq 报错，说明「没验成」，不说明「产线坏了」。
② 机器停着不是故障。工厂机是 scale-to-zero 的，队列空时它就该停机。
③ 没坐实根因前别改环境。改开关、改配置本身就是一次变更；失败时你不但没治好病，还多了一个新变量。
