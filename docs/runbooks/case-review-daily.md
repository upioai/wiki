# 对话到店专题：每天核对、总览与每日快照

用户要求每天更新，按日期回看，问题标明是否解决。总览 `/akke/cases/conversation-to-store`；每日 `/akke/cases/conversation-to-store-review-YYYY-MM-DD`。案例库已有总览入口。

## 当前发布授权

2026-09-24 用户在审阅总览、每日记录与页面结构后明确要求“上线”。本专题已获公开发布到 upio.ai 的授权；按此前每天更新的要求，后续对同一脱敏专题核对、更新并发布。公开内容仍限定脱敏案例总结、问题状态与修复证据，不扩散原始私有数据。

## 文件与生成

- `data/case-review/YYYY-MM-DD.json`：该日脱敏完整快照。
- `scripts/build-case-review.js`：生成总览与每日页。执行 `node scripts/build-case-review.js`。
- 问题编号 I01～I11 保持稳定；新增问题续号，禁止按排列顺序重编号。
- 同日更新原快照；跨日复制最新快照再核对，保留旧日证据与状态。新日期不能冒充已重新核对：只有成功读取对应来源才更新 lastChecked。
- 生成器会拒绝无解决日期或无行为证据的“已解决”。快照只放脱敏总结，绝不存原始消息、客户真实姓名、手机、微信号、内部会话 ID 或凭据。
- 专题是合集，不是第六位客户，不往客户 manifest 加假案例。

## 数据来源与步骤

1. 在 wecom-chat / upioai-wiki 仓 fetch 后读取 `origin/main`，不将主工作区文件当作最新代码事实。遵守各仓指令；对共享数据库只读查询，微信会话限定 `channel=wecom_chat`。
2. 原案例路径：xiangjia-2026-09-21、nifeng-2026-09-21、zhangzhibiao-2026-09-22、baihuting-store-visit、longwen-balcony。以原页会话证据定位，不仅凭相似昵称合并身份；白湖亭和龙文是地名，不是库里的客户昵称，可按原公开对话片段反查并校验通道、日期。
3. 查询 conversations / messages 的最新进展；必要时查对应 llm_call_provenance。凭据仅在本机连接使用，不输出、不存进快照。云端新增同文消息不能直接判定客户新回复，需核来源。
4. 对照最新 PR 内容、合并状态，读取 `https://wecom-chat.vercel.app/api/status` 生产 commit，再用 git 祖先关系核对部署覆盖。提交已合并、服务端已部署、客户端已安装、真实客户已改善分别记录。
5. 逐问题记录进展、PR、最近核对日期和验收条件。维护四态：unresolved 未解决；partial 部分解决；resolved 已解决（必须有对应行为验证）；verify 待核实（根因或关键证据不足）。取证网络失败不推导成未解决，也不自动降级已知状态；在 checkResult / checkNote 标记 partial 或 failed，并保留最后已知结果。
6. 填写 date、checkedAt（北京时间）、sourceWikiCommit、sourceCodeCommit、productionCommit、checkResult、checkNote。即使没有变化也留每日核对记录，无法核实时诚实注明。
7. 生成网页，跑 quote-guard 与 privacy-guard（覆盖 JSON 与 HTML），检查总览严格按“01 当前各案例状况 → 02 案例具体情况 → 03 问题与 bug → 04 对应解决方案”呈现。现状表和案例详情默认按本轮案例日期从早到晚，同日按时间；详情显示日期分组标题。更早历史起点单独标注，不混作排序日期。每案例在现状表和详情中均附显式“查看完整案例”按钮，链接绝对 upio.ai 原页。每日档案按日期新到旧。问题和方案用同一稳定编号互链，两处都显示状态。同步更新每例 currentSummary，不能保留过期总览一句话。验证状态筛选和日期跳转。当天未知的后续不得填成成交或到店。
8. 已有明确发布授权时，按 wiki README 的提交发布规则执行。上线后 HTTP 200 + 当日日期与状态计数匹配才记发布成功；无授权只留本地草稿。不要发送客户消息、改生产配置、修代码或推 Lark。
