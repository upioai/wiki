# 个人微信电脑端 Bug 集：新增记录规范

适用于 `public/akke/personal-wechat-pc-bugs.html` 中 **W-98 起**的新编号；W-01～W-97 是旧台账，不追溯补造画面。新增记录同时维护 HTML 台账和 `personal-wechat-pc-bug-guide.js` 的 `entries`、`highlights`、`scenes`。

每条新 Bug 必须有具体的微信场景还原，直接显示在卡片中，至少包括事发前、触发或事发后两个画面。画出客户消息、我方消息、系统提示或会话列表的相对顺序；每帧写清楚为什么这样还原。完整技术台账仍放在展开区。

- 有运营截图：`kind:'wechat'`，按截图还原微信聊天，说明哪些文字经过脱敏或意译。截图无法证明的时间、顺序和发送结果不要补写成事实。
- 只有日志：`kind:'log'`，以微信聊天或列表的示意卡片还原日志**能证明**的动作和先后，明确写“日志还原”、缺失原帧、无法确认的界面细节；不能冒称一比一截图。
- `source` 写具体证据类型与边界；两帧都要有标题、画面内容和说明。公开仓库不得提交未脱敏截图、客户身份、联系方式或原始私聊。推断与已确认事实分开标记。
- 证据不足以具体还原时，先补取截图或日志，暂不把猜测画面作为新编号发布。需要追踪的问题可以先留在非公开待核实流程，待有证据后再入 Bug 集。

提交前运行 `node tools/check-pc-bug-scenes.mjs --self-test`，PR 中同名检查必须通过。自动检查只验证**是否有结构化场景**，内容是否符合证据、是否脱敏仍需人工逐条复核。

## 修复与独立检验状态同步

`public/akke/personal-wechat-pc-bug-status.json` 是 Bug 卡片顶部“当前修复进度 / 独立检验”的公开数据源。页面打开时读取，之后每分钟重新检查；静态站只有在该 JSON 经 PR 合并并部署后才会有新状态，轮询不能自动发现另一个仓库的代码提交。HTML 详情中的旧“进度”是事故登记时记录，页面会标为“登记时进度”。

每个 W 编号修复由实现者在独立检验 agent 给出结论后，同步提交 Wiki 状态 PR；不得要求只读检验 agent 自行改公开台账。先在 `docs/runbooks/` 留一份脱敏的独立检验记录，再更新 `updatedAt`、`status`、`verification`、`review`（检验者、日期、记录链接）、`summary`、修复 PR 证据和 `needsAttention`，并核对进度与检验层级：

- `CODE_ONLY`：代码和定向测试已核，但要写清还缺服务端部署、正式包、目标电脑安装或真实微信场景中的哪一层；不能写“已验收”。
- `PASS`：所声明的完整修复范围已独立验收；涉及电脑端的事故还要有目标设备版本及同形真机场景证据。`FAIL` / `UNVERIFIED` 保留待关注。历史 Bug 没有独立报告时，页面明确显示“历史记录未复核”，不倒填通过。
- 状态、证据或范围有变化，修复方应在同一轮修复交付中更新这个文件，经隐私检查和 PR 发布；Wiki PR 未发布前只能说“状态同步待发布”。不要把另一个仓库的 PR 合并自动等同于设备装机或场景通过。

提交前运行 `node tools/check-pc-bug-status.mjs --self-test`、隐私检查，并打开页面验证卡片、待关注计数和 `#W-xx` 直达；上线后检查公开 JSON 与页面均是新版本。
